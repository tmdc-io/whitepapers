DuckLake: what it is, when to pick it over Iceberg, and how to run it in production

Architecture, speed, limits, adoption, four community projects, and a priced plan for AWS and Cloudflare

DuckLake is a lakehouse format that keeps all table metadata in an ordinary SQL database and all data in Parquet files. At the end of this page, you will know how it works, why its makers built it next to Apache Iceberg, where it is fast and where it is weak, how four community projects fit around it, and what a lean production setup costs on AWS and on Cloudflare.

Who this is for: engineers and architects who know what Parquet and a data warehouse are, and who must decide whether to run DuckLake for real. Read sections 1 to 4 to learn how DuckLake and its catalog work, sections 5 to 8 for the decision, and sections 9 to 12 for the build. The page does not teach SQL or DuckDB basics. Prices are list prices from November 2026 and are estimates, not quotes.

1 · What DuckLake is

two parts: a database for the facts, a bucket for the files

A lakehouse format is a set of rules that turns a folder of Parquet files into tables with transactions, schema changes and time travel. Apache Iceberg and Delta Lake do this with metadata files (JSON and Avro) that sit next to the data in object storage. DuckLake does it with tables in a SQL database. That database is the catalog database: one place that stores every snapshot, every file path, every column statistic and every schema version.

The DuckLake manifesto by Mark Raasveldt and Hannes Mühleisen of DuckDB Labs states the idea plainly: metadata is small, structured and changes often, so a database is the right home for it. The catalog database can be PostgreSQL, SQLite, MySQL or a DuckDB file. The data stays as normal Parquet files on S3, R2, GCS, Azure or a local disk. Any engine that speaks the format first reads the catalog with SQL, then reads only the Parquet files that it needs.

The diagram reads from top to bottom. Engines talk to the catalog database, and the catalog database points at files in storage.

Two results follow from this layout. First, a commit is one SQL transaction, so the catalog database gives DuckLake its atomicity and its conflict checks. Second, very small writes can skip the bucket. DuckLake calls this data inlining: if a write has fewer rows than a limit (10 by default in DuckLake 1.0), the rows go into a catalog table and not into a new Parquet file. A later flush moves them into Parquet in one batch.

The reference implementation is the ducklake extension for DuckDB. One statement attaches a lake:

INSTALL ducklake;
ATTACH 'ducklake:postgres:dbname=lake host=db.internal' AS lake
  (DATA_PATH 's3://my-bucket/lake/');
CREATE TABLE lake.events AS SELECT * FROM 'events/*.parquet';

2 · Why build it when Iceberg exists

the small-write problem and the metadata maze

Iceberg was created at Netflix in 2017 to fix Hive. Hive tracked tables as folders, and listing folders on S3 was slow and not transactional. Iceberg moved the facts into files: a metadata.json root, a manifest list, manifests, and then the data files. Each commit writes a new set of these files and then swaps one pointer in a catalog. The manifesto calls this a maze of JSON and Avro files, and it notes that Iceberg and Delta later added a database anyway (the REST catalog, Unity Catalog) to make the pointer swap safe.

The DuckDB team asked a simple question. If a database is necessary in any case, why not put all the metadata in it? The manifesto points out that BigQuery stores its metadata in Spanner and Snowflake stores its metadata in FoundationDB. DuckLake applies the same design to an open format. The team announced it on 27 May 2025.

The difference is largest for small, frequent writes, for example a stream of sensor rows. The figure shows one small insert under each design.

This is the source of the headline benchmark. In the data inlining post of 2 April 2026, DuckDB Labs streamed sensor rows in batches of 10. Against Iceberg (pyiceberg with Apache Polaris), DuckLake with inlining inserted 105 times faster (1,148.77 s against 10.88 s) and ran the follow-up queries 923 times faster (83.06 s against 0.09 s). The queries were faster because Iceberg had produced thousands of tiny files to scan. Read these numbers with care. The vendor ran the test, it used one writer, and the Iceberg run was cut to 100 seconds because the full 50-minute run took too long. The test shows a real design advantage for small writes. It does not show that DuckLake is 900 times faster in general.

For large batch loads, both formats write the same kind of Parquet files, and the gap is small. The main gains of DuckLake for big tables are simpler operations (one database to back up, no metadata files to clean) and fast planning, because a query plan needs one SQL query and not a walk through many small files.

3 · Inside the catalog

what the tables hold, and what happens on read, write, update and delete

To understand where DuckLake is fast and where it can choke, you must see what the catalog database does on each operation. This section follows the query steps in the DuckLake specification one at a time. Names and steps come from the spec 1.1 documentation. Spec 1.0 is the same in shape, with small name changes in the inlined tables.

3.1 The catalog tables

The catalog is about 29 ordinary SQL tables. You can open them with psql and read them like any other table. They fall into five groups. The figure shows the groups and the tables that matter most for performance.

Two ideas explain almost everything. First, snapshot ids are a single sequence for the whole catalog: 0, 1, 2 and so on. The snapshot_id column is the primary key of ducklake_snapshot. Second, most rows are versioned. A file row says "I am live from snapshot 12 until snapshot 30". If end_snapshot is NULL, the row is still live. Nothing is updated in place, except the table-wide statistics.

The statistics group grows fastest. ducklake_file_column_stats has one row for every column of every data file, with the minimum value, the maximum value and the null count. A table with 40 columns and 100,000 files has 4 million statistics rows. These rows are what lets a reader skip files, and they are also what makes the catalog heavy.

3.2 A read

A read is a short conversation with the catalog, followed by a long one with object storage. The sequence diagram reads from top to bottom. Each arrow is one request.

Step 3 is where the catalog earns its keep. The reader joins ducklake_data_file to ducklake_file_column_stats and keeps only files whose minimum and maximum can match the filter. For WHERE day = '2026-11-01', a table with 100,000 files can shrink to 30 files in one indexed query. Iceberg does the same pruning by reading manifest files from object storage. Steps 1 to 4 happen for every query, including dashboards that refresh every minute. So read traffic lands on the same database that writers use.

Time travel uses the same path with an older S. SELECT * FROM lake.events AT (VERSION => 30) runs steps 2 to 7 with S = 30. Old files stay readable until maintenance removes them.

3.3 A write

An insert writes the Parquet file first and then records it in one catalog transaction. If the insert is small enough for inlining, step 1 is skipped and the rows go into the inlined table inside the same transaction.

The commit itself is a handful of small inserts and updates. On a healthy PostgreSQL catalog it takes milliseconds. Two details matter later. Step 2 reads the latest snapshot id for the whole catalog, not for one table. Step 6 updates shared rows of table-wide statistics. If the commit fails, the Parquet file from step 1 is never recorded, and ducklake_delete_orphaned_files removes it later.

3.4 Delete, update and maintenance

DuckLake never edits a Parquet file. A delete writes a small delete file that lists row positions, and records it in ducklake_delete_file with a begin snapshot. An update is a delete of the old row plus an insert of the new row in one transaction. Each data file has at most one live delete file per snapshot, so a second delete on the same file writes a new delete file that replaces the first one. Small deletes are inlined in the catalog, just like small inserts.

The timeline below follows one data file through its life. Each bar is a catalog row with a begin snapshot and an end snapshot.

This design gives cheap deletes and full history, but every change adds rows and files. Maintenance turns the pile back into a small lake. The CHECKPOINT command runs six steps in order: flush inlined data to Parquet, expire old snapshots, merge small adjacent files, rewrite files that are mostly deleted (95% by default), delete files scheduled for deletion, and delete orphaned files. Expiry also removes catalog rows for dropped tables and deleted inlined rows that no remaining snapshot needs. If you skip maintenance, nothing breaks at once. The catalog just grows, and every operation in section 4 gets slower.

3.5 Two writers at once

DuckLake uses optimistic concurrency: writers do not lock anything up front, and they detect a clash at commit time. Because snapshot ids are one sequence with a primary key, two writers that both read 42 will both try to insert 43. The database lets one win. The figure shows what the loser does.

The conflict rules are fine-grained. Two inserts into the same table do not conflict. Deletes from different files of the same table do not conflict. Two deletes from the same data file do conflict, and so do changes to a table that another writer dropped or altered. The retry settings are ducklake_max_retry_count (default 10), ducklake_retry_wait_ms (default 100) and ducklake_retry_backoff (default 1.5).

The important point is scope. The clash happens on one sequence for the whole catalog, so a writer on table orders and a writer on table clicks also race for the next id. Neither has to abort, but only one commits at a time.

4 · When the catalog becomes the bottleneck

what PostHog hit, why it happens, and whether Iceberg has the same problem

The PostHog case

On 2 November 2026, PostHog published why it is moving its warehouse product off DuckDB. PostHog had rebuilt the product on DuckDB about five months earlier, with a DuckDB instance per customer and DuckLake catalogs on shared PostgreSQL instances. It put all of its own data in DuckLake as the first customer. When it decided to move, the lake held about 2 PB, about 1 trillion rows and 15.3 million snapshots.

PostHog reports these catalog problems:

  • A write to a single table could take more than three minutes, because each commit re-read statistics for the whole catalog.
  • More than 99% of the statistics rows belonged to tables that no longer existed. Deleting them made writes 30 to 50 times faster, but the rows grew back.
  • The number of connections that DuckLake opens to the catalog was a major problem on shared PostgreSQL, where each connection has a real cost.
  • The catalog schema must stay portable across PostgreSQL, SQLite, MySQL and DuckDB, so engine-specific tuning was limited. To stay compatible, PostHog carried patches in a fork.

It also reports problems outside the catalog: single-node DuckDB was hard to size for unpredictable customer queries, and serving many clients over the PostgreSQL wire protocol was hard to load-balance. PostHog moved to its own Trino build and a new table format of its own, HogLake. Its summary is that DuckLake was not designed for distributed scale from the start. PostHog builds a competing warehouse product, so read the post as one operator's experience at an extreme scale. The facts are still useful, because each problem maps to a part of section 3.

The five pressure points

The table links each symptom to its cause in the catalog design and to the fix that is available today.

The single sequence is the structural limit. Every successful commit in a catalog must take the next snapshot id. In practice, commits go through one at a time, so the catalog's commit rate is about one second divided by the length of one commit transaction. My rough estimate: at 20 ms per commit, a catalog does at most about 50 commits per second, shared by every table. At three minutes per commit, as PostHog saw, the catalog does one commit every three minutes. Inlining makes each commit cheaper, but it does not remove the queue.

Commit work that grows with the catalog turns a queue into a stall. A commit in the spec touches a few rows, so in principle its cost does not depend on catalog size. PostHog's report shows that the implementation at that time did more: it re-read catalog-wide statistics. DuckLake 1.1 made several catalog paths much faster, for example 102 times faster inlined commits on PostgreSQL. I cannot tell from the post which DuckLake version PostHog measured, so do not assume either way. Measure commit time on your own catalog as it grows.

Size grows with every change because history is kept until expiry. The worst item is ducklake_file_column_stats: files times columns. Many small files make it worse, which is why inlining, merging and a large target file size protect the catalog as well as the bucket. Dropped tables leave rows behind until snapshot expiry removes them, which matches PostHog's 99% stale statistics.

Connections fail first in multi-tenant setups. Each DuckDB process that attaches a PostgreSQL catalog holds its own connections. A PostgreSQL connection uses several megabytes of memory and the default limit is 100. Definite hit this limit in production, and so did PostHog. A connection pooler, or a single catalog server that speaks Quack, turns many clients into few connections.

Portability limits tuning. The spec targets four database engines, so the official schema avoids features of any one engine. You can add PostgreSQL indexes, but you cannot change table layouts and stay compatible. The roadmap lists "PostgreSQL catalogs at scale with automatic or suggested index creation" and "PostgreSQL performance (fewer roundtrips, stored procedures)", which are the same problems that PostHog reported.

How the catalog grows with data volume

The catalog does not grow with bytes or rows. It grows with four counts: data files, columns per file, snapshots and tables. Data volume reaches the catalog only through the file count, and the file count depends on file size. So two lakes of the same size can have catalogs that differ by a factor of a thousand.

The largest catalog table is ducklake_file_column_stats, with one row per column per file. The figure shows its size at three lake sizes, at the default DuckLake target file size of 512 MB and 40 columns, and for a petabyte lake made of small files. The last bar is the estimate by Alireza Sadeghi (November 2025): 100 million files at 10 columns.

A catalog with 80,000 or 8 million statistics rows is small work for PostgreSQL. At 80 million rows, it needs good indexes and enough memory to keep them cached. At about 1 billion rows, Sadeghi argues that a full DuckLake will likely struggle without heavy tuning, a larger server, or a distributed SQL database underneath. He also works out what one large query costs: a scan over 1 million files with 20 columns reads 1 million file rows and up to 20 million statistics rows before pruning. These are his estimates. Nobody has published a measurement at that size.

Snapshots grow with the commit rate, not the volume. Whether a commit carries 10 rows or 10 GB, it adds one snapshot row and one change log row. The table shows what a steady commit rate adds in one year if you never expire snapshots.

PostHog's 15.3 million snapshots sit in this range. Expiring snapshots keeps the count flat, and it also removes the statistics of dropped tables, which were 99% of PostHog's statistics rows.

Sadeghi gives useful history and context. Hive stored only folder locations in its metastore, so planning needed slow file listings on S3, where one list call returns at most 1,000 objects. Iceberg, Hudi and Delta fixed this by writing file lists and statistics into metadata files beside the data. He describes DuckLake as a small step back toward a central metastore, but with the full file list, per-file statistics and snapshots stored in it. He grants that a database is the better home for metadata, and that the design avoids Hive's listing problem and Iceberg's file clutter.

He also points to a design detail in BigQuery. Jordan Tigani compared DuckLake's statistics tables to BigQuery's CMETA metadata system. Sadeghi notes that BigQuery keeps a separate metadata table for each user table, not one central table, which lets it scale out. DuckLake keeps one statistics table for the whole catalog. This is one more reason why splitting a large lake into several catalogs helps. He reports that Hannes Mühleisen showed a test with 100 million snapshots in a talk, but no details were published. His conclusion is that DuckLake has real potential, but mostly for small and medium self-hosted lakes, and he notes that far more organizations store less than 100 TB than store petabytes.

In practice, three habits keep the catalog small at any data volume: large files (keep the 512 MB target, keep inlining on and run compaction), fewer and larger commits, and snapshot expiry on a schedule. With those, 1 TB and 100 TB look almost the same to the catalog.

Does Iceberg have the same problem?

Partly. Iceberg also has a commit point, also uses optimistic concurrency, and also grows metadata that maintenance must trim. The differences are in where the load lands and in the scope of the clash. The figure puts the two designs side by side.

Commit scope differs most. An Iceberg commit writes new metadata files and then swaps one pointer for one table in the catalog. Writers to different tables never race. Writers to the same table do race, and the loser re-reads the latest metadata, rewrites its manifest list and metadata.json, and tries again, by default up to 4 times (commit.retry.num-retries in the Iceberg configuration). So Iceberg has a hot-table problem, and DuckLake has a hot-catalog problem. Streaming jobs on Iceberg commit to one table often, which is why teams usually commit every minute or so and not every second.

Metadata growth is the same kind of problem in a different place. Every Iceberg commit writes a new metadata.json that lists the snapshots, plus a manifest list and manifests. Without maintenance, planning reads more and more small files, and each commit rewrites a larger root file. Iceberg's maintenance guide lists the same jobs that DuckLake needs: expire snapshots, remove old metadata files, compact data files and rewrite manifests. A neglected Iceberg table also gets slow. The difference is that a neglected Iceberg table slows down itself, while a neglected DuckLake catalog slows down every table in it.

Connections differ by protocol. Iceberg clients talk to a REST catalog over HTTP, or to a cloud API such as AWS Glue. HTTP is stateless and easy to load-balance, so many clients do not hold many open sessions. Many REST catalogs still store their state in a relational database (Apache Polaris, for example, can use PostgreSQL), but the service in front of the database controls the number of connections. DuckLake clients open the catalog database directly. PostHog's complaints about the PostgreSQL wire protocol come from this. The REST API on the DuckLake roadmap, or a Quack catalog server, would put a service in front of the database in the same way.

Planning cost moves in opposite directions. Iceberg planning reads manifests from object storage, so it costs network round trips per query but spreads across the storage service. DuckLake planning is one indexed SQL query, so it is fast but adds load to one server. At small and medium scale, the DuckLake way is faster and cheaper. At very large scale, the database becomes the part that you must scale up and protect.

Design rules that follow

Split catalogs along the lines where you never need a transaction across tables: one catalog per tenant, per domain or per environment. Each catalog then has its own snapshot sequence, its own statistics and its own connection budget. PostHog put all of its data in one lake, which put all of its commits in one queue.

Write fewer, larger commits. Batch streaming rows for a few seconds, keep inlining on for the stragglers, and flush inlined data often. Aim for a commit rate per catalog that stays well below what your measured commit time allows.

Run maintenance from the first day, and watch the catalog like a production database. Track the row counts of ducklake_snapshot, ducklake_data_file and ducklake_file_column_stats, the count of inlined tables, the connection count, and the commit time. Set an alert when commit time doubles. The queries are in section 12.

Put a pooler or a server in front of the catalog. PgBouncer in front of PostgreSQL, or one Quack catalog server, keeps the connection count flat as clients grow.

Know when to leave. If you need hundreds of commits per second into one catalog, a single catalog over 10 million snapshots, or many engines from many vendors, you are in PostHog's position, and Iceberg (or a distributed engine on top of it) is the better tool.

5 · Speed: DuckDB 2.0 and the catalog

reads got faster on object storage, and the catalog got faster at scale

Version names

The version numbers are confusing, so here they are in one place. DuckDB 2.0.0 shipped on 21 October 2026 as a long-term support (LTS) release, supported until at least October 2027. On the same day, the DuckLake specification moved to 1.1 and the DuckLake extension moved to 2.0 (see the release calendar and the DuckLake 1.1 post). The 2.0 extension still reads and writes 1.0 catalogs. Migration to spec 1.1 is opt-in with AUTOMATIC_MIGRATION true. The DuckLake roadmap uses the name DuckLake 2.0 for a future specification with branching and roles, which is a different thing.

Reads: asynchronous I/O

Before 2.0, a DuckDB worker thread waited while it fetched each byte range from S3. DuckDB 2.0 adds asynchronous I/O: a separate pool of I/O threads fetches row groups ahead of time, and workers stay busy. On TPC-H Q6 at scale factor 100 on S3 (EC2 r7i.16xlarge, same region), a 22 GB Parquet file scanned in 2.84 s against 8.23 s on DuckDB 1.5.5, about 3 times faster. With tuning it took 2.23 s and filled the 25 Gbit/s network link. Four concurrent queries finished in 15.6 s against 35.8 s. A large CSV scan dropped from 878 s to 45 s. The same post found that Parquet row groups of about 2 million rows gave the best scan time on S3. On a warm local disk, the change makes almost no difference.

For DuckLake this matters directly, because DuckLake data is Parquet on object storage. The settings to know are read_ahead_depth (default unlimited, bounded by memory), async_threads, and the HTTP retry settings.

Writes: inlining and commit cost

Write speed in DuckLake depends mostly on commit cost, and commit cost depends on the catalog database. With inlining on, a small commit is one database transaction. In the DuckLake 1.1 release, commits of 100,000 inlined rows became 46 times faster on a DuckDB catalog and 102 times faster on a PostgreSQL catalog. Large writes are Parquet writes and scale with CPU and network. The default target file size in DuckLake is 512 MB, which suits S3.

The Quack protocol is also new. Quack is an HTTP protocol that lets one DuckDB process act as a server for other DuckDB clients. In the DuckDB benchmark, it moved 10 million rows in 0.89 s, against 2.90 s for Arrow Flight and 25.64 s for the PostgreSQL wire protocol. For small single-row transactions it reached 5,434 per second with 8 threads. It is beta in 1.5.3 and a polished release in 2.0. It binds to localhost by default and needs a TLS reverse proxy for remote use.

Catalog efficiency

The catalog is where DuckLake wins or loses at scale. DuckLake 1.1 fixed several slow paths. The table shows the measured changes from 1.0 to 1.1, on one laptop with PostgreSQL 17 on the same machine.

The catalog choice changes what you get. A DuckDB file allows one writing process. SQLite allows one writer at a time, and DuckLake retries lock conflicts for you. PostgreSQL (version 12 or newer) is the recommended catalog for many users and remote clients. The catalog guide warns against MySQL because of known issues. A DuckDB catalog served over Quack is a newer option for a single server with many clients.

The PostgreSQL catalog got the largest gains in 1.1, as the table shows. Version 1.1 also lets a PostgreSQL catalog inline VARIANT values, which only DuckDB catalogs supported before. It stores row group counts in the catalog, keeps exact minimum and maximum values for strings (1.0 kept only the first 256 bytes), and prunes files for more filters: OR across columns, IS NULL, and fields inside structs. Read the numbers with two limits in mind. DuckDB Labs measured them on one laptop with PostgreSQL on the same machine, so network round trips were close to zero. In production, each round trip to a remote catalog costs from half a millisecond to a few milliseconds, and one operation can need many of them. In a smoke test of the catalog growth benchmark, one small inlined commit made about 20 round trips, so 2 ms of network delay turned a 5 ms commit into a 47 ms commit. And some PostgreSQL work is still open: the roadmap lists PostgreSQL catalogs at scale with suggested indexes, and fewer round trips with stored procedures, as future work.

pg_ducklake takes a different route for writes (see 9.1). Its native writer commits inside PostgreSQL itself, so a write needs no network round trips to the catalog. That helps only if the catalog runs inside the pg_ducklake extension. How catalog size affects these numbers is in section 4.

6 · Limits and sharp edges

what to plan for before the first production table

The engine ecosystem is narrow. DuckDB is the full implementation. Spark, Trino, DataFusion and Pandas clients exist, and the DuckLake 1.0 post lists them, but they come from MotherDuck, Hotdata and individual developers. Snowflake, BigQuery, Athena, Databricks and Redshift do not read DuckLake natively. If a team outside yours queries the lake with one of those engines, Iceberg is the safer format.

The catalog database is a single point of write coordination. If PostgreSQL is down, nobody can commit or plan queries. You must run it with backups, point-in-time recovery and high availability, just like any production database. Definite reported that its catalog failed on connection count, not on load: every query worker, ingest job and dashboard refresh held a catalog connection. Use a connection pooler such as PgBouncer from the first day. Section 4 explains how the catalog becomes a bottleneck and what PostHog saw at 2 PB.

Type mapping on PostgreSQL loses detail. With a PostgreSQL catalog, inlined UBIGINT values become VARCHAR and nested types become strings. VARIANT inlining on PostgreSQL arrived only with spec 1.1. Inlined rows also pile up if nobody flushes them. Definite found one table with an 835,000-row gap between the snapshot and the Parquet files, spread across more than 3,000 inlined tables.

Scale at petabytes is unproven. Alireza Sadeghi estimated that a 1 PB lake holds 50 to 100 million files, which means about 100 million rows in the file table and about 1 billion rows of column statistics. A PostgreSQL instance can hold that, but it needs tuning and indexes. The DuckLake roadmap lists "PostgreSQL catalogs at scale" as a goal, which confirms that the work is not done. Section 4 shows how the catalog grows with file size and commit rate.

Some features are missing or young. There are no built-in roles or access control in the format today, so you control access with storage credentials and database grants. Puffin deletion vectors are experimental. Spatial file pruning is not implemented. Quack is new. Maintenance is your job: you must schedule the flush, merge, snapshot expiry and file cleanup jobs (see section 12).

Version drift between tools is real. The DuckDB 2.0 storage format cannot be read by older DuckDB versions, which matters if you use a DuckDB file as the catalog. If you migrate a catalog to spec 1.1, every client must run DuckLake 2.0. In November 2026, pg_ducklake pins DuckDB 1.5.6, swanlake uses DuckDB 1.5.x, and boilstream uses DuckDB 1.5.2, so all three still expect spec 1.0. pg_ducklake has an open tracking issue for DuckDB 2.0 and spec 1.1.

7 · DuckLake or Iceberg

the answer depends on who else reads the data

The question to answer first is not size. It is how many different engines and teams read and write the tables. Iceberg is a standard that every large vendor supports. DuckLake is simpler and faster for the DuckDB world. The table puts the main factors side by side.

FactorPick DuckLakePick Iceberg
EnginesDuckDB is the main engine, plus some Spark or TrinoSnowflake, BigQuery, Athena, Databricks or Flink must read or write
Write patternMany small writes, streams, CDC, frequent updatesLarge batch loads, few commits per minute
Data sizeUp to tens of terabytesHundreds of terabytes to petabytes
TeamOne platform team owns the stackMany teams and vendors share the tables
OperationsYou already run PostgreSQL wellYou want a managed catalog (Glue, Polaris, Unity, R2 Data Catalog)
GovernanceStorage credentials and database grants are enoughYou need fine-grained policies in a catalog service

Definite's rule of thumb, after a year of DuckLake in production, gives size bands: DuckLake for up to 5 TB with one team, either format from 1 to 50 TB, and Iceberg above 50 TB with many engines. Definite sells a DuckDB-based product, so treat this as an operator's view, not a neutral study. The bands match the design: DuckLake is simplest when one database and one engine family run the show.

The choice is less final than it looks. DuckLake writes Iceberg-compatible Parquet data and delete files. Since DuckLake 0.3, iceberg_to_ducklake() copies an Iceberg table into DuckLake with only metadata changes, and a copy in the other direction also works. Fuller Iceberg and Delta interoperability is on the roadmap. A team can start on DuckLake and move hot tables to Iceberg later if a new consumer needs them.

8 · Adoption, activity, future

fast release cadence, thin public case studies

Development is active. Releases came in May 2025 (0.1), July 2025 (0.2), September 2025 (0.3), March 2026 (0.4), April 2026 (1.0) and October 2026 (spec 1.1, extension 2.0). DuckLake 1.0 merged 108 pull requests, and more than 200 bug fixes landed between 1.0 and 1.1. The non-profit DuckDB Foundation governs the project, under the MIT license and without venture funding. The DuckDB 2.0 preview announced a technical advisory board that covers DuckDB, DuckLake and Quack.

Usage is growing fast, but evidence of production use is thin. The DuckLake extension had more than 1.5 million downloads in the week of 12 to 18 October 2026, and DuckDB Labs calls it the most downloaded lakehouse extension for DuckDB. MotherDuck (vendor) offers managed DuckLake with three options: fully managed, bring your own bucket, and bring your own compute. MotherDuck says that dozens of companies use DuckLake and that about one quarter of pull requests come from the community. Two companies have written about production use in detail. Definite still runs DuckLake. PostHog ran its warehouse product on DuckDB and DuckLake for about five months, reached about 2 PB, and in November 2026 announced a move to Trino and its own format, mainly because of catalog and scaling limits (see section 4). Skeptics remain: The Register quoted Russell Spitzer of Snowflake, who said that it is too early to know if the concept will succeed. Snowflake sells an Iceberg-based platform, so it competes in this market.

The specification is open. The full specification is public: every catalog table, every column, and the SQL steps for reads, writes and commits. The reference implementation is on GitHub under the MIT license. Anyone can implement it without permission or fees, and several teams outside DuckDB Labs did (see section 9). There is no lock-in: the data is plain Parquet, and the catalog is ordinary SQL tables that you can read with psql.

Governance is less open than Iceberg's. Apache Iceberg is an Apache Software Foundation project, where committers from many companies vote on changes in a public process. DuckLake's specification is written mainly by DuckDB Labs, and each new specification version ships on the same day as the DuckDB extension, so in practice the reference implementation sets the specification. The announced technical advisory board is a step toward wider control. PostHog's experience shows the current limit: it could not get changes accepted upstream fast enough and kept patches in a fork. If you need a voice in the format's direction, you have less of one than with Iceberg.

The roadmap (October 2026) lists these priorities for the next major specification: branching and clones, protected snapshots, a REST API, and roles with access control. If time permits: PostgreSQL catalogs at scale with suggested indexes, better MySQL support, Iceberg and Delta interoperability, pluggable catalogs, and Bloom filters for better pruning. The roadmap says that nothing is guaranteed. In my view, the REST API and roles are the two items that decide whether DuckLake reaches companies with strict governance needs.

The tutorials that you shared show the range of today's use. The Tobiko SQLMesh tutorial (August 2025) builds a laptop lakehouse with a DuckDB-file catalog and keeps the SQLMesh state in a separate DuckDB file. Its remark that DuckLake tables do not support UPDATE does not match current releases, which support UPDATE, DELETE and MERGE. The Leafcloud post (February 2026) by Gábor Szárnyas publishes a read-only lake on public object storage, with the catalog file and the data in the same bucket. That pattern is a good, cheap way to share open data. It is not a multi-writer setup.

9 · The four projects

each one fills a different hole around the core format

The four repositories in this folder do not compete. Each one adds a piece that DuckLake does not ship: a writer inside PostgreSQL, a network query server, a serverless catalog, and a streaming ingest service. Each entry below gives the role, the facts and a verdict.

These four projects are part of a wider set of DuckLake implementations. They come in three kinds, and only the second kind replaces the catalog itself. The table lists the ones found in this research. Smaller projects on GitHub may exist.

For a production catalog that is not plain PostgreSQL, the choice is thin today. pg_ducklake is the only mature option, and it is PostgreSQL underneath. quacklake and the Quack catalog server point to a serverless or single-server future, but both are young.

9.1 pg_ducklake

Rolecatalog and writer inside PostgresLicenseMITVersionv1.0.3, DuckDB 1.5.6

pg_ducklake is a PostgreSQL extension from relytcloud. It adds CREATE TABLE ... USING ducklake, so DuckLake tables live inside a normal PostgreSQL database next to ordinary tables. PostgreSQL holds the catalog and the inlined rows in a ducklake schema. DuckDB, embedded in the extension, runs the analytical queries. Outside DuckDB clients attach the same catalog with METADATA_SCHEMA 'ducklake'.

Its strongest part is a native writer (RFC-001) for INSERT and COPY. Many PostgreSQL sessions write concurrently into inline tables, and the metadata commits in one PostgreSQL transaction, with retries on conflict. A background worker flushes inlined data and expires snapshots every 60 seconds by default. Its feature list shows 58 supported and 11 missing features, for example views and CREATE SCHEMA. It supports PostgreSQL 14 to 18. It is the most active of the four projects, with 318 commits in 2026 and regular tags.

The main limit is hosting. RDS, Aurora and Cloud SQL do not let you install arbitrary extensions, so you must run PostgreSQL yourself (on a VM or with a Kubernetes operator) or find a host that accepts the image pgducklake/pgducklake.

SolidThe best choice when an application already writes to PostgreSQL and you want those rows in the lake within seconds, without a separate pipeline.

AskCan we self-manage PostgreSQL, or does our platform only allow RDS or Cloud SQL?

9.2 swanlake

Rolequery serverLicenseMITVersionv0.1.0, DuckDB 1.5.x

swanlake is a Rust Arrow Flight SQL server with DuckDB inside. It gives a shared network endpoint for ADBC and JDBC clients, in front of a DuckLake with a PostgreSQL catalog and data on S3, R2 or a local disk. Each client session gets its own DuckDB connection, up to 100 sessions by default. A status page on port 4215 shows latency percentiles and slow queries. Several instances can run side by side, and they use a PostgreSQL advisory lock so that only one of them runs the daily CHECKPOINT.

Its benchmark (TPC-H at scale factor 0.1, 4 clients) gives 10.4 queries per second with local files and 4.9 with S3, so data on S3 was about 2.1 times slower. These are small, single-run numbers. The project has one tag and recent commits are mostly dependency updates. Quack in DuckDB 2.0 now covers part of the same need, with a faster protocol in the DuckDB benchmark.

Useful, earlyA good fit when clients need a standard Flight SQL or JDBC endpoint, for example BI tools or Go and Java services. Plan to own the code if you depend on it.

AskDo our clients need Flight SQL or JDBC, or can they use DuckDB with Quack directly?

9.3 quacklake

Roleserverless catalog on CloudflareLicenseMITVersion0.2.1, alpha

quacklake, by the GitHub user tobilg, runs a DuckLake catalog on Cloudflare Workers and Durable Objects. Each catalog is one Durable Object with its own SQLite database. Clients speak the Quack protocol to the Worker and attach with ATTACH 'ducklake:quack:host:443'. Data files go to R2. It adds JWT and OIDC login (Cognito and Entra ID guides), catalog policies and short-lived R2 credentials of 30 to 120 seconds.

The README says plainly that it is an alpha. It has 7 commits and one author. Clients need nightly builds of the quack and ducklake extensions. Transactions are emulated, and there is no conflict detection between sessions, so you must treat each catalog as single-writer. Row filters apply only to catalog access, not to the Parquet files.

PrototypeA clear look at where Cloudflare-native DuckLake can go: no database to run, one catalog per tenant, and login built in. Do not put production data on it yet.

AskIs a single writer per catalog acceptable for this use case?

9.4 boilstream

Rolestreaming ingest and servingLicenseclosed source, free tierVersion0.10.64, DuckDB 1.5.2

boilstream from BoilingData is a multi-tenant Rust server with an embedded, forked DuckDB. It accepts data over Kafka, Arrow Flight, Flight SQL, HTTP Arrow and the PostgreSQL wire protocol, and it writes into DuckLake on S3 with inlining. The vendor says that rows commit to the hot tier every second and that HTTPS Arrow ingest exceeds 2 GB/s. It also offers streaming views, materialized views and full-text search. A Helm chart runs it as a three-pod StatefulSet.

The repository in this folder holds only docs, a Helm chart and examples. The binaries are closed source. The free tier is capped at 8 vCPU and 2 pods per cluster in cluster mode. Release churn is high: one version was withdrawn, and the changelog recommends 0.10.64 as the first safe release after 0.10.29.

CommercialWorth a test if you need Kafka-compatible ingest into DuckLake without Flink or Spark. Weigh the closed source and the vendor dependency.

AskWhat happens to our pipeline if the vendor changes the license terms?

10 · Production architecture

one catalog, one bucket, small stateless compute

A lean production DuckLake has four layers. The figure shows them from the users at the top to storage at the bottom. The same shape works on AWS, GCP, Azure and Cloudflare. Only the products change.

Three design rules come out of the figure. First, keep the compute stateless, so that you can scale it to zero and replace it at any time. Second, put the catalog database and the bucket in the same region as the compute, because every query starts with a catalog round trip and then reads Parquet. Third, scale DuckDB up before you scale it out. One DuckDB process on a large machine uses every core, and a few separate processes share the catalog for concurrency.

Option A: AWS (or GCP and Azure)

Use S3 for data and RDS PostgreSQL or Aurora PostgreSQL for the catalog, with RDS Proxy or PgBouncer in front. Run DuckDB on Graviton EC2 instances for long jobs, or on ECS Fargate or Lambda for short jobs. For a shared query endpoint, run DuckDB 2.0 with Quack behind an nginx or ALB TLS proxy, or run swanlake. If you need sub-second freshness from an application database, add pg_ducklake on a self-managed PostgreSQL. If you prefer not to run any of this, MotherDuck offers DuckLake with your own S3 bucket. On GCP, the same plan uses GCS, Cloud SQL and Cloud Run. On Azure, it uses Blob Storage, Azure Database for PostgreSQL and Container Apps.

Option B: Cloudflare

Use R2 for data. R2 has no egress fee, so analysts and BI tools anywhere read the lake without a transfer bill. Cloudflare does not offer managed PostgreSQL, so put the catalog in a managed PostgreSQL service in a region near your R2 bucket (for example Neon, Supabase or a small RDS instance). Set the R2 location hint to match that region. Hyperdrive speeds up PostgreSQL calls from Workers, but DuckDB does not run inside a Worker. DuckDB runs in Cloudflare Containers, which are billed per second and sleep when idle. Use a Worker as the front door for auth and routing.

Know the limits. A Cloudflare container is small (at most 4 vCPU and 12 GiB of memory in the largest standard instance at the time of writing), so heavy transforms and large joins belong on a larger VM. Containers suit spiky, interactive query load. When quacklake matures, it can replace the external PostgreSQL with a catalog per tenant in Durable Objects.

Option C: hybrid, R2 for storage and a cheap VM for compute

Because R2 charges nothing for egress, the compute can run anywhere. A common low-cost setup puts data in R2 and runs DuckDB plus the PostgreSQL catalog on one or two VMs at a low-cost provider or on EC2 near the R2 region. You pay R2 storage, the VM and nothing for data transfer out of R2. Network latency between the VM and R2 is higher than inside one cloud, and asynchronous I/O in DuckDB 2.0 hides much of it. Use an EU provider and an EU R2 jurisdiction if data residency matters, as the Leafcloud example shows.

11 · What it costs

storage is cheap, egress and always-on compute are not

The model uses one realistic team-size workload: 1 TB of Parquet in storage, 1 million write requests and 10 million read requests a month, 300 GB a month read directly by clients outside the cloud, one query server with 2 vCPU and 8 GiB running all month, and one small PostgreSQL catalog. Ingest and transform jobs are extra and scale with your data volume.

Four lessons come from the table. Storage is the smallest line at this size, and R2 is about 35% cheaper than S3. Egress decides the winner when clients read Parquet directly from laptops or SaaS tools: at 300 GB a month the AWS bill is $18, and at 5 TB a month it is about $450, while R2 stays at zero. Always-on compute on Cloudflare Containers costs about 2.6 times more per vCPU than EC2, so Cloudflare wins only when the server sleeps most of the day. The hybrid setup is cheapest, at the cost of some network latency and two vendors to manage.

Three settings protect the bill on any cloud. Keep inlining on, because it turns thousands of tiny PUT requests into a few large ones. Run compaction, because fewer and larger files mean fewer GET requests per query. Put the query server next to the data, and send results to users, not raw Parquet, when users are outside the cloud.

12 · Rollout plan and runbook

four phases, each with an exit test

Phase 1 is a pilot of two weeks. Pick one real dataset with both batch and small writes. Run DuckDB 2.0 LTS with a PostgreSQL catalog and one bucket. Load it with SQLMesh or dbt. Measure query latency, commit latency and the request count on the bucket. The exit test: the pilot meets the latency target with a catalog on the smallest database tier.

Phase 2 hardens the stack. Turn on point-in-time recovery for PostgreSQL and versioning on the bucket. Put PgBouncer in front of the catalog. Store bucket credentials in a secret manager and scope them per job, because DuckLake has no roles yet. Write down the version pins for DuckDB, the DuckLake extension and the catalog spec, and do not migrate to spec 1.1 until every client supports it. The exit test: you restore the catalog and the bucket to a point in time in a drill.

Phase 3 adds maintenance and monitoring. Schedule the jobs below. Alert on catalog connections, catalog row counts, the count of inlined tables, file count per table, commit time and query latency. The exit test: one week with no manual action.

-- every 15 minutes: move inlined rows into Parquet
CALL ducklake_flush_inlined_data('lake');
-- hourly: merge small files into larger ones
CALL ducklake_merge_adjacent_files('lake');
-- daily: drop old snapshots, then delete files no snapshot uses
CALL ducklake_expire_snapshots('lake', older_than => now() - INTERVAL '7 days');
CALL ducklake_cleanup_old_files('lake', older_than => now() - INTERVAL '7 days');
-- weekly: remove files that the catalog never recorded
CALL ducklake_delete_orphaned_files('lake', older_than => now() - INTERVAL '7 days');
-- or run all of the steps above in one command
USE lake; CHECKPOINT;

-- catalog health: run in PostgreSQL, alert when these jump
SELECT count(*) FROM ducklake_snapshot;
SELECT count(*) FROM ducklake_data_file WHERE end_snapshot IS NULL;
SELECT count(*) FROM ducklake_file_column_stats;
SELECT count(*) FROM ducklake_inlined_data_tables;
SELECT count(*) FROM pg_stat_activity WHERE datname = 'lake';

Function names come from the DuckLake 1.x maintenance docs. Make sure that the names and arguments match the extension version that you pin. Keep the snapshot retention at least as long as your longest time-travel need.

Phase 4 opens the lake to users. Add the query server (Quack behind TLS, or swanlake for Flight SQL clients). Add pg_ducklake if an application must stream rows into the lake. Test boilstream if you need Kafka-style ingest. Review the setup against the decision table every six months, and plan an Iceberg export for any table that a new outside engine must read.

13 · Open questions

what nobody has measured in public yet

How large can a PostgreSQL catalog grow before commits slow down? PostHog reached 15.3 million snapshots and saw single-table writes take more than three minutes. Nobody has published the same test on DuckLake 1.1, which made several catalog paths much faster. The catalog growth benchmark in this folder grows a PostgreSQL catalog to 10 million files and snapshots, and measures attach, query planning, commit time and parallel commits at each step, with optional network delay. A first smoke test on a laptop ran only up to 20,000 files. With 2 ms of added round-trip delay, one small inlined commit took about 47 ms, not 5 ms, so one commit made about 20 round trips to the catalog. Run the full benchmark before you size a production catalog.

How does DuckLake perform with many concurrent writers on one table? The published benchmarks use one writer, and Quack tests stopped at 8 threads because of a DuckDB limit on concurrent inserts into one table.

Will the large query engines add native DuckLake support? Until Snowflake, BigQuery, Athena or Databricks read DuckLake, it stays a format for the DuckDB world plus Spark and Trino clients.

When will the REST API and roles ship? The roadmap names them as the top priorities for the next major specification, with no date. They decide whether companies with strict access rules can adopt DuckLake without extra tools.
