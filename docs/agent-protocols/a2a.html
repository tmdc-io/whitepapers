Agent2Agent (A2A), end to end

spec, task lifecycle, bindings, evolution, adoption, SDKs, security and examples, as of A2A v1.0.1

A2A is the open standard for one AI agent to hand work to another agent it can't see inside, often one run by a different team or company. By the end of this page you'll know when you need it and when you don't, how agents find each other, how a task moves from submitted to completed, what travels over the wire, how A2A relates to MCP, how far adoption really goes, and where the security risks sit.

A note on bias: the author's company builds data products that agents reach through open protocols. This page names none of those products and argues for no vendor, including his own.
Who this is for: engineers building multi-agent systems who want the protocol from first principles. Builders should read sections 3 to 6, then 13 and 16. Readers weighing A2A as a platform bet can start with sections 2, 9, 11 and 14. Unfamiliar terms are defined in the glossary, and section 18 condenses the page into checklists. It assumes you know what JSON, HTTP and an LLM agent are.

1 · Why A2A exists

delegation across a boundary you can't see past

An agent that books freight for your company may need a quote from a supplier's agent. The supplier won't give you its prompts, its tools or its database. It will only accept a request and send back a result. Before A2A, every such pairing needed its own integration: a bespoke API, a bespoke message format, a bespoke way to report progress. A2A, the Agent2Agent protocol, standardises that exchange so any compliant agent can delegate to any other.

Google announced A2A on 9 April 2025 with more than 50 technology partners, and donated it to the Linux Foundation that June. Since August 2026 it has been a project of the Agentic AI Foundation, the same home as MCP (section 8). The first diagram shows the problem A2A solves and how it sits next to MCP.

The A2A project describes this split itself: MCP is vertical and A2A is horizontal. MCP deepens one agent by giving it tools. A2A connects agents across a team, department or company boundary. The defining property is opacity. The remote agent's prompts, tools, memory and reasoning stay private; you see only what it chooses to advertise and what it sends back. Everything else in this guide follows from that choice.

2 · When you don't need it

most multi-agent systems never cross a boundary

A2A solves a real problem, but a narrower one than the volume of announcements suggests. Many multi-agent systems are a planner and a few specialist agents in one codebase, sharing one framework. A framework like LangGraph or CrewAI already passes state between them in-process, with no network hop, no serialisation and no authentication to manage. Adding A2A there buys distance you don't need. The decision flow below is the author's rule of thumb, not something the specification prescribes.

The middle question matters most. If the remote side behaves like a function (send inputs, get an answer, no follow-up), an MCP tool is simpler, and the A2A project itself says skills of that kind can be exposed as MCP-compatible tools. A2A's advantage is the conversation: a task that runs for hours, asks clarifying questions, needs fresh credentials midway, and returns several artifacts. If you need none of that, you don't need A2A.

The honest complication is that MCP's July 2026 revision narrowed the gap. It added long-running tasks and a way for servers to ask for input mid-call, so "wrap the other agent as an MCP tool" now covers more cases than it did a year ago. Section 11 compares the two in detail.

3 · The moving parts

two agents, a card, and four nouns

A2A has two roles. The client agent acts for a person or a system and starts the exchange. The remote agent, also called the A2A server, does the work. Before talking, the client reads the remote agent's Agent Card: a JSON document describing who it is, what skills it offers, where to reach it and how to authenticate. Everything then travels as four kinds of object: a Task (a unit of work with a lifecycle), Messages (turns in the conversation), Parts (pieces of content inside a message) and Artifacts (the outputs a task produces). The component diagram shows how they fit.

Two design choices shape how agents behave in practice. First, a remote agent can answer with either a Message or a Task. The project's guide to the task lifecycle describes messages for quick, stateless replies and tasks for work that needs tracking. Some agents only ever return messages, some always create tasks, and many do both, using messages to agree the scope of work and a task once there's something to execute.

Second, a contextId groups related tasks and messages into one conversation. The client reuses it to continue a thread, and can run several tasks in parallel inside one context: book a flight, then a hotel and an activity that both depend on it. The remote agent typically uses the context id to manage its own model's conversation state, which the client never sees.

4 · What the specification defines

one data model, three bindings, eight subsections

4.1 How the spec is built

Version 1.0, released on 12 March 2026, reorganised the specification around a single source of truth. The v1.0 notes make the protocol buffer file, a2a.proto, the normative definition of every object and operation. Three bindings then map that model onto wire formats: JSON-RPC 2.0, gRPC and plain HTTP with JSON. All three run over HTTPS and are specified to behave the same way, so an agent can offer whichever its clients prefer (section 6). The current release is v1.0.1, a 26 May 2026 patch that changed no wire behaviour.

The operations are few. A client can send a message and wait (SendMessage), send one and stream the updates (SendStreamingMessage), fetch, list or cancel tasks (GetTask, ListTasks, CancelTask), reattach to a task's stream after a dropped connection (SubscribeToTask), manage push-notification webhooks, and fetch a fuller Agent Card after authenticating (GetExtendedAgentCard).

4.2 Agent Cards and discovery

An Agent Card is a remote agent's public description. The discovery guide lists what it holds: identity and provider, the endpoints where the service can be reached, supported features such as streaming and push notifications, the authentication schemes it accepts, and a list of skills, each with a description, example prompts and the media types it takes and returns. Since v1.0, endpoints live in a supportedInterfaces list where each entry names its URL, its binding and its protocol version, so one agent can serve old and new clients side by side.

Clients find cards in one of three ways. A public agent publishes its card at https://{domain}/.well-known/agent-card.json. A company can run a registry that collects cards and lets clients search by skill; the specification doesn't yet define a standard registry API. Or a client is simply configured with the card's location. Cards can be signed: v1.0 specifies JSON Web Signatures over a canonical form of the card, so a client can check that a card really came from the agent's owner. Anything sensitive belongs in the extended card, served only after authentication.

4.3 The task lifecycle

Every task moves through a fixed set of states. The diagram groups them the way the protocol treats them: two states before and during work, two interrupted states where the client must act, and four terminal states.

Three rules follow. Interrupted is not finished. In INPUT_REQUIRED the agent is waiting for an answer from the client, perhaps a question for a person; in AUTH_REQUIRED it needs fresh credentials. The client replies with a message carrying the same task id, and work resumes. Terminal is final. The lifecycle guide says a finished task can't restart; a refinement such as "make it red" becomes a new task in the same context, pointing back with referenceTaskIds. That makes every artifact traceable to exactly one unit of work. Rejection is a valid answer. An agent can decline work it won't do, which matters when the client is a stranger.

In v1.0 the states are written in upper case with a prefix, such as TASK_STATE_INPUT_REQUIRED, replacing the lowercase names of earlier versions. Code written against v0.3 has to change these strings.

4.4 Messages, parts and artifacts

A message has a role (ROLE_USER for the client, ROLE_AGENT for the remote agent) and a list of parts. In v1.0 there's a single Part type whose content is exactly one of four fields: text, raw (inline bytes, base64 in JSON), url (a file reference) or data (structured JSON), each with a mediaType and an optional filename. An artifact is a task's output: a name, an id and its own list of parts. The lifecycle guide recommends that agents keep an artifact's name stable across refinements and give each version a new id, so clients can track versions on their side.

4.5 Streaming, polling and push

A2A offers three ways to follow a task. A client can call SendMessage and either wait for the result or ask for an immediate return and poll with GetTask. It can use SendStreamingMessage and receive a Server-Sent Events stream of status and artifact updates; the streaming guide says the server closes the stream when the task ends or is interrupted, and a dropped connection can be resumed with SubscribeToTask. Or, for tasks that run for hours or days, it can register a push notification webhook and get called back on significant changes, then fetch the full task.

Push notifications reverse the usual direction of trust, so the spec is explicit about both sides. The server should not post to any URL a client supplies, since a malicious client could aim it at internal systems; allow-lists and ownership checks are the suggested defences. The webhook, in turn, must verify that a notification really came from the agent, for example with signed tokens checked against the agent's published keys, and reject stale or replayed ones.

4.6 Security and identity

A2A deliberately reuses existing standards rather than inventing its own security. An Agent Card declares which schemes it accepts: API keys, HTTP authentication, OAuth 2.0, OpenID Connect or mutual TLS. Version 1.0 also modernised the OAuth options, according to the v1.0 notes: it removed the implicit and password flows, added the device-code flow for command-line and headless clients, and added a flag to require PKCE. Clients authenticate with those standard schemes over HTTPS, and the discovery guide strongly recommends dynamic credentials over static secrets embedded in a card. Section 14 covers what this does and doesn't protect against.

4.7 Extensions and multi-tenancy

Extensions let a community add capabilities without changing the core. An Agent Card lists the extensions an agent supports and marks some as required, so a client knows in advance whether it can work with that agent. Payments (section 12) arrived this way. Version 1.0 also added native multi-tenancy: a tenant field on every request lets one endpoint host many agents, with a default tenant declared on each interface in the card.

4.8 Errors and versions on the wire

Errors in v1.0 follow Google's google.rpc.Status model on every binding, with an ErrorInfo object naming the reason, such as TASK_NOT_FOUND, under the domain a2a-protocol.org. Clients send an A2A-Version header on each request, and a server that doesn't support that version rejects it. Combined with per-interface versions in the card, this is how old and new agents coexist (section 7).

5 · One delegation, end to end

a quote request that needs a person's answer

The sequence follows a freight agent asking a supplier's quoting agent for a price. Midway, the supplier needs a detail only a person can give. Read it top to bottom; the shaded bands mark discovery and the task itself.

Three things in the picture are worth pausing on. Discovery happens once and can be cached; the discovery guide recommends ordinary HTTP caching headers on the card. The remote agent decides on its own that it needs input, and says so through the task state rather than a special request type. And the person never talks to the quoting agent: the freight agent relays the question, so the supplier never learns who the person is unless the client chooses to say.

          "mediaType": "text/plain"
        }
      ]
    }
  }
}

The server opens a stream and, after some work, sends this event. The question for the person rides inside the status as an agent message:

          "mediaType": "text/plain"
        }
      ]
    }
  }
}

On the new stream, the quote arrives as an artifact update, followed by the completed status:

{
  "jsonrpc": "2.0",
  "id": "req-2",
  "result": {
    "artifactUpdate": {
      "taskId": "t-81",
      "contextId": "ctx-7",
      "artifact": {
        "artifactId": "art-q1",
        "name": "quote.pdf",
        "parts": [
          {
            "url": "https://quotes.supplier.example/q/881.pdf",

            "mediaType": "application/pdf"

      },
      "index": 0
    }
  }
}

Field names follow the v1.0 JSON conventions in the v1.0 notes: events are told apart by their wrapper (statusUpdate or artifactUpdate) rather than a type field, and the end of the stream signals that the task has stopped.

6 · The three bindings

same model, three ways to carry it

Every A2A operation exists in all three bindings, and v1.0 specifies them to be equivalent. Pick by your clients and your infrastructure, not by features.

BindingWhat it looks likeStreamingGood fit
JSON-RPC 2.0One endpoint; method names such as SendMessage in the bodyServer-Sent EventsThe default in most samples; easy to debug
gRPCProtocol buffer services generated from a2a.protogRPC server streamingService-to-service traffic inside one company, high volume
HTTP+JSONResource paths such as POST /message:send and GET /tasks/{id}Server-Sent EventsTeams used to REST tooling, gateways and caches

An agent can offer several bindings at once by listing them in supportedInterfaces, in order of preference. Version 1.0 dropped the /v1 prefix from HTTP paths, leaving versioning to the interface entry and the A2A-Version header, and v1.0.1 recommends the media type application/a2a+json for the HTTP binding.

7 · Versions and migration

v0.3 to v1.0 was a real migration

The jump to v1.0 broke a lot. The v1.0.0 release notes list 16 breaking changes. The ones most code hits are the unified Part type, the new upper-case state and role names, stream events identified by wrapper rather than a kind field, the Agent Card's move to supportedInterfaces, cursor-based pagination for task lists, and the switch of errors to google.rpc.Status. The migration notes rate the Part change as the most disruptive.

The same release also built in a way to avoid repeating the pain. Because each interface in a card declares its own protocol version, an agent can expose a v0.3 interface and a v1.0 interface at the same time, and a client picks the newest one it understands. The project suggests three phases: read both formats, emit v1.0 while still accepting v0.3, then drop v0.3 once clients have moved. The roadmap's next version, v1.1, is planned as an evolution within the v1 line rather than another break (section 17).

9 · Adoption, read carefully

broad support; thinner evidence of use

A2A's adoption story is real but needs sorting by evidence type, because "supports A2A" covers everything from a logo on a slide to agents in production. The table separates the claims by what they actually show.

Two things are missing that MCP has. There's no public usage figure comparable to MCP's SDK download counts, and no named, quantified production deployment in the sources reviewed for this page. That doesn't mean A2A isn't used; cross-company agent traffic is exactly the kind companies don't publicise. It does mean the adoption claims are claims, and they come from the project and its backers.

The fair reading: A2A has won the standards contest for agent-to-agent delegation (its main rival merged in, and the large clouds and enterprise suites all ship it), while the volume of real cross-organisation agent traffic is still unknown.

Three tools round out the kit. The A2A Inspector is a debugger for poking at an agent's card and tasks. The Technology Compatibility Kit (TCK) tests whether an implementation follows the spec. 11 · A2A and MCP

different jobs, converging features

The two protocols are designed to stack. A person or app talks to a client agent; that agent delegates across organisations with A2A; each remote agent uses MCP to reach its own tools. The layer diagram shows the arrangement, including where payment extensions ride.

That's the clean picture. The messier truth is that the two protocols have grown similar features, because both had to handle long-running, interactive work. The table maps the concepts side by side, using MCP's 2026-07-28 revision.

ConcernA2A v1.0MCP 2026-07-28
DiscoveryAgent Card at a well-known URL; skills described in proseserver/discover and tools/list; tools described with input schemas
Unit of workA task with a lifecycle; finished tasks never restartA tool call; long jobs use the Tasks extension
Asking for moreINPUT_REQUIRED and AUTH_REQUIRED task statesAn input_required result, then a retry with answers
Following progressServer-Sent Events, resubscription, push webhooksProgress on the response stream; polling with tasks/get; subscriptions/listen
What the caller seesOnly the card and the outputs; internals stay opaqueEvery tool's name, description and schema
TransportsJSON-RPC, gRPC or HTTP+JSON, all over HTTPSstdio locally, Streamable HTTP remotely
GovernanceAgentic AI Foundation, since August 2026Agentic AI Foundation, since December 2025

So when should you choose which? In the author's view, the deciding question is control, not features. MCP assumes the caller is in charge: it sees every tool and decides each call. A2A assumes a peer: you state a goal, and the other agent decides how to meet it. If you want to drive the work, expose tools. If you want to hand off the work and get a result, delegate a task. The A2A project draws a similar line when it says A2A is about agents partnering on tasks while MCP is about agents using capabilities.

12 · Payments and commerce

the layer MCP doesn't have

Once agents can delegate across companies, the next question is whether one agent can spend money on a person's behalf at another. Google's answer is the Agent Payments Protocol (AP2), launched on 16 September 2025 and usable as an extension of A2A or MCP. Its core idea is the mandate: a cryptographically signed, tamper-evident record of what the person actually authorised. An intent mandate captures the request ("buy these tickets if the price drops below this"), and a cart mandate captures the final purchase. The chain of mandates links intent to payment, so a merchant or bank can check the agent had permission.

Two related pieces sit around it. The A2A x402 extension, built with Coinbase, the Ethereum Foundation, MetaMask and others, carries crypto payments over the same mechanism. And according to the Linux Foundation's April 2026 update, AP2 had more than 60 supporting organisations in payments and financial services, and Google's Universal Commerce Protocol is compatible with it through a mandates extension.

Mandates prove what the person signed. They don't prove the agent understood the person correctly. A January 2026 red-team study of AP2 showed prompt injection steering which products an agent ranked and chose. Signed consent is only as good as the reasoning that led up to it.

13 · Designing a good A2A agent

what the spec leaves to you

The specification defines the envelope. These six practices come from the project's own guides plus the author's judgment, and they decide whether other agents can use yours well.

Write skills for a reader that's a model. A client agent picks your agent by reading the skills on your card. Give each skill a concrete description, real example prompts, and accurate input and output media types. Vague skills get the wrong work, or none.

Decide between messages and tasks deliberately. Use messages for quick answers and to agree scope; create a task once there's committed work to track. The lifecycle guide describes message-only, task-only and hybrid agents; pick one and be consistent, because clients build their logic around it.

Use the interrupted states instead of guessing. When a request is ambiguous, return INPUT_REQUIRED with a precise question. When you need consent or credentials, return AUTH_REQUIRED. A wrong guess executed confidently costs more than one round trip.

Keep artifacts traceable. Reuse an artifact's name across refinements and give each version a new id, as the lifecycle guide recommends. Since finished tasks never restart, every artifact maps to exactly one task.

Make long work resumable. Support streaming and SubscribeToTask so dropped connections don't lose work, and offer push notifications for anything that runs longer than a client can sensibly stay connected.

Keep the card honest and cacheable. Serve it with caching headers, sign it, put anything sensitive in the extended card, and update it when skills change. A card that promises more than the agent does turns into failed tasks on someone else's side.

14 · Security in practice

trusting a stranger's agent

MCP's main risk is a tool description written by someone else. A2A raises the stakes, because the other side is a full agent with its own goals, run by someone you may never have met. Research so far points at three entry points, shown below with the defences a client can apply.

Card poisoning is the A2A version of tool poisoning. A client agent typically puts the cards of candidate agents into its model's context to choose one. A March 2026 demonstration by Keysight (vendor) hid instructions in a card's text and got a host agent to send a user's booking details, including payment card data, to an attacker's endpoint. A valid signature doesn't help here: it proves who wrote the card, not that the text is safe.

The protocol itself has gaps. A September 2026 study, A2ABreak, reported eleven protocol-level vulnerabilities exploitable by agents that follow the specification exactly, with no implementation bugs required. An earlier threat-modelling paper catalogued spoofing, task replay, privilege escalation and prompt injection in A2A deployments. Research has run ahead of incidents: this review found no publicly reported real-world A2A breach, which may reflect limited cross-company deployment as much as safety.

Defences sit mostly with the client. Allow-list the agents you delegate to instead of discovering strangers at runtime; verify card signatures and pin the card you approved; keep cards and remote outputs out of the instruction part of your model's context; give each delegation the narrowest credentials that work; and require a person's confirmation before any task that spends money or shares personal data. On the server side, follow the push-notification rules in 4.5, and remember that a client can be hostile too.

15 · Operations

discovery, gateways, tenants and tracing

Discovery at company scale needs a registry. Well-known URLs work for public agents, and direct configuration works for a handful of partners. Beyond that, companies put cards in a registry that can return different cards to different callers. The specification doesn't yet standardise a registry API, so today each registry is product-specific; the Linux Foundation's April 2026 update lists consolidating registry efforts as a roadmap goal.

Treat agent endpoints like any partner API. The same gateway jobs that apply to MCP apply here: central authentication, per-identity allow-lists of which agents may call which, rate limits, and one audit log. A2A's use of plain HTTPS, standard OAuth and, for the HTTP binding, resource paths makes this ordinary gateway work.

Use tenants for hosting many agents. The v1.0 tenant field lets a platform host many customers' agents behind one endpoint, with each card naming its default tenant. Every request must still be checked against the caller's own access; the specification requires servers to return only tasks visible to the caller.

Trace across agents. A delegated task may pass through several agents, each calling its own tools. Carry a trace identifier through every hop and log task ids alongside it, so one request can be followed end to end. The contextId groups work inside one agent pair; it isn't a cross-agent trace on its own.

A Python agent. The official Python SDK separates the card from an agent executor that does the work. This executor is adapted from the quickstart tutorial; imports and the server wiring are in the tutorial's helloworld sample.

class QuoteExecutor(AgentExecutor):
    async def execute(self, context: RequestContext,
                      event_queue: EventQueue) -> None:
        # 1. Reuse the task, or create one for a new request
        task = context.current_task
        if task is None:
            task = new_task_from_user_message(context.message)
            await event_queue.enqueue_event(task)

        updater = TaskUpdater(event_queue=event_queue,
                              task_id=task.id,
                              context_id=task.context_id)
        await updater.update_status(
            state=TaskState.TASK_STATE_WORKING,
            message=new_text_message("Pricing the shipment..."))

        # 2. Do the work: your model, your MCP tools
        quote = await price_shipment(get_message_text(context.message))

        # 3. Return the result as an artifact, then finish
        await updater.add_artifact(
            parts=[new_text_part(text=quote, media_type="text/plain")])
        await updater.update_status(
            state=TaskState.TASK_STATE_COMPLETED,
            message=new_text_message("Quote ready."))

    async def cancel(self, context, event_queue) -> None:
        ...

The pattern is the same in every SDK. The executor reads the incoming message, reports state changes through an event queue, and attaches artifacts; the SDK turns those events into the right messages for whichever binding the client used. To ask a question instead of guessing, the executor would set TASK_STATE_INPUT_REQUIRED with the question as its message and return.

A raw call with curl. Fetching a card and sending a message over the HTTP+JSON binding needs no SDK:

# 1. Fetch the Agent Card
curl -s https://agents.supplier.example/.well-known/agent-card.json

# 2. Send a message and wait for the task to settle
curl -s -X POST https://agents.supplier.example/a2a/rest/message:send \
  -H "Content-Type: application/a2a+json" \
  -H "A2A-Version: 1.0" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
  "message": {
    "messageId": "msg-9",
    "role": "ROLE_USER",
    "parts": [
      {
        "text": "Quote 12 pallets from Chennai to Delhi in 10 days.",
        "mediaType": "text/plain"
      }
    ]
  }
}'

17 · What's next

the September 2026 roadmap, and open questions

The project's roadmap, last updated on 15 September 2026, lists four near-term efforts.

EffortWhat's plannedWhy it matters to you
v1.1Tighter task timelines, standard event filtering, rules for messages that arrive while an agent is workingFewer ambiguous behaviours between implementations
Bidirectional streamingTwo-way streams for live artifact updates and continuous conversation during a taskAgents could collaborate in real time instead of turn by turn
A2A CLIA command-line client meant to bring A2A into coding toolsDevelopers can test and script agents without writing a client
Elicitation and multi-turn workStructured human-in-the-loop interactions and multi-round negotiation patternsA standard way to ask people questions, beyond free-text input requests

Further out, the roadmap mentions governance through extensions, validation with the Inspector and TCK, SDKs in all six languages, and collecting community best practices. Four questions remain open.

Will real cross-company traffic materialise? The standard is settled; usage evidence isn't (section 9). The first published, quantified deployment between two unrelated companies will say more than another list of backers.

Will a registry standard emerge? Without one, discovery beyond known partners stays product-specific, and so does trust.

How will A2A and MCP divide the work? Both now handle long-running, interactive tasks. Sharing a foundation may push them to align concepts, or to keep their lines sharp; the roadmap doesn't say.

Can trust keep up? Signed cards establish who an agent is. The research in section 14 shows that knowing who wrote something isn't the same as knowing it's safe to act on.

18 · Checklists

the page, condensed into things to do

If you're building an A2A agent

  1. Describe each skill concretely, with real examples and accurate media types (section 13).
  2. Choose a message, task or hybrid style and stick to it.
  3. Ask with INPUT_REQUIRED or AUTH_REQUIRED rather than guessing.
  4. Support streaming, resubscription and push for anything long-running.
  5. Sign your card, cache it, and keep sensitive detail in the extended card.
  6. Validate every webhook URL a client gives you before calling it (4.5).
  7. Return only tasks the caller may see, and check tenants on every request.
  8. Test with the Inspector and the TCK before publishing.

If you're delegating to A2A agents

  1. First ask whether you need A2A at all (section 2).
  2. Allow-list the agents you call; verify and pin their cards.
  3. Keep cards and remote outputs out of your model's instructions (section 14).
  4. Give each delegation the narrowest credentials that work.
  5. Require a person's approval before tasks that spend money or share personal data.
  6. Handle every terminal state, including REJECTED, and never assume a task restarts.
  7. Send the A2A-Version header and pick interfaces by version (section 7).
  8. Trace each delegation end to end across agents.
