The Model Context Protocol, end to end

spec, transports, evolution, adoption, SDKs, security, operations and examples, as of the 2026-07-28 revision

MCP is the standard way for an AI application to reach tools and data it doesn't own. By the end of this page you'll know when to use it and when not to, which parts the protocol defines, what travels over the wire for a single tool call, why the July 2026 revision dropped sessions, who has adopted it, what each host actually supports, how to design, ship and secure a server, and where the protocol is heading next.

A note on bias: the author's company builds data products that agents reach through MCP servers. This page names none of those products and argues for no vendor, including his own.
Who this is for: engineers who are new to building agents and want the protocol from first principles. Builders should read sections 3 to 6, then 12 to 15. Readers weighing MCP as a platform bet can start with sections 2, 9, 16 and 18. Unfamiliar terms are defined in the glossary, and section 19 condenses the page into checklists. It assumes you know what JSON and HTTP are. It isn't a substitute for the specification, which is linked throughout.

1 · Why MCP exists

one shared interface instead of a connector per pair

Before MCP, every AI application that wanted to read a GitHub issue or query a Postgres table needed its own connector for that system. Three apps and three systems meant nine integrations, each written, secured and maintained by someone. The Model Context Protocol, or MCP, replaces those pairs with one shared interface. A system exposes its tools and data once, as an MCP server. Any application that speaks MCP can then use them.

Anthropic introduced MCP in November 2024. A year later it donated the protocol to the Linux Foundation, so no single vendor now owns it (section 9). The first diagram shows the arithmetic that made it spread.

The gap widens as the market grows. Ten apps and fifty systems would need five hundred custom integrations, or sixty MCP connections. The same arithmetic made the Language Server Protocol stick for code editors, and it's why vendors that compete on models still agree on this one interface.

What MCP doesn't do. It doesn't decide which context a model needs, choose which tool to call, or make a badly designed tool good. The model still sees tool names and descriptions as text, and the host application still runs the agent loop. MCP standardises the connection. Everything about judgment stays with you.

2 · When you don't need it

the protocol has a cost, so check you need it

MCP puts a process boundary, a wire protocol and often a login between your agent and its tools. That's worth it when several applications share the tools, or when someone else owns them. For a single agent calling its own Python functions, it's overhead. A plain function-calling loop, like the one in any model provider's tool-use guide, is simpler to build, faster to run and easier to debug. The decision flow below is the author's rule of thumb, not something the specification prescribes.

Two middle paths are worth knowing. First, you can start with plain functions and wrap them later: the SDKs turn a typed, documented function into an MCP tool with one decorator (section 15), so the switch is cheap if the tools are already well designed. Second, using other people's MCP servers doesn't require writing any yourself. Most agent frameworks can act as MCP clients (section 11), and if the servers are already on the internet, the model provider can be the client for you (3.1).

Two things MCP is the wrong tool for. It isn't a bulk data channel: tool results go into the model's context window, so moving a million rows through a tool call wastes money and gets truncated. Start an export job and return a handle instead. And it isn't the standard for agents talking to other agents; that's a different protocol, covered in section 17.

3 · The moving parts

hosts, clients and servers

The specification names three roles. The host is the AI application a person uses: Claude Desktop, Cursor, ChatGPT, or an agent you wrote. Inside the host sit one or more clients, each holding a connection to exactly one server. A server is a program that exposes capabilities: tools to call, data to read, prompt templates to fill in. A server can run on your machine as a child process, or on the internet as a web service. The component diagram below reads left to right, from the person's app to the systems a server wraps.

Two things follow from that picture. First, the model only ever asks for a tool. The host decides whether to run it, can ask the person first, and sends the request through the right client. That gap between request and execution is where every safety check lives. Second, the trust boundary is real. A server's tool descriptions land in your model's context, so installing a server means letting its author write part of your prompt (section 16).

The protocol itself has two layers. The data layer defines the messages: which methods exist and what their parameters and results look like (section 4). The transport layer defines how those messages move between processes or across a network (section 6). You can swap transports without touching the messages.

3.1 When the model provider is the client

Everything so far assumes the MCP client runs inside your host. There's a second arrangement. Anthropic's Messages API and OpenAI's Responses API can each act as the MCP client themselves. You put a server's URL in the API request; the provider's infrastructure fetches the tool list, lets the model call tools, runs each call against your server, and sends back the final answer with a record of every call. Your code never opens an MCP connection.

Compare this with the component diagram. The agent loop and the MCP client have moved out of your host and into the provider. That removes a lot of code, and it also moves the trust boundary: the provider now holds your server's access token and sees every tool result.

The two providers expose it differently. Anthropic calls it the MCP connector, still in beta; OpenAI calls it the remote MCP tool.

Here's the SQL server from section 15 called through each API, limited to two read-only tools. The requests differ in shape but do the same thing.

# Anthropic: the provider runs the MCP client
import anthropic

client = anthropic.Anthropic()

response = client.beta.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    betas=["mcp-client-2025-11-20"],
    mcp_servers=[
        {
            "type": "url",
            "url": "https://mcp.example.com/mcp",
            "name": "shop-sql",
            "authorization_token": TOKEN,
        }
    ],
    tools=[
        {
            "type": "mcp_toolset",
            "mcp_server_name": "shop-sql",
            "default_config": {"enabled": False},
            "configs": {
                "list_tables": {"enabled": True},
                "run_sql": {"enabled": True},
            },
        }
    ],
    messages=[
        {"role": "user",
         "content": "Which country led revenue in October?"}
    ],
)
# OpenAI: the same server through the Responses API
from openai import OpenAI

client = OpenAI()

response = client.responses.create(
    model=MODEL,  # any current model
    tools=[
        {
            "type": "mcp",
            "server_label": "shop-sql",
            "server_url": "https://mcp.example.com/mcp",
            "authorization": TOKEN,
            "allowed_tools": ["list_tables", "run_sql"],
            "require_approval": "never",
        }
    ],
    input="Which country led revenue in October?",
)

print(response.output_text)

When it fits. Provider-side clients suit server-side agents that call public servers, such as a SaaS vendor's MCP endpoint, and prototypes where writing a client loop is overhead. Pinning a tool list (Anthropic) and per-call approval (OpenAI) also close two of the gaps in section 16.

When it doesn't. A server holding private data usually lives behind a firewall, and Anthropic's connector can't reach it. You also lose resources, prompts and elicitation, and you hand an access token to a third party. OpenAI says it doesn't store the token, so you send it with every request; Anthropic's docs note its connector isn't covered by zero-data-retention agreements. For those cases, run the client yourself, as in the rest of this page. Anthropic's SDK includes helpers for that, and OpenAI's Agents SDK can act as a client itself.

4 · What the specification defines

five layers, read from the bottom up

The specification is a dated document. The current revision is 2026-07-28, and each revision has its own changelog. It covers a required base protocol, server and client features, a set of utilities, an authorization profile for HTTP, and a framework for optional extensions. The stack below maps them; the amber boxes are deprecated but still working.

Read the stack as a contract that grows upward. A minimal server needs JSON-RPC, one transport and one feature, usually tools. Authorization matters only once the server is on a network. Extensions are opt-in on both sides, so a host that ignores them sees an ordinary server.

4.1 Base protocol

Every MCP message is a JSON-RPC 2.0 message: a request with an id and a method, a result or error that echoes the id, or a one-way notification. The 2026-07-28 revision changed what goes around those messages. There is no longer an opening handshake. Instead, every request carries its protocol version and the client's capabilities in a _meta field, and clients should identify themselves on each request.

Three other base changes are worth knowing. Servers must implement server/discover, which returns their supported versions, capabilities and identity; clients may call it first but don't have to. Every result now carries a resultType: complete for a normal answer, or input_required when the server needs something before it can finish (section 5). And the error codes from -32020 to -32099 are now reserved for the specification, so a version mismatch, for example, has one standard code everywhere.

4.2 Server features

Servers offer three kinds of thing. They differ mainly in who decides when they're used, which the table makes clear.

FeatureWho decidesMethodsExample in a SQL server
ToolsThe model, during a tasktools/list, tools/callrun_sql, describe_tables
ResourcesThe host applicationresources/list, resources/readA data dictionary at a URI like docs://schema
PromptsThe person, often as a slash commandprompts/list, prompts/getA template: monthly revenue review for a region

Tools carry the most weight in practice. A tool declares a name, a description and a JSON Schema for its inputs. Since the 2025-06-18 revision it can also declare an output schema and return typed results in structuredContent, or return links to resources instead of inlining large payloads. The 2025-03-26 revision added tool annotations such as read-only or destructive. Treat those as labels for the user interface, not as security controls: a malicious server can label anything read-only.

List results got cheaper to fetch in 2026. Responses to tools/list and the other list methods now carry a freshness hint (ttlMs) and a cache scope, and servers should return tools in a fixed order. The fixed order matters more than it looks. A stable tool list keeps the model provider's prompt cache warm, which cuts cost on every turn of an agent loop.

Resources deserve more than a table row. Each one has a URI, and a server can publish resource templates: URIs with parameters, such as warehouse://tables/{name}/schema, listed through resources/templates/list, so a host can fetch the schema of any table without the server listing thousands of them. Clients can also subscribe to changes in a resource; since July 2026 that happens on the single subscriptions/listen stream (section 6). Prompts take named arguments, and argument completion lets a host offer autocomplete as the person fills them in. Support for resources and prompts varies a lot between hosts, which section 10 covers.

4.3 Tool results and errors

A tool result is a list of content items, plus optional typed data. The content types are text, images and audio (base64 with a MIME type), resource links that point to data the client can fetch later, and embedded resources that carry the data inline. A tool with an output schema also returns structuredContent, and the specification asks it to repeat that JSON as text for clients that only read text. The maintainers admit the two-channel design confuses people, and redesigning it is on the roadmap.

Errors come in two kinds, and the difference matters more than anything else in this subsection. A protocol error is a JSON-RPC error: unknown tool, malformed request. A tool execution error is a normal result marked isError: true: bad SQL, an empty search, an upstream API that timed out. The 2025-11-25 tools page says clients should pass execution errors to the model so it can correct itself and try again.

// Protocol error: the host handles it
{
  "jsonrpc": "2.0",
  "id": 3,
  "error": {
    "code": -32602,
    "message": "Unknown tool: run_sqll"
  }
}

// Tool execution error: the model reads it and retries
{
  "jsonrpc": "2.0",
  "id": 4,
  "result": {
    "resultType": "complete",
    "content": [
      {
        "type": "text",
        "text": "No column 'revenue' in orders. Columns: id, customer_id, amount, created_at. Revenue is usually SUM(amount)."
      }
    ],
    "isError": true
  }
}

The second error is written for a model, not a log file. It names the problem, lists the valid options and suggests the fix. A server that raises exceptions for bad input instead turns every model mistake into a dead end. Section 12 has more on writing errors that teach.

4.4 Client features

Clients can offer things back to servers. The one that survives into the current revision is elicitation: a server asking the person for input mid-task, such as a confirmation or a missing parameter. It arrived in 2025-06-18, and the 2025-11-25 revision added a URL mode, where the server sends the person to a browser page for anything sensitive, like a login or a payment, so the client never sees the credentials.

Two older client features are on their way out. Roots told a server which folders it could work in. Sampling let a server borrow the host's model to generate text. Both were deprecated in July 2026. The suggested replacements are plain: pass folders as tool parameters or configuration, and have servers call a model provider's API directly if they need one.

4.5 Utilities

A small set of helpers sits beside the features: progress notifications for slow calls, cancellation, argument completion (autocomplete for prompt and resource arguments), and pagination for long lists. Progress and log messages travel on the response stream of the request they belong to. The old logging feature, where a client set a server's log level for the whole session, is deprecated; the level is now set per request, and the advice is to log to stderr or use OpenTelemetry.

4.6 Authorization

Authorization applies to HTTP servers only. The specification tells stdio servers not to use it and to take credentials from their environment instead. For remote servers, MCP builds on OAuth, the standard behind most single sign-on buttons, and the profile has tightened with each revision:

RevisionWhat changedWhy it mattered
2025-03-26First authorization framework, based on OAuth 2.1Remote servers could finally require a login
2025-06-18Servers became OAuth resource servers that point to a separate authorization server; tokens are bound to one serverFits existing company identity systems; a token stolen from one server can't be replayed at another
2025-11-25Client ID Metadata Documents: a client identifies itself by a URL it controlsNo need to pre-register every client with every server
2026-07-28Issuer validation required; credentials bound to the issuer; Dynamic Client Registration deprecatedCloses an attack where one authorization server is swapped for another

The maintainers say authorization is where implementers spend most of their integration time, and the table shows why. Each revision fixed a real gap that early remote servers hit in production.

4.7 Extensions

Extensions are optional features with their own names and their own version histories, negotiated through an extensions field in each side's capabilities. Three matter today. Tasks (io.modelcontextprotocol/tasks) turns a slow call into start now, check later: the server returns a handle, and the client polls with tasks/get. AWS contributed it, and it moved out of the core protocol in July 2026. MCP Apps (io.modelcontextprotocol/ui) lets a tool ship an interactive HTML interface that the host renders in a sandboxed frame. Enterprise-managed authorization lets a company's identity provider decide centrally which servers each employee can reach.

The framework is the part to remember. Before it, new ideas either went into the core, where everyone had to support them, or lived as incompatible forks. Now they can mature outside the core and only move in once they've proven themselves.

5 · One request, end to end

what actually travels, in order

The sequence below follows one task through a host on the 2026-07-28 revision. The model wants to delete rows, and the server wants the person's confirmation first. Read it top to bottom; the shaded bands mark the two phases.

Walk through it in three parts. In discovery, the host may ask the server what it supports, then fetches the tool list, which it can cache for as long as ttlMs allows. In the middle, the host hands those tool definitions to the model as text, and the model replies with a request to use one. The model has no idea MCP exists; it only sees tools.

The bottom band is the newest part of the protocol, called Multi Round-Trip Requests, or MRTR. In older revisions, a server that needed the person's confirmation sent its own request back to the client over a held-open connection. Now the server returns an interim result marked input_required, listing what it needs. The host asks the person, then sends the original call again with the answers in inputResponses. Each step is an ordinary request and response, which is what makes the stateless design in section 6 possible.

Here is what the tool call looks like on the wire over HTTP. The method and tool name appear twice, once in headers and once in the body, so a gateway can route or rate-limit without parsing JSON. The client also declares in _meta that it can handle elicitation; without that declaration, the server isn't allowed to ask the person anything.

POST /mcp HTTP/1.1
Content-Type: application/json
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: delete_rows

{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "delete_rows",
    "arguments": {
      "table": "staging_orders",
      "where": "load_date < '2026-01-01'"
    },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {
        "elicitation": {}
      },
      "io.modelcontextprotocol/clientInfo": {
        "name": "sql-agent",
        "version": "0.3"
      }
    }
  }
}

And the interim answer, abridged from the shapes in the MRTR pattern page. The keys in inputRequests are names the server chooses; each value is an ordinary request, here a form-style elicitation.

{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "resultType": "input_required",
    "inputRequests": {
      "confirm": {
        "method": "elicitation/create",
        "params": {
          "message": "Delete 1,240 rows from staging_orders?",
          "requestedSchema": {
            "type": "object",
            "properties": {
              "ok": {
                "type": "boolean"
              }
            },
            "required": [
              "ok"
            ]
          }
        }
      }
    },
    "requestState": "opaque-token-from-server"
  }
}

The host asks the person, then sends the original call again as a new request with a new id. It adds the answers under matching keys and echoes requestState untouched; the specification says clients must not inspect or change it.

{
  "jsonrpc": "2.0",
  "id": 8,
  "method": "tools/call",
  "params": {
    "name": "delete_rows",
    "arguments": {
      "table": "staging_orders",
      "where": "load_date < '2026-01-01'"
    },
    "inputResponses": {
      "confirm": {
        "action": "accept",
        "content": {
          "ok": true
        }
      }
    },
    "requestState": "opaque-token-from-server",
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {
        "elicitation": {}
      },
      "io.modelcontextprotocol/clientInfo": {
        "name": "sql-agent",
        "version": "0.3"
      }
    }
  }
}

State without sessions. Dropping protocol sessions doesn't make your application stateless. If a server needs to remember something across calls, such as an open export job, the maintainers' advice is to mint an explicit handle from a tool and have the model pass it back as an argument. The model can see the handle, which turns out to work better than state hidden in the connection.

6 · Transports

stdio for local, Streamable HTTP for remote

A transport is how the JSON-RPC messages move. There are two standard ones, plus a legacy third that's being retired.

TransportHow it worksUse it forStatus
stdioThe host starts the server as a child process and exchanges newline-delimited JSON over its standard input and output. Logs go to stderr.Local tools: files, git, a local database, anything on your machineActive
Streamable HTTPOne HTTP endpoint. Each request is a POST; the response is plain JSON or a stream of server-sent events when the server sends progress first.Remote servers shared by many users, behind normal web infrastructureActive, the default for remote
HTTP+SSEThe 2024 design: a separate long-lived event stream plus a POST endpointNothing newDeprecated since 2025-03-26

The big transport story of 2026 is statelessness. Until 2025-11-25, an HTTP client opened a session with an initialize handshake and got back an Mcp-Session-Id. Every later request had to reach the server instance that remembered that session, or every instance had to share a session store. The diagram compares the two designs.

The 2026-07-28 changelog lists what went to make that possible: the handshake, the session header, the separate GET stream for server messages, the ping method, and stream resumability. A broken response stream now loses the request in flight, and the client simply sends it again with a new id. Change notifications, such as a server announcing that its tool list changed, now flow over one opt-in subscriptions/listen stream.

The trade is clear. Servers lose the ability to push requests to clients at will, and anyone who stored state in sessions has migration work. In return, MCP servers run on standard serverless and load-balanced infrastructure with no shared storage, which is what cloud providers had been working around.

7 · Old and new versions together

how a client talks to a server it hasn't met

The July 2026 revision split MCP into two eras. The versioning page calls revisions up to 2025-11-25 legacy (they open with an initialize handshake) and 2026-07-28 onward modern (every request carries its own version). An implementation that speaks both is dual-era. For the next year or more, most production clients will be dual-era, because servers upgrade on their own schedules. The flow shows how such a client finds out which kind of server it's talking to.

The mechanics differ slightly by transport. On stdio the client probes with server/discover and falls back on any error that isn't a recognised modern one. On HTTP it sends a normal modern request and inspects the body of a 400 Bad Request before falling back, possibly all the way to the deprecated HTTP+SSE transport. The reverse direction is harder: a legacy client has no way to move forward, so a modern-only server simply can't serve it. That's why the guidance is for servers to stay dual-era for now.

The SDKs make this a setting rather than code. The TypeScript SDK's version negotiation offers three modes: legacy only, auto (probe, then fall back), or pinned to one revision with no fallback. The same docs warn against auto mode for command-line tools that start a fresh process per call, because every invocation pays for the probe.

8 · How it evolved

five revisions in twenty months

MCP versions are dates, not numbers. The timeline puts the five revisions above the line and the ecosystem events that shaped them below.

The details sit in the changelogs. The table summarises the headline of each.

RevisionHeadline changesProblem it answered
2024-11-05Tools, resources, prompts, sampling; stdio and HTTP+SSE transports; an initialize handshakeConnecting a desktop app to local tools
2025-03-26OAuth 2.1 authorization, Streamable HTTP, JSON-RPC batching, tool annotations, audio contentRemote servers that need logins and simpler hosting
2025-06-18Structured tool output, servers as OAuth resource servers, elicitation, resource links; batching removed againTyped results, company identity systems, asking the user mid-task
2025-11-25Experimental tasks, URL-mode elicitation, client metadata documents, the extensions frameworkLong-running jobs and safe out-of-band logins
2026-07-28No handshake or sessions, MRTR, header routing, cacheable lists, tasks as an extension, deprecationsRunning servers at web scale

The process has matured alongside the protocol. Proposed changes go through Specification Enhancement Proposals (SEPs), now managed as pull requests. The July 2026 revision also adopted a formal deprecation policy: features move from active to deprecated to removed, with at least twelve months' notice. Roots, Sampling and Logging can't be removed before the first revision released on or after 28 July 2027.

9 · Adoption

from one vendor's protocol to shared infrastructure

The turning point was a competitor. On 26 March 2025, OpenAI's chief executive Sam Altman said the company would add MCP support across its products, starting with the Agents SDK and followed by the ChatGPT desktop app and the Responses API, as SiliconANGLE reported. Once the two largest model vendors both spoke it, building a rival connector standard made little sense. The two companies later co-authored the MCP Apps extension.

Then it left Anthropic. On 9 December 2025, Anthropic donated MCP to the Agentic AI Foundation, a fund under the Linux Foundation co-founded by Anthropic, Block and OpenAI, with support from Google, Microsoft, AWS, Cloudflare and Bloomberg. Block's goose and OpenAI's AGENTS.md joined as founding projects, and the MCP project's own post says its governance model stayed the same. Anthropic added its Agent Skills standard to the same foundation in October 2026.

The numbers are large, and self-reported. At the donation, Anthropic counted more than 10,000 active public servers, support in ChatGPT, Cursor, Gemini, Microsoft Copilot and VS Code, and 97 million monthly SDK downloads across Python and TypeScript. By July 2026 the maintainers reported close to half a billion downloads a month across the Tier 1 SDKs, with the TypeScript and Python SDKs each past one billion in total. Both figures come from the project and its founding sponsor, and download counts include automated builds, so read them as direction rather than precise usage.

The clouds built it in. The July 2026 release post carries statements from AWS (stateless servers in Bedrock AgentCore, and Tasks, which AWS contributed), Cloudflare (day-zero support in its Agents SDK), Microsoft (MCP as the base of Foundry's tool catalogue) and Google Cloud. Google documents its own remote MCP servers as compliant with the authorization spec. Usage signals are thinner but telling: in the same post, Honeycomb says close to a fifth of its monthly interactive queries now come from agents.

The interface went visual. MCP Apps became the first official extension on 26 January 2026, built from the community MCP-UI project and OpenAI's Apps SDK. A tool can now return a dashboard or a form instead of text, rendered in Claude, goose and other hosts that support it.

Data platforms followed. Snowflake, Databricks and Google Cloud now run managed MCP servers over their own data, which section 14 compares.

10 · What hosts actually support

the spec is a menu; each host orders differently

A server can offer every feature in section 4, but a feature only works if the host the person uses supports it. Support is uneven, and it differs between products from the same company. 12 · Designing a good server

the protocol carries the call; the design decides whether it works

In the author's experience, most MCP servers that disappoint are correct protocol implementations with poor tools. Anthropic's guide to writing tools for agents makes the core point: design tools for a model that reads descriptions literally and pays for every token, not for a developer browsing API docs. Six rules cover most of it.

Start from tasks, not endpoints. Wrapping every REST endpoint as a tool gives the model dozens of small steps to chain, each a chance to go wrong. A tool shaped like the task (describe_tables returning columns, types and sample values together) beats four tools the model has to combine.

Name tools so they don't collide. The specification asks for names without spaces or special characters, unique within a server. Across servers there's no such guarantee, and a host connected to five servers may see two tools called search. Snowflake's documentation warns about tool shadowing, where one server's tool hides or impersonates another's. Prefixing names with the service (warehouse_run_sql) avoids both problems.

Write errors that teach. Return execution failures as results with isError: true and text that names the problem and the fix (4.3). The model reads it on the next turn and corrects itself.

Return less. Cap rows, paginate, and say when you truncated, or the model will treat a sample as the whole. For large outputs, return a resource link or a job handle instead of the data.

Keep stdout clean. Over stdio, standard output is the protocol channel. One stray print() corrupts the message stream and the host disconnects with a confusing error. Log to stderr.

Label honestly, enforce elsewhere. Set annotations such as read-only and destructive accurately, since hosts use them to decide when to ask the person. But the specification tells clients to treat annotations as untrusted unless the server is trusted, so real limits belong in the server: read-only database roles, row caps, timeouts.

Testing has three layers. The MCP Inspector is the project's interactive debugger; the Python SDK's mcp dev server.py launches it against your server the way a real host would. The conformance suite checks protocol behaviour. And task evaluations, real requests run by a real model against your tools with the transcripts read by a person, are the only way to learn whether the model actually uses the tools well. The Anthropic guide recommends exactly this loop, including using a model to read the transcripts and suggest improvements to the tools.

13 · Packaging, hosting and gateways

getting a server to people, and keeping control of it

Local servers are packages. The simplest distribution is a command the host runs, such as uvx my-server for Python or npx my-server for Node, written into the host's configuration. That still needs a working runtime on the person's machine. MCP Bundles (.mcpb) solve that: a zip archive holding the server, its dependencies and a manifest.json. Anthropic built the format for Claude's desktop app as Desktop Extensions, then moved it into the MCP project in November 2025 so any host can support it. Anthropic's launch post lists the enterprise controls: pre-installed approved bundles, blocklists, and secrets kept in the operating system's keychain.

Remote servers are web services. Since the stateless revision, a remote server runs anywhere an ordinary HTTP service runs: containers, serverless functions, edge platforms. In Python it's one argument, mcp.run(transport="streamable-http", port=8000), with options for plain JSON responses and per-request stateless handling, according to the Python SDK docs. The cloud providers that commented on the July release (section 9) all host MCP servers natively.

Publish where hosts look. The community-run MCP Registry is where clients and directories discover public servers. Listing is discovery, not a security review.

Gateways put one control point in front of many servers. Once a company runs dozens of servers for hundreds of agents, credentials, permissions and audit logs scatter across config files. An MCP gateway is a proxy that understands MCP methods. Gateway vendors, including Zuplo and TrueFoundry, describe the same core jobs, shown below. The protocol's July 2026 headers, which put the method and tool name outside the JSON body, exist partly so gateways can do this cheaply.

Filtering tools per identity does double duty. It's a security control, and it's a context-cost control, because every tool an agent can see is a definition resent on every turn (section 17). Several gateways offer virtual servers: a curated subset of one upstream server's tools, behind its own URL and its own access rules.

14 · MCP for data access

what the warehouse and lakehouse vendors shipped, and the questions it raises

Data platforms adopted MCP fast, because analytics is where agents most need governed access to company data. The three largest cloud data platforms now run managed MCP servers themselves, so there's no server to deploy.

PlatformWhat the managed server exposesHow access is controlled
SnowflakeCortex Analyst (questions over semantic views) and Cortex Search as tools; generally available since November 2025OAuth sign-in; role-based access decides which tools each role can discover and call
DatabricksGenie spaces, AI Search indexes, Databricks SQL and Unity Catalog functions, each at its own URL (docs; preview and beta labels vary by server)Unity Catalog permissions enforced on every call; per-server OAuth scopes for acting on behalf of a user
Google CloudA managed remote BigQuery server (preview from January 2026) plus servers for Cloud SQL and other databases; an open-source toolbox for self-hostingGoogle says its managed database servers log every query and action in Cloud Audit Logs

Read the table for its pattern rather than its rows. Each vendor routes agents through something more than raw SQL: Snowflake through semantic views, Databricks through curated Genie spaces and registered functions, Google through Looker definitions as well as BigQuery. A data catalogue vendor's ranking of AI-ready platforms (vendor) makes the same observation: most major platforms now pair an MCP endpoint with a layer of metric definitions the agent queries through. Four design questions follow for anyone building a data server.

Semantic layer or raw SQL? Raw SQL is flexible and lets the model compute the wrong revenue in a hundred creative ways. A tool that queries named metrics returns the company's agreed number. Most teams will want both, with the metrics tool listed first.

Whose permissions apply? A server running as one service account sees everything that account sees, for every user. Acting on behalf of the signed-in user, as Databricks does with per-server OAuth scopes, keeps row and column rules intact. The Supabase incident in section 16 shows what a connection that bypasses those rules costs.

What happens with slow queries? Warehouse queries can run for minutes. Databricks' SQL server makes the agent start a query and poll for the result, the same shape as the Tasks extension (4.7). Holding a tool call open for minutes is fragile.

How much comes back? Row caps, truncation flags and aggregation hints (section 12) matter more for data servers than any other kind. Snowflake also caps nested tool invocations at a depth of ten, a reminder that agents can loop.

15 · Examples

a server, a host configuration, a raw request

A small server in Python. This exposes two read-only SQL tools using the v2 SDK. The docstring becomes the tool description and the type hints become the input schema, so writing a good docstring is writing the prompt the model will read.

from mcp.server import MCPServer
from warehouse import list_tables_impl, run_sql_impl

mcp = MCPServer("shop-sql")

@mcp.tool()
def list_tables(keyword: str = "") -> str:
    """List tables with a one-line summary each.
    Use first to find candidate tables.
    Does not return columns."""
    return list_tables_impl(keyword)

@mcp.tool()
def run_sql(query: str) -> str:
    """Run one read-only SELECT. Returns up to
    50 rows as JSON, flagged if truncated."""
    return run_sql_impl(query)

if __name__ == "__main__":
    mcp.run()   # stdio by default
    # remote: mcp.run(transport="streamable-http", port=8000)

The safety lives in run_sql_impl, not in the docstring: a read-only database role, a forced row limit and a query timeout. The protocol carries the request; it doesn't make the request safe.

Connecting it to a host. Most hosts take a short configuration. A local server is a command to launch; a remote server is a URL, plus a token or an OAuth login. Two real forms, from one public server's setup guide:

# Claude Code, remote server over HTTP (OAuth opens a browser)
claude mcp add --transport http --scope user mytools https://mcp.example.com

# Cursor or VS Code style JSON
{
  "mcpServers": {
    "mytools": {
      "type": "http",
      "url": "https://mcp.example.com",
      "headers": {
        "Authorization": "Bearer YOUR_KEY"
      }
    }
  }
}

A raw call with curl. Because every request is self-contained since July 2026, you can call a remote server with no client library at all. This is useful for debugging a gateway or a firewall rule.

curl -s https://mcp.example.com/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: 2026-07-28" \
  -H "Mcp-Method: tools/list" \
  -d '{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}'

A long-running job. For an export that takes ten minutes, a server that supports the Tasks extension answers tools/call with a task handle instead of a result. The host tells the person the job has started, polls tasks/get, and hands the final result to the model when it's ready. The model never waits on an open connection.

16 · Security in practice

what goes wrong, and where the fixes live

Tool descriptions are prompts written by someone else. A server's tool descriptions go straight into your model's context before any call is made. Tool poisoning hides instructions there, such as telling the model to read the user's SSH key before any file operation. The MCPTox benchmark built 1,312 such cases on 353 real tools from 45 real servers and found attack success rates up to 72.8%; its authors note that more capable models were often more vulnerable, because they follow instructions better. A 2026 study of seven popular MCP clients found uneven defences. Two related attacks are worth naming: a rug pull, where a server changes its descriptions after you approved it, and injection inside tool results. The diagram shows where each enters, and what a host can do about it.

None of these checks is in the protocol; they're the host's job. The practical rules for your own agents: install few servers, from sources you trust; pin their definitions; keep destructive tools behind a confirmation; and give each server the narrowest credentials that work.

16.1 Incidents so far

Benchmarks show what could go wrong; these public incidents from 2025 show what did. They cluster into three kinds of failure, and none was a flaw in the protocol's message format.

WhenWhat happenedRoot cause
May 2025Invariant Labs showed a malicious issue in a public GitHub repository steering an agent, via the official GitHub server, into copying private repository data into a public pull requestUntrusted text, a broad token and a public write channel in one session
June 2025Asana took its MCP server offline from 5 to 17 June after a bug let users see other organisations' dataA tenant-isolation bug in the server's own code
Mid-2025MCP Inspector, the debugging tool, could be made to run code through its unauthenticated local web interface (CVE-2025-49596, fixed in 0.14.1)A developer tool listening on localhost without authentication
July 2025Two flaws in Anthropic's reference filesystem server let a path or symlink escape its allowed folder (CVE-2025-53110, CVE-2025-53109)Path checks that compared prefixes and followed links
July 2025mcp-remote, a popular bridge to remote servers, executed operating-system commands hidden in a malicious server's authorization URL (CVE-2025-6514, CVSS 9.6, fixed in 0.1.16)Trusting a URL from an untrusted server
July 2025A support ticket containing instructions led a coding agent, connected to Supabase's server with a service role that bypasses row-level security, to read a private table and write its contents back into the ticketUntrusted text, a connection that bypassed row-level security, and a write path

The first and last rows share a shape that Simon Willison calls the lethal trifecta: private data, exposure to untrusted content, and a way to send data out, all in one agent session. Remove any one leg and the attack fails. Invariant itself framed the GitHub case as an agent-design problem rather than a server bug to patch, which is why the fixes live in token scopes and session design. The middle rows are ordinary software bugs in new code: tenant checks, path validation, command injection. MCP servers need the same review as any service that holds credentials.

17 · Context cost and tracing

the remaining things a builder runs into

Tool definitions cost context. Every connected server's tools are resent to the model on every turn. Anthropic reported tool definitions consuming 134,000 tokens before optimisation in its own setup. Two fixes have emerged. Tool search loads only a search tool up front and pulls in definitions on demand, which Anthropic measured at about an 85% reduction. Code execution with MCP presents servers as code libraries the model writes against, so large intermediate results stay in a sandbox instead of the context window; Cloudflare calls the same idea Code Mode. Both are vendor measurements on vendor setups.

Tracing works across servers. Since July 2026 the specification documents OpenTelemetry trace context in _meta, so one trace can follow a request from the agent through the host into each server. This is what you'll use to debug an agent that calls five servers in one task.

MCP and A2A solve different problems. MCP connects an agent to tools and data. Google's Agent2Agent protocol, also now under the Linux Foundation, lets agents hand tasks to other agents. One analysis frames them as complements rather than rivals, which matches how most teams use them.

18 · What's next

the August 2026 roadmap, and the questions it leaves open

The maintainers published an updated roadmap on 22 August 2026 for the next revision. It names five priority areas, and proposals inside them get reviewed first. The roadmap itself says these are current thinking, not commitments. No date appears on it, but the Ruby SDK team's September post says the next revision is currently scheduled for 15 December 2026.

AreaWhat's plannedWhy it matters to you
Agentic messagingServer-initiated events, including webhooks; making Tasks, subscriptions and progress compose; moving Tasks toward the coreLong jobs could notify the host when done instead of being polled
One transportStreamable HTTP spoken over stdio for local servers, possibly HTTP/2; ETag caching; standard errorsLocal and remote servers would share one code path
Agent identityProof-of-possession tokens (DPoP), workload identity, token exchange for delegationHeadless agents could authenticate as themselves, without pasted API keys
Better primitivesA redesigned tool result shape; progressive discovery of tools; a decision on content annotationsClients could load tools as needed instead of the whole catalogue
SDK experienceAn extension contract for SDKs; an experiment generating an SDK from the specification and conformance testsFewer gaps between SDKs and the spec

Four questions remain open.

How painful is the dual-era period? Servers must serve both handshake-era and stateless clients (section 7). The SDKs hide most of this, but anyone who stored state in sessions has real migration work before the old revisions fade.

Will MRTR deliver human-in-the-loop at scale? Elicitation was hard to support on stateless servers before July 2026. MRTR fixes the protocol side, but each host still has to design how it asks the person, and hosts differ (section 10).

Who owns tool security? The protocol has hardened authorization, but tool poisoning lives in plain-text descriptions the specification can't check. For now the defence sits in hosts and gateways, and research suggests most hosts are still uneven.

Will loading every tool stay the default? Tool search, code execution and the roadmap's progressive discovery all move away from sending the full tool catalogue on every turn. If they spread, the typical server may shift from many small tools toward fewer, code-friendly ones.

19 · Checklists

the page, condensed into things to do

If you're building a server

  1. Shape tools around tasks, prefix their names with your service, and write descriptions as prompts (section 12).
  2. Return execution errors as results with isError: true and a suggested fix (4.3).
  3. Cap and paginate output, flag truncation, and return handles for anything large or slow.
  4. Enforce limits in code and credentials: read-only roles, timeouts, per-user permissions. Don't rely on annotations or descriptions.
  5. Over stdio, log to stderr only. Over HTTP, stay stateless and pass state as explicit handles.
  6. Support both protocol eras until your users' hosts have moved (section 7).
  7. Put essential behaviour in tools, since resources and prompts aren't supported everywhere (section 10).
  8. Test with the Inspector, then with real tasks run by a real model, and read the transcripts.

If you're building a host or an agent

  1. Install few servers, from sources you trust, and pin their tool definitions. Re-approve when they change (section 16).
  2. Never give one session private data, untrusted content and an outbound channel at the same time.
  3. Ask the person before destructive or outbound calls, whatever the annotations say.
  4. Give each server the narrowest token that works, scoped to one repository, project or tenant.
  5. Pass execution errors to the model; handle protocol errors in code.
  6. Watch context cost: filter tools per task, or use tool search (section 17).
  7. Trace across servers with the OpenTelemetry fields in _meta.
  8. For many agents and servers, route traffic through a gateway with per-identity allow-lists and one audit log (section 13).
