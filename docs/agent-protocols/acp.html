Agent Client Protocol (ACP), end to end

v1 as it runs today, the v2 draft, adoption, the registry, SDKs, security and examples, as of November 2026

ACP is the open standard that lets any coding agent run inside any editor that supports it, the way the Language Server Protocol let any language tool run in any editor. By the end of this page you'll know when it matters, how an editor and an agent talk during one prompt, what the v2 draft changes and why, who has adopted it, where it sits next to MCP and A2A, and what its trust model does and doesn't protect.

A note on bias: the author's company builds data products that agents reach through open protocols. This page names none of those products and argues for no vendor, including his own.
Which ACP: this page covers the Agent Client Protocol, started by Zed. It is unrelated to IBM's Agent Communication Protocol, which merged into A2A in 2025, and to the commerce protocols that share the acronym.
Who this is for: engineers building coding or data agents, or tools that host them. Builders should read sections 3 to 6, then 13 to 15. Readers weighing ACP as a distribution channel can start with sections 2, 10 and 16. Terms are defined in the glossary, and section 17 condenses the page into checklists.

1Why ACP exists

editors times agents, again

Every coding agent wants to live where developers already work, and every editor wants to offer the agents developers already use. Without a standard, each pairing needs its own plugin: the Claude integration for one IDE, the Codex integration for another, maintained separately and drifting apart. Zed hit this problem directly. On 27 August 2025 it announced the Agent Client Protocol with Google's Gemini CLI as the first agent, and framed the goal in terms of the Language Server Protocol: switch agents without switching editors. The diagram shows the arithmetic.

The appeal runs both ways. Zed's launch post pitches agent builders a ready-made interface inside an IDE, so they can build the agent instead of forking VS Code. Editors get access to many agents without writing an integration for each. And because the editor renders the work, users get features that are hard to offer from a terminal: live edit visualisation, multi-file review and jumping between the agent's changes and the code.

2When you don't need it

ACP solves one placement problem

ACP is about where an agent's interface lives. If your agent runs in a terminal and your users are happy there, you don't need it. If you build for exactly one editor and plan to stay there, that editor's native extension API may give you more control. And if your agent runs unattended in CI or a cloud sandbox with no person watching, ACP's model of a person approving actions in an editor fits poorly.

It earns its place in three cases. You build an agent and want it in several editors without several plugins. You build an editor or notebook and want many agents without integrating each one. Or you build an agent product with your own clients and want a clean boundary between the interface and the agent, which is how AWS used it for Kiro (section 10).

3The moving parts

the editor hosts, the agent works, both call each other

ACP has two roles. The client is usually an editor, though notebooks and other interfaces qualify. The agent is a program that uses a model to change code, and the v1 overview says agents typically run as subprocesses of the client. Messages are JSON-RPC 2.0 over the agent's standard input and output. The component diagram shows the arrangement, which differs from MCP in one important way.

Three things set ACP apart. Calls go both ways. In MCP the client calls and the server answers. In ACP both sides expose methods: the editor calls session/prompt on the agent, and the agent calls fs/read_text_file or session/request_permission on the editor. The editor owns the environment. The overview says clients manage the environment, handle user interactions and control access to resources; in v1 that includes serving file contents, unsaved edits included, and running terminals. The agent owns the intelligence. It calls its own model provider with its own credentials, and the editor never sees the model.

The editor also hands the agent a list of MCP servers when each session starts. That's how one editor's configured tools (a database, an issue tracker) become available to whichever agent the person picks, which ties ACP closely to MCP (section 7).

4What v1 defines

the protocol editors and agents run today

Everything in this section is the stable v1 protocol. The project ships features into v1 continuously through a request-for-discussion (RFD) process; the v2 draft announcement counts more than fifteen RFDs delivered on v1 without a breaking change. Section 6 covers what v2 changes.

4.1 Initialisation and authentication

The editor opens with initialize, stating the protocol version it speaks and what it offers: whether it can read and write files, whether it can run terminals, and which elicitation modes it supports. The agent answers with its own capabilities (images and audio in prompts, which MCP transports it can use, whether sessions can be reloaded) and any authentication methods it needs. Authentication can be handled by the agent itself or by the editor launching the agent in an interactive terminal for a login.

4.2 Sessions

A session is one conversation. The editor creates it with session/new, passing the working directory as an absolute path and the MCP servers the agent should use. v1 has grown a full set of session operations: load an earlier session with its history, resume one, list, close and delete. The protocol requires absolute file paths and 1-based line numbers everywhere, which removes a whole class of off-by-one and relative-path bugs between independent implementations.

4.3 The prompt turn

The person types; the editor sends session/prompt with the message as content blocks (text, images, audio, links to files or embedded file contents). In v1 that request stays open for the whole turn. The agent streams progress as notifications, may call back into the editor, and finally answers the prompt request with a stop reason: it finished (end_turn), ran out of tokens or turns, refused, or was cancelled. The editor can stop a turn at any time with a session/cancel notification.

4.4 Session updates

The agent reports everything through session/update notifications, which the editor renders. The overview lists the kinds: chunks of the agent's message and its visible reasoning, tool calls and their updates, plans (a checklist of steps), available slash commands, mode and configuration changes, usage and cost, notices, and context compaction.

Tool calls carry the most structure. Each has an id, a title, a kind that tells the editor how to display it (read, edit, delete, move, search, execute, think, fetch and a few more), a status (pending, in_progress, completed, failed), the files it touches, and content that can include a diff or a live terminal. The tool calls page calls the file locations follow-along metadata: the editor can open files as the agent works on them.

4.5 Permission requests

Before risky work, the agent calls session/request_permission on the editor with the tool call and a set of options, each labelled with a kind: allow once, allow always, reject once, reject always. The editor asks the person and returns the chosen option, or cancelled if the turn was cancelled. Editors may also answer automatically from user settings.

One rule is easy to miss and matters a great deal. Permission in ACP is advisory. The security page says the agent performs its own operations and is responsible for honouring the person's decision. When the person picks "allow always", the agent, not the editor, stores that decision and decides its scope. A buggy or malicious agent can ignore a rejection. Section 13 follows that through.

4.6 Files and terminals

Two optional capabilities let the agent use the editor's environment. With file access, the agent asks the editor to read or write a text file; reads return the editor's view, which includes edits the person hasn't saved yet. With terminal access, the agent asks the editor to start a command, read its output, wait for it to exit, or kill it, and can embed the live terminal in a tool call so the person watches it run. These are the APIs v2 removes (section 6).

4.7 Modes, elicitation and extensibility

Agents can expose modes (for example ask versus code) and configuration options such as model choice, which the editor shows as controls. Elicitation, now stable in v1, lets an agent ask the person a structured question through a form or send them to a URL. For anything the protocol doesn't cover, both sides can attach custom data in _meta fields, call custom methods whose names start with _, and advertise custom capabilities at initialisation.

5One prompt turn, end to end

a request that reads, edits and asks first

The sequence follows one prompt in v1: the person asks the agent to turn on debug logging. The agent reads a config file through the editor, proposes an edit, asks permission, writes the file, and finishes. Read it top to bottom.

Two things stand out. The agent reads the file through the editor, so it sees the person's unsaved changes rather than a stale copy on disk. And the turn is one long-running request: the prompt goes out at the top and its answer, with end_turn, comes back at the bottom, with everything else streamed in between. That design is exactly what v2 rethinks.

The prompt itself is a JSON-RPC request carrying content blocks:

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "session/prompt",
  "params": {
    "sessionId": "sess_7f2",
    "prompt": [
      {
        "type": "text",
        "text": "Turn on debug logging in config.json"
      }
    ]
  }
}

Mid-turn, the agent reports the edit as a tool call update carrying a diff. This shape comes from the v1 tool calls page:

{
  "jsonrpc": "2.0",
  "method": "session/update",
  "params": {
    "sessionId": "sess_7f2",
    "update": {
      "sessionUpdate": "tool_call",
      "toolCallId": "call_002",
      "title": "Enable debug in config.json",
      "kind": "edit",
      "status": "pending",
      "locations": [
        {
          "path": "/home/dev/shop/config.json",
          "line": 2
        }
      ],
      "content": [
        {
          "type": "diff",
          "path": "/home/dev/shop/config.json",
          "oldText": "{\n  \"debug\": false\n}",
          "newText": "{\n  \"debug\": true\n}"
        }
      ]
    }
  }
}

Before writing, it asks permission. The editor shows the options and returns the person's choice:

// Agent asks the editor
{
  "jsonrpc": "2.0",
  "id": 5,
  "method": "session/request_permission",
  "params": {
    "sessionId": "sess_7f2",
    "toolCall": {
      "toolCallId": "call_002"
    },
    "options": [
      {
        "optionId": "allow-once",
        "name": "Allow once",
        "kind": "allow_once"
      },
      {
        "optionId": "reject-once",
        "name": "Reject",
        "kind": "reject_once"
      }
    ]
  }
}

// Editor answers with the person's choice
{
  "jsonrpc": "2.0",
  "id": 5,
  "result": {
    "outcome": {
      "outcome": "selected",
      "optionId": "allow-once"
    }
  }
}

When the work is done, the agent finally answers the prompt request that has been open all along:

{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "stopReason": "end_turn"
  }
}

6Version 2: what's changing

a draft that moves beyond the turn

The project published the first draft of v2 on 20 July 2026. It is still labelled draft, and the migration guide tells implementers to keep v1 working and add v2 behind version negotiation and feature flags until it stabilises. The announcement explains the motivation plainly: agents now work longer, run things in the background and receive input while busy, and a protocol built around one request per turn makes that awkward. The diagram compares the two lifecycles.

The migration guide lists five things to remember. The table puts them next to what they replace.

Changev1 todayv2 draft
Prompt lifecycleThe prompt response ends the turn and carries the stop reasonThe response returns the inserted message's id; progress and completion arrive as state_update notifications
UpdatesTool calls patched by id; messages streamed as chunksMessages, tool calls and terminals all patched by id with one rule set; plans replaced whole
Files and terminalsThe editor reads and writes files and runs commands for the agentRemoved; editors offer such tools as MCP servers; terminals become display-only output the agent owns
CapabilitiesSeparate client and agent fields, booleansOne shape on both sides, nested by area, object markers instead of booleans
ExtensibilityCustom data in _meta, custom methodsMost enums and unions accept unknown values, so new variants don't break older peers

Two more additions matter for anyone building orchestration. Subagents become first-class: an agent can announce child sessions, and every v2 editor must handle them. And background work gets a place in the protocol: an agent can report itself idle while listing tool calls or terminals that are still running, and offer cancel controls for each.

The removal of file and terminal APIs is the most consequential change. The guide's reasoning is that these methods were implemented inconsistently outside a few IDEs, and agents needed their own file and execution handling anyway for editors that didn't offer them. In v2, an editor that wants to share unsaved buffers or a sandboxed shell does it the same way as any other tool: by passing an MCP server into the session. That pulls ACP and MCP closer together. v2's content blocks are also realigned with MCP's 2026-07-28 revision.

Supporting both. Version is negotiated once per connection at initialize. The TypeScript and Rust SDKs include routers that send each connection to a v1 or a v2 implementation behind shared application logic. The project recommends exactly that: keep v1 peers working, because v1-only editors and agents will remain common for some time.

7ACP, MCP and A2A

three protocols, three boundaries

The three open agent protocols each cover a different boundary, and a single coding session can use all three. The layer diagram shows where each sits.

The relationships are tighter than the picture suggests. The editor configures MCP servers once and passes them to whichever ACP agent the person chooses, so tools travel with the editor rather than with the agent. v2 goes further, replacing the editor's own file and terminal APIs with MCP servers and aligning content types with MCP. The SDKs also carry draft support for running MCP over the ACP connection itself, so an editor can offer tools without a separate server process; the Rust SDK exposes it behind an unstable flag.

A2A sits further out. A coding agent that delegates a code review to another company's agent would use A2A for that hop, while the person still sees everything through ACP. Governance differs too: MCP and A2A sit in the Agentic AI Foundation, while ACP does not yet (section 16).

8Transports

stdio today, remote in progress

ACP v1 defines one transport. The transport page spells it out: the editor launches the agent as a subprocess; messages are single JSON-RPC objects, one per line, on the agent's standard input and output; the agent may log to standard error; and nothing that isn't a valid ACP message may appear on standard output. Implementations may also define custom transports, provided they keep the message format and lifecycle.

Remote agents are the obvious next step: an agent running in a cloud sandbox while the person works in a local editor. A transport based on Streamable HTTP, with a WebSocket option, is being specified in its own RFD and is not part of core v1 or v2. The project has set up a Transports Working Group to stabilise it. Until then, remote setups rely on custom transports or on vendors' own bridges.

Two details in the registry data are worth noticing. Several big agents arrive through adapters rather than native support: the Claude entry is described as an ACP wrapper for Anthropic's Claude, with Anthropic, Zed and JetBrains as authors, and Codex arrives through an ACP adapter for OpenAI's coding assistant. Licences vary by entry, from Apache 2.0 to proprietary, which matters for anyone auditing what they install. And a data vendor's agent, Snowflake's Cortex Code, is listed alongside the coding tools. The VS Code gap is the adoption story's open question. Agents still need a separate VS Code extension to reach its users, so ACP hasn't yet removed the per-editor plugin for the largest audience.

11The registry and distribution

how an agent gets onto a developer's machine

An ACP agent is a program the editor launches, so distribution means getting the right binary or package onto the machine and knowing how to start it. The registry, which Zed and JetBrains launched together in January 2026, solves this with a public JSON file. Each entry names the agent, its version, authors, licence and repository, and a distribution block: either an npm package run with npx, often with an argument like --acp to switch the tool into protocol mode, or prebuilt binaries per platform. Editors read the registry, install on request and update automatically.

Agents not in the registry can still be added by hand in each editor's settings, pointing at a local command. That's the route for internal agents a company doesn't publish.

13Security in practice

a program on your machine, with your keys

An ACP agent is not a remote service. It runs as a process on the developer's machine, with that person's files, credentials and network. The security page is unusually frank about what follows: the agent runs with whatever permissions its process is given, and ACP itself does not sandbox it. It lists three things as out of scope entirely: a malicious agent binary, detecting prompt injection, and operating-system sandboxing. The diagram shows where untrusted input enters and which defences sit where.

Permission is a request, not a lock. Because the agent performs its own operations, a rejection in the editor only works if the agent honours it. The spec's residual-risk note names the remaining exposure in one line each: a person can approve something harmful, prompt injection can steer operations the person allowed, and an agent can act without asking at all. Treat ACP permissions as a good interface for an honest agent, not as a control against a compromised one.

The editor's job is to show the truth. The spec asks editors to describe each request from its kind, locations and content rather than the agent's own title, to show commands and paths in full, to strip hidden characters (bidirectional, zero-width and tag characters) from commands, paths and diffs, to sanitise Markdown and never run scripts from agent output, and to avoid fetching remote images or opening links without the person's action. Automatic approval should never rely only on the agent-written title.

The agent's job is to treat inputs as data. The spec asks agents to treat files, embedded resources and tool results as data rather than instructions, to ask before sending data off the machine after reading untrusted content, and to ask before writing files that control execution or approval: version-control hooks, editor or agent settings, MCP configuration. That last item closes a classic escalation path, where an injected instruction quietly rewrites the agent's own permissions.

Your job is the outer wall. Install agents from sources you trust and pin versions rather than tracking the latest. Check each registry entry's licence and authors. Run agents in a container or OS sandbox when they work on untrusted repositories. Give the agent's model and tool credentials the narrowest scope that works, and keep secrets out of _meta fields, which the spec warns against. If a proxy sits between editor and agent, remember it can read and change every message.

14Designing a good agent or editor integration

what separates a usable integration from a working one

These practices come from the spec's guidance plus the author's judgment.

Report tool calls richly. Set the kind, the file locations and a clear title for every tool call, and attach diffs to edits. Editors build their whole interface from these fields; an agent that reports everything as other with no locations looks like a black box.

Ask with precise options. Offer permission options whose names state their scope ("Allow edits in src/ for this session"), honour exactly what was approved, and ask again if the command or target changes. Never treat an unrecognised answer as approval.

Use the editor's view of files when it offers one. In v1, reading through the editor gives the agent unsaved changes and keeps both sides consistent. Plan for v2, where the same access arrives as an MCP server, by keeping file access behind one interface in your agent.

Keep standard output clean. Over stdio, standard output is the protocol channel; the spec forbids anything else there. Log to standard error.

Support both versions on purpose. Negotiate the version at initialize and route each connection to a v1 or v2 handler. Don't drop v1: the project expects v1-only peers to stay common.

Test against the kit. Run the Test Compatibility Kit, then try the agent in at least two different editors, since implementations differ in which optional capabilities they offer.

15Examples

adding an agent by hand, and the opening handshake

Adding a custom agent to an editor. Both Zed and JetBrains accept agents that aren't in the registry. The shape is nearly identical: a name and the command to launch. These snippets follow configurations published in two community guides; check your editor's documentation for the full set of fields.

// Zed: settings.json
{
  "agent_servers": {
    "My Custom Agent": {
      "type": "custom",
      "command": "/path/to/agent"
    }
  }
}

// JetBrains: ~/.jetbrains/acp.json
{
  "agent_servers": {
    "OpenCode": {
      "command": "/usr/local/bin/opencode"
    }
  }
}

The opening handshake. The first message an editor sends tells the agent what it can offer. This v1 request is taken from the migration guide's side-by-side example:

{
  "jsonrpc": "2.0",
  "id": 0,
  "method": "initialize",
  "params": {
    "protocolVersion": 1,
    "clientCapabilities": {
      "fs": {
        "readTextFile": true,
        "writeTextFile": true
      },
      "terminal": true
    },
    "clientInfo": {
      "name": "my-editor",
      "version": "1.0.0"
    }
  }
}

Then the editor opens a session, giving the working folder and any MCP servers it wants the agent to use:

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "session/new",
  "params": {
    "cwd": "/home/dev/shop",
    "mcpServers": []
  }
}

The same handshake in v2. For comparison, a v2 editor sends a single capabilities object and a required info block, and no longer offers file or terminal access:

{
  "jsonrpc": "2.0",
  "id": 0,
  "method": "initialize",
  "params": {
    "protocolVersion": 2,
    "info": {
      "name": "my-editor",
      "title": "My Editor",
      "version": "1.0.0"
    },
    "capabilities": {}
  }
}

16Governance and what's next

two companies today, a foundation later

ACP's governance is the least settled of the three agent protocols. The project's governance page describes an interim model: Zed and JetBrains govern the protocol jointly, with two lead maintainers, Ben Brandt of Zed and Sergey Ignatov of JetBrains, who can veto decisions, and a stated aim of moving to an independent foundation. MCP and A2A already sit in the Linux Foundation's Agentic AI Foundation. For a company betting on ACP, the practical meaning is simple: two vendors with their own editors decide the protocol's direction today.

Changes arrive through RFDs, and many land in v1 without breaking anything. The v2 announcement lists the themes still in motion. Four questions remain open.

When does v2 stabilise? No date is published. Until then, implementers carry two code paths, which the SDK routers make manageable but not free.

Will VS Code adopt it? Microsoft already uses ACP in its terminal. Native support in VS Code would make ACP the default way to put any agent in front of most developers; its absence keeps per-editor plugins alive.

What will remote agents look like? The Streamable HTTP and WebSocket transport would let local editors drive agents in cloud sandboxes, which is also where safer isolation is easiest. It's still an RFD.

Will ACP join a foundation? The governance page says that's the goal. Joining MCP and A2A in the Agentic AI Foundation would complete a three-layer stack under one neutral home; staying with its two sponsors keeps decisions fast but concentrated.

17Checklists

the page, condensed into things to do

If you're building an ACP agent

  1. Report every tool call with a kind, locations and a clear title; attach diffs to edits (section 14).
  2. Ask before risky actions with options that state their scope, and honour exactly what was approved.
  3. Treat files, web content and tool results as data; ask before sending data off the machine.
  4. Never write hooks, settings or MCP configuration without asking.
  5. Log to standard error; keep standard output for protocol messages only.
  6. Negotiate the version and keep v1 working while you add v2 (section 6).
  7. Run the Test Compatibility Kit and try at least two editors.
  8. Publish to the registry with an accurate licence, authors and pinned package versions.

If you're integrating ACP into an editor or choosing agents

  1. Describe permission requests from their kind, locations and content, and show commands and paths in full (section 13).
  2. Strip hidden characters, sanitise Markdown, and never run scripts or fetch remote content from agent output automatically.
  3. Keep the agent to the session's root folders.
  4. Remember that permissions are advisory; sandbox agents that work on untrusted code.
  5. Install agents from trusted sources and pin their versions.
  6. Pass MCP servers deliberately: every tool you hand over is a tool the agent can use.
  7. Plan for v2, where file and terminal access move to MCP servers.
  8. Track governance: today two vendors decide the protocol's direction (section 16).
