3

1 · Bad data is published

Nothing stops bad data between the pipeline and the consumers.

Cost: wrong decisions, lost trust

2 · It is found late

A consumer finds the problem, often the next day, not the team.

Cost: long MTTD, mean time to detect

3 · It is slow to fix

Nobody knows which tables used the bad data, so the team runs everything again.

Cost: long MTTR, mean time to recover

The cause

The logic, the checks, the meaning and the access rules live in different tools. Each tool keeps its own copy, and the copies drift apart.

5

Prevent

Five gates stop problems early

1

As you edit

Linter

Catches: risky SQL, for example SELECT *.

If it fails: the plan stops, or it warns.

2

As you edit

Unit tests

Catches: wrong logic, tested on fixed rows.

If it fails: the plan stops.

3

Before you apply

Plan review

Catches: a change that breaks a consumer.

If it fails: the plan stops and names the measure.

4

In each run

Assertions

Catches: bad rows in inputs and in models.

If it fails: the models after it do not run.

5

After each run

Data quality checks

Catches: patterns, such as fewer orders than usual.

If it fails: Vulcan records it and sends a message.

Before anything is built

Gates 1 to 3 catch mistakes in the logic and in changes.

On real data

Gates 4 and 5 catch bad data from sources.

Last gate: gold only

Consumers can read only the gold layer, so bad data that stops in silver never reaches them.

7

Change

A plan shows the effect of a change

You edit the SQL. Vulcan compares it with the version that runs now, puts the change in a category, and lists each model that it affects. You read the plan, then you apply it.

Plan: remove a column from orders

orders

daily_sales

metric: stop

API

customers

Built again

Breaking: plan stops

Unchanged

Breaking

Data that later models read can change: a new formula, a new filter or a removed column. All of them are built again.

Non-breaking

You only added a column. Only this model is built again.

Forward-only

Only new data uses the change. Old data stays as it is.

Metadata

Nothing is built, for example a new description or owner.

12

Your week

Four tasks that change

Late source data

Before: the job runs and loads half a day.

With Vulcan: a signal waits until the source is ready.

Bad source data

Before: it goes into every table.

With Vulcan: an assertion stops it, and the owner gets a message.

Change a model

Before: edit, run, and look at each table after it.

With Vulcan: read the plan, then apply.

Correct bad data

Before: run the full pipeline again.

With Vulcan: restate the days that had the problem.

What stays the same: your SQL, your engine and your warehouse

Vulcan writes the SQL for your engine: Postgres, Snowflake, BigQuery, Databricks, Trino, Spark and more.
