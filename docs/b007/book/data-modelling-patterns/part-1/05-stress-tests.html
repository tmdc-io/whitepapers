Part I · Chapter 5

The twelve stress tests

This chapter covers
  • Why this book tests patterns instead of describing them
  • The twelve events that every pattern must survive
  • How a result is scored: Good, Costly, or Fails
  • Scoring each pattern as teams deploy it
  • Build and run effort, the thirteenth measure
  • How to read a chapter's strip, and how to disagree with it

Every modeling pattern looks good on a whiteboard. Its diagram is clean, its tables have clear names, and its first load works. The differences between patterns show later, when something changes: a new source arrives, a relationship changes shape, a regulator asks an awkward question. This chapter defines twelve such changes at Lantern, and the scoring that every pattern chapter uses for them.

5.1Why test instead of describe

Descriptions of patterns tend to list strengths in the words of the pattern's own community. "Agile", "auditable", "business-friendly", and "flexible" each mean something, but they are hard to compare. A test is easier to compare. It asks one concrete question: when this event happens at Lantern, what must change in the model, and what is lost?

The twelve tests come from the systems and rules in chapter 2 and from the timeline in Table 2.3. Ten of them are about change over time, because change is what separates the patterns. One is about how easy the data is to query. One is about the law. The mix is deliberate. A pattern that absorbs every change can still be slow to query or hard to delete from, and the tests show that too.

5.3Scoring

Each pattern gets one of three results on each test.

Good means the pattern absorbs the event with new rows or new tables only. Nothing that already exists has to change, and nothing is lost.

Costly means the pattern handles the event, but someone must change existing tables, rewrite queries, or reload data. The cost can be small or large. The pattern chapter explains which.

Fails means the pattern loses information, gives wrong answers, or needs a redesign to handle the event.

The results are the author's judgment, based on the reasoning in each pattern chapter and in chapter 16. They are not measurements. A different team, with different skills and tools, can reasonably move a result by one step. What matters more than any single chip is the reason behind it, and every result has one.

5.4Each pattern as teams deploy it

A pattern is scored the way teams usually run it, not in its barest form. The rule matters most for test 11. Inmon's normalized core and a Data Vault are both hard to query directly, and both are normally deployed with a serving layer on top. Scoring one with its serving layer and the other without it would not be fair.

When a bare core gives a different result, the pattern chapter says so. For example, the raw Data Vault without its serving layer fails test 11, and the Data Vault chapters explain why the serving layer exists.

5.5Build and run effort

Serving layers and extra tables are not free. A Data Vault with marts on top has many more tables and much more load code than a single star. A comparison of the twelve tests alone favors the heaviest patterns every time, and gives a small team with simple needs the wrong advice.

So the full comparison in chapter 16 adds a thirteenth measure that is not a stress test: build and run effort. It counts the number of tables, the amount of load code, and what a new team member must learn before they can work on the model. It is rated Low, Medium, or High, using the same three colors.

5.6How to read a strip

Each pattern chapter ends with a section called Strengths and limits. It has two or three paragraphs about what the pattern does well and where it struggles, then a strip of twelve chips, one per test, and one sentence on when to choose the pattern. The strip below is the one from chapter 8, for the star schema with its advanced techniques.

Read the strip as a profile, not as a score. Count the colors for a quick impression: the star is mostly amber, with green on history and fast queries. Then select the chips that matter for your situation, and read the reason. If you disagree with a result, follow the link to chapter 16, where the full argument for each result sits next to the results for every other pattern.

Summary

  • Patterns differ most when something changes, so this book tests them against twelve events at Lantern instead of describing them.
  • Ten tests are about change, one is about querying, and one is about the law.
  • Each result is Good, Costly, or Fails, and each one comes with its reason. The results are judgments, not measurements.
  • Each pattern is scored as teams deploy it, including the serving layers that it normally has.
  • Build and run effort is a thirteenth measure, so that heavy patterns do not win by default.
  • Every pattern chapter ends with the same strip, and chapter 16 holds the full reasoning.
