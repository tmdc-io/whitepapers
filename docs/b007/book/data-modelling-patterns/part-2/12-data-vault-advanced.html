The raw vault from chapter 11 absorbs change better than any pattern so far, and nobody can use it yet. It holds three keys for Maria with nothing that says they are one person. It holds one row per load in every satellite, so every question starts with "find the newest row". It has no place for business rules, and its insert-only rule collides with the right to delete. Its strip showed one Fails and four Costly results.

This chapter adds what teams build around the raw vault in practice: special satellites and links for awkward data, helper tables for fast reads, a business vault for rules, information marts for analysts, and a plan for deletion. At the end, the vault is scored again, as it is usually deployed.

12.1Multi-active satellites

Maria has three phone numbers in the CRM: mobile, home, and work. All three are valid at the same time. A normal satellite has one row per key per load, so it cannot hold three current values. A multi-active satellite adds a sub-key that tells the values apart. Here the sub-key is the phone type.

Change detection works on the whole set. The hash diff covers all of Maria's phones in one load. When she moves to San Jose, she drops the home phone and gets a new work number. The set changes, so the loader inserts the full new set, shown in green. To read her phones on any date, take the whole set with the newest load_dts up to that date.

The grooming system's pets fit the same shape. Its bookings name pets but do not key them, so until the pets are matched to hub_pet, the vault stores them in a multi-active satellite on the customer, with the pet name as the sub-key.

12.2Effectivity satellites and driving keys

A link records that a relationship was seen, never that it ended. An effectivity satellite on a link records when the relationship is valid. In September 2025, Sam becomes a co-owner of Biscuit. In January 2026, Sam and Maria separate, and the CRM removes Sam as an owner.

Table 12.2 Effectivity of Sam's ownership

The link row stays forever, and the effectivity satellite closes it. Some relationships also have a driving key: the side of the link that decides what "the same relationship" means. An order has exactly one customer. If the web shop moves order W-77810 from Maria's account to Sam's, the order is the driving key. The old order-to-Maria relationship must end when the order-to-Sam relationship starts, even though the source never sent "ended". The effectivity load uses the driving key to close the old row on its own.

12.3Record-tracking and status-tracking satellites

Some sources send a full snapshot every night, with every customer, changed or not. Happy Tails works this way. A record-tracking satellite stores one small row per key per load, saying "this key was present". It answers "when did the Happy Tails system last show this customer?" without storing the full attributes every night.

Deletes are invisible in an insert-only model unless you look for them. When Happy Tails removes a duplicate customer, the record simply stops appearing in the snapshot. A status-tracking satellite compares each full snapshot with the keys that the vault already knows. A key that is missing gets a new row with status D, for deleted. A key that returns gets status I again. The vault never removes the old rows, but every report can exclude records that the source deleted, and an auditor can see when it happened.

12.4Same-as and hierarchical links

12.4.1Same-as links

Stress test 2 asks for one Maria, while audit wants to see what each system said. The hub already holds all her keys. A same-as link records which keys belong to the same real customer. It links the hub to itself: one hash key for the chosen master key, one for the duplicate. Figure 12.1 shows Maria's.

The matching rules are business decisions, so they live in the business vault (section 12.9), and their results are stored as rows of the same-as link. Lantern's rule says: the same email after trim and lower case is a match, and the same phone plus the same last name is a match. In June, the rule wrongly matched Happy Tails customer HT-90051, Maria's sister Ana, to Maria, because they share a family phone. Chapter 6 showed what that mistake cost in a normalized core. 12.4.2Hierarchical links

Lantern's product categories form a tree: Dog, then Dog food, then Dry dog food. A hierarchical link joins a hub to itself to store parent and child, such as link_category_parent. When merchandising moves cat litter under Home and Hygiene, the vault inserts a new link row, and an effectivity row ends the old one. Every past report can still show the tree as it was on any date. This is the vault's answer to the catalog reorganization in chapter 9.

12.5Non-historized links

Some events never change once they happen: a card tender at the till, a timesheet punch, a web page view. Change detection is wasted on them, and a satellite per event doubles the row count. A non-historized link, also called a transactional link, stores the event's values in the link row itself. Each punch is one row with the employee, the store, the time, and the punch type. It loads with a plain insert. Lantern's clocks record about 6 million punches a year, so the saving is real.

A correction to an event is not an update. The source sends a new event that reverses or adjusts the first one. That matches how payroll systems already work. The 8 July shift correction from chapter 2 arrives as an adjustment punch, and both punches stay.

12.7Point-in-time tables

Listing 11.4 showed the problem. To read Maria as of 1 June, you need the newest row up to that date from each satellite, with a window function each. Across 600,000 customers and a year of daily snapshots, that query is slow and hard to write.

A point-in-time table, or PIT, does that work once. For each hub key and each snapshot date, it stores the load_dts of the valid row in each satellite. Every later query then joins on equality, which every engine does fast.

Listing 12.1 Build the customer PIT for one snapshot date, then read through it

INSERT INTO pit_customer (hk_customer, snapshot_date, crm_load_dts, web_load_dts, pii_load_dts)
SELECT h.hk_customer,
       DATE '2025-06-01',
       COALESCE((SELECT MAX(c.load_dts) FROM sat_customer_crm c
                 WHERE c.hk_customer = h.hk_customer
                 AND   c.load_dts < TIMESTAMP '2025-06-01 00:00:00'),1
                TIMESTAMP '0001-01-01 00:00:00'),                       -- ghost row2
       COALESCE((SELECT MAX(w.load_dts) FROM sat_customer_web w
                 WHERE w.hk_customer = h.hk_customer
                 AND   w.load_dts < TIMESTAMP '2025-06-01 00:00:00'),
                TIMESTAMP '0001-01-01 00:00:00'),
       COALESCE((SELECT MAX(p.load_dts) FROM sat_customer_pii p
                 WHERE p.hk_customer = h.hk_customer
                 AND   p.load_dts < TIMESTAMP '2025-06-01 00:00:00'),
                TIMESTAMP '0001-01-01 00:00:00')
FROM   hub_customer h;

-- Reading through the PIT: plain equality joins, no window functions.
SELECT p.snapshot_date, c.address, w.loyalty_tier
FROM   pit_customer p
JOIN   sat_customer_crm c ON c.hk_customer = p.hk_customer AND c.load_dts = p.crm_load_dts3
JOIN   sat_customer_web w ON w.hk_customer = p.hk_customer AND w.load_dts = p.web_load_dts;
  1. 1For each satellite, the newest load before the snapshot. The half-open rule from section 4.3 applies: the snapshot date itself is excluded.
  2. 2A customer with no web account yet points at a ghost record: one dummy row per satellite, with the earliest possible date and empty values. It lets the read query use inner joins everywhere.
  3. 3Equality on both columns of the satellite's key. Engines join this fast, and analysts can read it.

12.8Bridge tables

A PIT table removes the newest-row logic from satellites. A bridge table removes long walks across links. To find the customer behind a sale line, a query walks link_sale_line to hub_order to link_order_customer to hub_customer, then through the same-as link to the master key. A bridge stores that whole path, with the hash key at each step, for each snapshot date. The recall query for lot L24-0917 becomes: find the lot in the bridge, read the master customer key, done.

PIT and bridge tables hold no data of their own, only keys and load times. They can be dropped and rebuilt at any time. Most teams rebuild them after each load, for the snapshot dates that reports need.

NoteThe Data Vault bridge and the dimensional bridge in section 8.3 share a name and not a purpose. The dimensional bridge models a many-to-many relationship with weights. The vault bridge is a query helper that shortens join paths.

12.9The business vault

The raw vault stores what sources said. The business vault stores what the company decided. It uses the same table types, built by queries over the raw vault instead of loaded from sources. Its main tool is the computed satellite, which holds the result of a business rule for each key and date. Three Lantern rules show how it works.

Address standardization. A computed satellite turns "220 Bay Road" and "220 Bay Rd" into one standard form. The raw satellite still shows both, as in the exercise in section 11.4.

Active customer, two versions. Stress test 8 changes the meaning of active customer from 12 months to 6 months. The computed satellite gets a rule_version column, and both versions are stored for every customer and every date. Last year's board report used version 1, and it still reproduces exactly. This year's reports use version 2. Nobody has to explain why last year's numbers changed, because they did not.

Pay and labor rules. California's daily overtime and meal break rules (section 2.4) become a computed satellite on link_employment. For each shift, it stores regular hours, overtime hours, double-time hours, and any meal break penalty hour. The inputs are the raw punches and the minimum wage reference table.

Listing 12.2 A versioned business rule: active customers

INSERT INTO bv_sat_customer_active (hk_customer, snapshot_date, rule_version, is_active)
SELECT m.master_hk, DATE '2026-01-01', 'v2-6-months',1
       CASE WHEN MAX(s.order_date) >= DATE '2025-07-01' THEN TRUE ELSE FALSE END
FROM   bv_customer_master m                                 -- same-as results2
JOIN   link_order_customer l ON l.hk_customer = m.member_hk
JOIN   sat_order_web       s ON s.hk_order    = l.hk_order
WHERE  s.load_dts < TIMESTAMP '2026-01-01 00:00:00'
GROUP BY m.master_hk;
-- Version 1, with a 12-month window, stays in the same table, untouched.
  1. 1The rule version is part of the row. Reports choose a version, and an old report keeps its old version.
  2. 2The rule counts orders across all of a person's keys, through the same-as results. A real version also unions store and Happy Tails orders.

The wage claim from stress test 7 is now answerable in two ways. What did Lantern have on record on the 15 July pay date? Filter the raw punches and pay rates on load_dts up to that date. What was the correct pay? Rerun the overtime rule on the corrected punches. The difference is the retro pay, and every input carries its source and arrival time.

12.10Information marts

Analysts at Lantern never query hubs and links. They query information marts: stars, wide tables, or summaries built from the raw and business vault. A mart can be a set of views or a set of tables. Views cost nothing to store and always show the latest data, but every query pays the join cost. Tables are fast and must be refreshed after each load. Most teams start with views and turn the slow ones into tables.

Listing 12.3 A type 2 customer dimension, built from the vault

CREATE VIEW mart.dim_customer AS
SELECT m.master_bk                                 AS customer_id,   -- one id per person
       std.address_std                             AS address,
       s.moved_on                                  AS valid_from,
       COALESCE(LEAD(s.moved_on) OVER (PARTITION BY m.master_bk
                                     ORDER BY s.moved_on),
                DATE '9999-12-31')                  AS valid_to1
FROM   sat_customer_crm s
JOIN   bv_customer_master m        ON m.member_hk   = s.hk_customer
JOIN   bv_sat_customer_address_std std
  ON   std.hk_customer = s.hk_customer AND std.load_dts = s.load_dts;2
  1. 1LEAD takes the next move date for the same person, which ends this version. The newest version gets the far-future date.
  2. 2The standardized address comes from the business vault, so "Rd" and "Road" are one version, not two.

In a star built straight from sources, the SCD type is decided once and baked into stored rows. On a vault, a dimension is a query. If finance wants type 1 and marketing wants type 2, each gets its own view over the same satellites, and changing the type later is a change to a view, not a data migration.

12.11Deleting personal data

Stress test 12 is a real conflict. On 9 February 2026, Dev Patel asks Lantern to delete his personal information as a customer. The CCPA allows exceptions, including data that a business must keep to meet a legal duty, and payroll record keeping is one. So Lantern must delete Dev's customer data and keep his pay records. In an insert-only store, both halves need a plan made at design time.

Split personal data into its own satellites. Name, email, phone, and address go into sat_customer_pii, as section 11.4.1 suggested. Purchase history goes elsewhere. On request, delete Dev's rows from the personal-data satellites only. This is a deliberate, logged exception to the insert-only rule. His sales stay as anonymous history.

Protect personal business keys. The hub key for a web customer is an email, and a hash of an email is still personal data. Options include a keyed hash with a secret (an HMAC), a random token issued by a separate key store, or a non-personal customer number as the business key instead of the email.

Encrypt, then delete the key. With crypto-shredding, each customer's personal values are encrypted with that customer's own key. To delete, destroy the key. The rows stay, and nobody can read them, including from backups.

Keep the employee side separate. Dev's employee data lives under hub_employee, with its own personal-data and pay satellites. The deletion touches the customer hub only. Pay records stay for the legal retention period, then follow their own schedule.

Record the request. The deletion is an event that an auditor will ask about. Store it in a non-historized link: who asked, when, which keys, and what was removed.

WarningMarts and PIT tables copy personal values. After a deletion, rebuild every mart that holds the customer's attributes, or build marts as views over the personal-data satellites so that they follow the deletion automatically.

12.12Building a vault from metadata

A vault for Lantern has hundreds of tables, and almost all of their load statements share one of three shapes: Listing 11.1 for hubs, Listing 11.2 for links, and Listing 11.3 for satellites. Writing each one by hand is slow and invites small differences, such as a missing TRIM, that break hash keys.

So vault teams describe the model as metadata instead. A table lists each hub with its business key columns per source. Another lists each link with the hubs it joins, and another each satellite with its parent and columns. A generator turns that metadata into DDL, stage logic, and load statements, using one template per table type. Adding a source then means adding rows of metadata, and every load follows the same rules, including the same hash recipe. Many teams treat this automation as a requirement for Data Vault, not an extra: the pattern pays for its many tables only when the tables cost little to create.

12.13Common mistakes

Skipping the business vault. If matching, standardization, and pay rules live in report queries or dashboard tools, they are repeated, they disagree, and nobody can version them. Then stress test 8 fails even though the raw vault is fine.

Letting analysts query the raw vault. The raw vault is for loading and audit. Without PIT tables and marts, analysts write slow, wrong queries and decide that Data Vault does not work.

No plan for deletion. Personal data mixed into general satellites makes stress test 12 a rewrite. Decide the personal-data split before the first load.

Treating every table as historized. Events that never change belong in non-historized links. Change detection on 6 million punches a year wastes time and storage.

Building everything before delivering anything. A vault grows well in small pieces. Start with one business process, deliver a mart on it, and add sources one at a time. That is the vault's main strength, so use it from the first month.

12.14Strengths and limits

With its special tables and its layers, Data Vault keeps every strength of the raw vault and adds the missing pieces. Same-as links match identities without losing any source's view, and a wrong match is one more row. Effectivity and multi-active satellites handle relationships that end and values that come in sets. The business vault stores rules as versioned data, so an old report reproduces exactly. PIT tables, bridges, and marts give analysts the easy shape of a star. Every row still carries its load time and record source, so audits work across the whole stack.

The price is size and discipline. The vault has the most tables of any pattern in this book, and it needs automation to build and run them. Its layers must be rebuilt in the right order after each load. Deletion works only if the personal-data split was designed in from the start, and even then it is a deliberate exception to the pattern's main rule. Build and run effort, the thirteenth measure in section 5.5, is High.

Choose the full Data Vault when sources are many and keep changing, when audit and regulation matter, and when the team can automate. For a small team with a few stable sources, its tables and layers cost more than they return.

Summary

  • Multi-active satellites hold sets of current values. Effectivity satellites record when relationships start and end, using driving keys where one side decides.
  • Record-tracking and status-tracking satellites detect presence and deletion in snapshot sources.
  • Same-as links record which keys are one entity. A wrong match is ended with new rows, and the history of the mistake stays visible.
  • Hierarchical links store trees with history. Non-historized links store events that never change. Reference tables hold small lookup lists.
  • Point-in-time and bridge tables are rebuildable query helpers that remove newest-row logic and long join paths.
  • The business vault stores rule results as versioned computed satellites.
  • Information marts give analysts stars and wide tables, as views or tables over the vault.
  • Deletion needs personal-data satellites, protected business keys, and a separate employee side, designed in from the start.
  • Vaults are built from metadata and templates. The full vault scores Good on eleven tests, at the highest build and run effort in the book.
