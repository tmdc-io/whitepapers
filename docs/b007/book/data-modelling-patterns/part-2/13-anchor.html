On 4 November 2025, the web shop adds a loyalty tier column and renames another. In the star, that meant a new dimension column and a broken load. In the vault, it meant a new satellite. In an anchor model, it means one new table, and nothing else changes: no existing table gains a column, no existing row is rewritten, and no existing query notices.

Anchor modeling takes the vault's idea, separate what changes from what does not, as far as it can go. Every attribute gets its own table. This chapter builds Lantern's customers and pets as an anchor model, shows how generated views keep the many tables usable, and then explains the full model that anchor modeling uses to record time, sources, and certainty.

13.1The idea

Anchor modeling was published by Olle Regardt, Lars Rönnbäck, Maria Bergholtz, Paul Johannesson, and Petia Wohed in 2009, in a paper that won the best paper award at the ER 2009 conference. An extended version appeared in the journal Data and Knowledge Engineering in 2010. The anchor modeling site hosts the papers, and its authors publish an open-source generator for the database code.

The design goal is stated plainly in the original paper: a change to the model needs only extensions, never modifications. A model built that way can evolve for years without a migration, because every change adds tables and leaves old ones alone.

The tool for that goal is sixth normal form, from section 3.6.3. In 6NF, a table holds a key and at most one other value, usually with the time when the value was true. A customer is not one table with ten columns. It is an identity table plus one table per attribute.

13.2The building blocks

An anchor model has four constructs. Each maps to exactly one kind of table.

An anchor holds an identity. CU_Customer has one column, CU_ID, and one row per customer. It stores nothing else, not even a business key. A business key, such as the CRM ID, is just another attribute.

An attribute holds one property of an anchor. CU_NAM_Customer_Name holds names, and CU_ADR_Customer_Address holds addresses. A static attribute never changes, such as a pet's birth date. A historized attribute adds a changing-time column, such as CU_ADR_ChangedAt, and keeps one row per value.

A tie holds a relationship between anchors. CU_owner_PE_owned connects customers and pets, with a role for each side. Ties can be static or historized, and their cardinality comes from which roles form the key.

A knot holds a small shared set of values. Lantern's loyalty tiers, None, Silver, Gold, and Platinum, form the knot TIR_Tier. A knotted attribute stores a reference to the knot instead of the text, so "Gold" is stored once.

Recent versions of the method add a fifth construct, the nexus, for event-like things that have their own identity and roles, such as a grooming visit. This chapter uses anchors, attributes, ties, and knots, which carry the pattern.

13.3The Lantern anchor model

Figure 13.1 shows Lantern's customers and pets as an anchor model. Anchors are the plum boxes, attributes the grey boxes around them, the tie sits between the anchors, and the knot sits on the right.

The table names follow the method's naming convention. Each anchor has a two-letter mnemonic, such as CU. Each attribute has a three-letter mnemonic, such as ADR, and its table name combines both mnemonics with the descriptive names: CU_ADR_Customer_Address. Columns follow the same pattern, such as CU_ADR_ChangedAt. With hundreds of tables, the convention is what keeps a model readable: anyone can tell from a name which anchor a table belongs to and what it holds.

13.4Loading

An anchor model loads insert-only, like a vault, and each attribute loads on its own. When the CRM sends Maria's new address, the load inserts one row into CU_ADR_Customer_Address and touches no other table. Her name, email, and tier are not copied.

Identity works differently from a vault. A vault stores every source key in a hub and matches them later. An anchor holds a surrogate identity, so the load must decide which anchor a source row belongs to before it can insert attributes. When Happy Tails customers arrive, each must be matched to an existing CU_ID or given a new one. In that respect, an anchor model behaves like a normalized core or a star: identity is decided at load time.

Listing 13.2 Load changed addresses

INSERT INTO CU_ADR_Customer_Address (CU_ADR_CU_ID, CU_ADR_Customer_Address, CU_ADR_ChangedAt)

FROM   stg_crm_customer s
JOIN   CU_CID_Customer_CrmId k ON k.CU_CID_Customer_CrmId = s.customer_id1
WHERE  NOT EXISTS (                                        -- skip if the latest value is the same2
         SELECT 1 FROM CU_ADR_Customer_Address a
         WHERE  a.CU_ADR_CU_ID = k.CU_ID

  1. 1The CRM ID finds the anchor. A new customer needs an anchor row and a CRM ID row first.
  2. 2The method calls a repeated identical value a restatement. Most models skip restatements, so the same address loaded twice adds nothing.

13.5Generated views and join elimination

Nobody queries attribute tables one by one. The method generates views that assemble each anchor with all its attributes, and the generator writes them for every anchor.

The latest view, such as lCU_Customer, shows each customer with the most recent value of every attribute. The point-in-time view, a function such as pCU_Customer, takes a time and shows the values valid at that time. The now view shows values as of the current time. The difference view shows every change between two times.

Listing 13.3 A simplified latest view

CREATE VIEW lCU_Customer AS
SELECT cu.CU_ID,
       cid.CU_CID_Customer_CrmId,
       nam.CU_NAM_Customer_Name,
       adr.CU_ADR_Customer_Address,
       tir.TIR_Tier
FROM   CU_Customer cu
LEFT JOIN CU_CID_Customer_CrmId cid ON cid.CU_CID_CU_ID = cu.CU_ID1
LEFT JOIN CU_NAM_Customer_Name nam
       ON nam.CU_NAM_CU_ID = cu.CU_ID
      AND nam.CU_NAM_ChangedAt = (SELECT MAX(x.CU_NAM_ChangedAt) FROM CU_NAM_Customer_Name x
                                WHERE x.CU_NAM_CU_ID = cu.CU_ID)
LEFT JOIN CU_ADR_Customer_Address adr
       ON adr.CU_ADR_CU_ID = cu.CU_ID
      AND adr.CU_ADR_ChangedAt = (SELECT MAX(x.CU_ADR_ChangedAt) FROM CU_ADR_Customer_Address x
                                WHERE x.CU_ADR_CU_ID = cu.CU_ID)
LEFT JOIN CU_TIR_Customer_Tier ct
       ON ct.CU_TIR_CU_ID = cu.CU_ID
      AND ct.CU_TIR_ChangedAt = (SELECT MAX(x.CU_TIR_ChangedAt) FROM CU_TIR_Customer_Tier x
                               WHERE x.CU_TIR_CU_ID = cu.CU_ID)
LEFT JOIN TIR_Tier tir ON tir.TIR_ID = ct.CU_TIR_TIR_ID;           -- knot: the text2
  1. 1Left outer joins on the anchor's key. Each attribute table can only add values to an anchor row, never remove or repeat it.
  2. 2The knot turns a stored tier ID into its text, so "Gold" exists once in the database.

The view looks expensive: one join per attribute. It is not, thanks to join elimination, also called table elimination. Each joined table can contribute at most one row per anchor, through a left join on its key. So when a query does not select any column of that table, the engine can prove that the join changes nothing, and skip the table entirely. A query for names reads only the anchor and the name table, however many attributes the view has.

13.6The concurrent-reliance-temporal model

So far, each attribute row says: this value was true from this changing time on. That is one clock, business time, and one implicit source. Anchor modeling has three settings for time. The uni-temporal setting, used so far, keeps changing time only. The bitemporal setting adds recording time. The concurrent-reliance-temporal setting, or CRT, goes further. It records several sources at once (concurrency), how certain each source is (reliance), and both clocks (temporal). This section defines the CRT model in full, following Lars Rönnbäck's Posits and Assertions and the anchor modeling generator's documentation.

13.6.1Posits

A posit is a statement about something, separated from anyone's opinion of it. Formally, a posit is a triple:

p = [ {(i1, r1), …, (in, rn)}, v, t ]

The first element is the dereferencing set: a set of pairs, each pairing an identity with a role. It says what the statement is about, and in what capacity. The second element, v, is a value. The third, t, is a time point: the changing time, when the value took effect. For Maria's address, a posit is:

[ {(CU 48211, address)}, "220 Bay Rd, San Jose", 2025-03-10 ]

A posit about a relationship has several pairs. Sam's ownership of Biscuit is [ {(CU 50177, owner), (PE 905, owned)}, true, 2025-09-10 ]. A posit is neither true nor false on its own. It is a candidate fact.

13.6.2Assertions

An assertion records someone's opinion of a posit. Formally, it is a predicate with four arguments:

assert(P, p, α, T)

P is the positor: the source that holds the opinion, such as the CRM or the web shop. p is the posit. α is the reliability, a real number between −1 and 1. T is the positing time: when the positor held that opinion, which in a warehouse is when the warehouse recorded it.

The reliability scale carries meaning at every point. A reliability of 1 means the positor is certain that the posit is true. A reliability of −1 means it is certain that the posit is false, which asserts the opposite. Values between express degrees of certainty. A reliability of 0 means complete uncertainty, and it is how a positor retracts an earlier assertion: it does not delete anything, it records that it no longer holds an opinion.

In the uni-temporal setting, an assertion is simply assert(p): every stored posit is taken as true, by the database, now. CRT makes the hidden arguments explicit.

13.6.3From the formal model to tables

The generator maps each CRT attribute and tie to two tables. A posit table holds the posits: a posit ID, the anchor identity, the value, and the changing time. An annex table holds the assertions about those posits: the posit ID, the positor, the positing time, and the reliability. A small table of positors lists the sources. Listing 13.4 shows the shape, simplified.

Listing 13.4 Posit and annex tables for customer addresses

CREATE TABLE CU_ADR_Customer_Address_Posit (
  CU_ADR_ID          INTEGER      PRIMARY KEY,              -- posit identity
  CU_ADR_CU_ID       INTEGER      NOT NULL REFERENCES CU_Customer,
  CU_ADR_Customer_Address VARCHAR(200) NOT NULL,          -- v
  CU_ADR_ChangedAt   DATE         NOT NULL,                 -- t, changing time
  UNIQUE (CU_ADR_CU_ID, CU_ADR_Customer_Address, CU_ADR_ChangedAt)1
);
CREATE TABLE CU_ADR_Customer_Address_Annex (
  CU_ADR_ID          INTEGER      NOT NULL REFERENCES CU_ADR_Customer_Address_Posit,
  CU_ADR_Positor     SMALLINT     NOT NULL,                 -- P
  CU_ADR_PositedAt   TIMESTAMP    NOT NULL,                 -- T, positing time
  CU_ADR_Reliability DECIMAL(3,2) NOT NULL,                -- alpha, from -1 to 12
  PRIMARY KEY (CU_ADR_ID, CU_ADR_Positor, CU_ADR_PositedAt)
);
  1. 1A posit is stored once, however many sources assert it. Two systems that agree on an address share one posit row.
  2. 2Every opinion is a new annex row. A correction is a retraction of the old posit, with reliability 0, plus an assertion of a new posit.

13.6.4Asking questions

A CRT question has three parameters: a changing time (what was true when), a positing time (according to what was recorded by when), and a positor (according to whom). The generated views take these parameters, and by default show only positive assertions, one row per identity and positor. A rule called decisiveness controls whether one positor may hold several contradicting opinions at once. A decisive positor holds one value per identity at a time.

13.8Common mistakes

Querying attribute tables directly. Hand-written joins across dozens of attribute tables are slow to write and easy to get wrong. Use the generated views, and let join elimination do its work.

Hand-writing the database code. An anchor model has many more tables than any other pattern, and their views and load logic follow strict templates. Generate them from the model.

Choosing CRT by default. Concurrency and reliability are powerful and expensive. Use uni-temporal or bitemporal settings unless sources really disagree and the business needs to see it.

Skipping knots. Storing "Gold" as text on every tier row wastes space and makes a renamed tier a mass update. Shared small value sets belong in knots.

Ignoring the engine. If the engine does not eliminate joins in the generated views, every query reads every table. Test before you build.

13.9Strengths and limits

Anchor modeling is the most change-friendly pattern in this book at the level of single attributes. A new attribute, a new relationship, or a new kind of history is always an extension. Each attribute keeps its own history, so a fast-changing value never copies slow ones. Ties are many-to-many and can be historized. The bitemporal and CRT settings record when each value was recorded, by which source, and with what certainty, which makes the pattern strong on audits.

Its limits are the number of tables and the dependence on tools. A query for many attributes joins many tables, and only an engine with join elimination keeps that fast. Identity is decided at load time, so new sources and wrong matches still cost matching work. There is no separate layer for business rules, and personal data, while neatly separated, must still be removed from an insert-only store.

Choose anchor modeling when the schema changes constantly, when attribute-level history matters, and when the team has a generator and an engine that eliminates joins. For most teams, it is the core of a layered design, with stars or wide tables on top for analysts.

Summary

  • Anchor modeling builds a warehouse in sixth normal form, so that every model change is an extension and never a modification.
  • Anchors hold identities, attributes hold one property each, ties hold relationships, and knots hold small shared value sets.
  • A strict naming convention, built from mnemonics, keeps hundreds of tables readable.
  • Loads are insert-only and per attribute, but identity is decided at load time.
  • Generated latest, point-in-time, now, and difference views assemble anchors, and join elimination keeps them fast.
  • A posit is a triple of a dereferencing set, a value, and a changing time. An assertion records a positor's reliability in a posit at a positing time. Reliability 0 is a retraction.
  • The CRT setting maps posits and assertions to posit and annex tables, and answers questions by changing time, positing time, and positor.
