Lantern's marketing team asks a question that every other model in this book makes painful: "Of the customers who bought dog food online, how many booked a grooming visit within 30 days, and how much did they spend before their next order?" In a star, the answer needs the sales fact, the grooming fact, the customer dimension, and a careful set of date comparisons between rows of different tables. In a vault, it needs links, satellites, and the same comparisons.

The activity schema is built for questions like this one. It stores everything that a customer did as rows in one narrow table, ordered by time, and answers questions with a small set of temporal joins. This chapter builds Lantern's customer stream and shows where the pattern shines and where it stops.

14.1The idea

Most patterns in this book model what things are: a customer with an address, a product in a category, an order with lines. The activity schema models what an entity did: viewed a product, completed an order, booked grooming, updated an address. Each of those is an activity, and all activities of one kind of entity go into one table, the activity stream.

Ahmed Elsamadisi created the pattern and implemented it at his company, Narrator. The public specification reached version 2.0 in December 2022. The specification's central claim is that most analytical questions about customers are questions about the order of events: what happened first, what happened before or after something else, and what happened in between. A single time-ordered table makes those questions uniform.

14.2The activity stream

The specification defines eight columns. Every activity, of every kind, uses the same eight.

Table 14.1 The columns of an activity stream

ColumnMeaningRequired
activity_idA unique ID for the activity rowYes
tsWhen the activity happened, in UTC by conventionYes
customerThe global ID of the entity. It can be empty only if the anonymous ID is setUsually
activityThe activity name, such as completed_orderYes
anonymous_customer_idA local ID used before the global ID is known, such as a web visitor IDNo
feature_jsonThe activity's own details, as key-value pairsYes
revenue_impactMoney in, or money out, in one currency for the whole streamNo
linkA URL to the source recordNo

The specification recommends naming activities as a verb and a noun from the entity's point of view, such as viewed_product, and naming streams after their entity, such as customer_stream. Three things stand out. Everything about Maria, from browsing to grooming, is in one table, in time order. Each activity's details live in feature_json, so a new detail needs no new column. And the first row has no customer, only a web visitor ID: Maria browsed before she logged in.

That last point is how the pattern handles identity. When a row carries both a customer and an anonymous_customer_id, as the autoship row does, it links the two. Earlier rows with only the anonymous ID can then be credited to Maria, and the common practice is to fill in the customer column on those older rows once the link is known.

14.3Building the stream

Each activity comes from a transformation: a query over a source that produces rows in the eight columns. The completed_order activity reads the store POS, the web shop, and the Happy Tails POS, and unions them. The groomed activity reads the grooming system. The stream is the union of all activity transformations.

Listing 14.1 The completed_order activity from the web shop

INSERT INTO customer_stream
       (activity_id, ts, customer, activity, anonymous_customer_id, feature_json, revenue_impact, link)
SELECT 'web_order_' || o.order_id,                              -- stable, unique per activity1
       o.ordered_at,
       x.customer_id,                                             -- global ID, when known
       'completed_order',
       'webshop_' || LOWER(TRIM(o.email)),                         -- local ID, prefixed by source2
       '{"order": "' || o.order_id || '", "store": "web"}',         -- engines have JSON builders
       o.total_amount,
       NULL
FROM   stg_web_order o
LEFT JOIN customer_key_map x ON x.email = LOWER(TRIM(o.email))
WHERE  NOT EXISTS (SELECT 1 FROM customer_stream s
                   WHERE s.activity_id = 'web_order_' || o.order_id);3
  1. 1A deterministic ID makes the load safe to repeat.
  2. 2The specification suggests prefixing anonymous IDs with the name of the system that issued them, so IDs from two systems never collide.
  3. 3Only new activities are inserted. Existing rows are never changed.

The specification states the pattern's one hard rule: an activity never changes. If something changes, such as an order that is later refunded, that is a new activity, refunded_order, not an update of the old row. The stream is an append-only record of events, which makes it simple to load and safe to reload.

NoteA changing attribute becomes an event too. Maria's move is not an address column that changes. It is an updated_address activity with the new city in its features. Her address on any date is the last updated_address before that date, which is exactly the kind of question the next section answers.

14.4Temporal joins

Every query on an activity stream has the same structure. A cohort activity decides the rows of the result: for example, one row per completed_order. Append activities add columns to those rows, through a relationship that says which occurrence of the append activity to use. Appending never adds or removes rows. The specification compares the cohort to a FROM clause and each relationship to a LEFT JOIN.

Table 14.3 The relationships in the specification

RelationshipWhich append occurrence it uses
First everThe customer's first, at any time
Last everThe customer's last, at any time
First beforeThe first before the cohort row
Last beforeThe most recent before the cohort row
First afterThe first after the cohort row
Last afterThe last after the cohort row
First in betweenThe first after the cohort row and before the customer's next cohort row
Last in betweenThe last in that same window
Aggregate in betweenA count or sum over that window
Aggregate beforeA count or sum over everything before the cohort row

Two relationships carry most real questions. "Last before" gives the state of something at the time of an event, such as the city where Maria lived when she ordered. "First in between" answers "what happened next, before the same thing happened again", such as whether a grooming booking followed an order before the next order.

Listing 14.2 Last before: the city at the time of each order

SELECT o.activity_id, o.ts AS order_ts,
       (SELECT a.feature_json                                  -- the latest address activity
        FROM   customer_stream a
        WHERE  a.customer = o.customer
        AND    a.activity = 'updated_address'
        AND    a.ts < o.ts                                     -- strictly before the order1
        ORDER BY a.ts DESC
        FETCH FIRST 1 ROW ONLY) AS address_then
FROM   customer_stream o
WHERE  o.activity = 'completed_order';                       -- the cohort: one row per order2
  1. 1The time comparison is the whole join condition. No dimension table, no surrogate key, no validity range.
  2. 2The cohort sets the rows. The subquery returns at most one value per row, so appending cannot multiply rows.

Listing 14.3 First in between: a grooming booking before the next order

WITH orders AS (
  SELECT customer, activity_id, ts,
         LEAD(ts) OVER (PARTITION BY customer ORDER BY ts) AS next_order_ts1
  FROM   customer_stream
  WHERE  activity = 'completed_order'
)
SELECT o.activity_id, o.ts,
       (SELECT MIN(b.ts) FROM customer_stream b
        WHERE  b.customer = o.customer
        AND    b.activity = 'booked_grooming'
        AND    b.ts > o.ts
        AND    (o.next_order_ts IS NULL OR b.ts < o.next_order_ts)) AS first_booking_between2
FROM   orders o;
  1. 1LEAD finds the customer's next order, which closes the window.
  2. 2The first booking inside the window, or nothing. The last order has an open window.

The SQL is not short, but it is always the same shape, which is why implementations generate it from three choices: cohort, append, and relationship. With one table and one time column, every question is a combination of those three choices.

14.5Journeys and funnels

The marketing question from the start of the chapter is a cohort, two appends, and a filter. The cohort is completed_order where the store is the web and the product is dog food. The first append is booked_grooming, first in between. The second is completed_order revenue, aggregate in between. A filter keeps rows where the booking happened within 30 days.

A funnel chains such appends: of customers who viewed a product, how many added it to the cart, then completed an order, then started autoship. Each step is a "first after" append on the previous step. In a star, each funnel step is a different fact table with different grain. In an activity stream, it is the same table, read again with a different activity name.

TipKeep activity names few and stable. A stream with 30 well-named activities answers more questions than one with 300 activities that differ by a channel or a flag. Put the channel and the flags in the features.

14.6What does not fit

The specification is explicit that each stream holds one kind of entity. Lantern's customer stream answers customer questions well. Several Lantern questions are not about customers.

Other entities. Payroll is about employees, stock is about products in stores, recalls are about lots. Each needs its own stream, such as employee_stream with punched_in and was_paid activities. Questions that cross entities, such as grooming revenue per groomer hour, need two streams joined, and the pattern gives no special help there.

Many-to-many relationships. Biscuit's two owners do not fit a customer-centric stream directly. Each owner can have groomed activities for Biscuit, but then a revenue total counts the visit twice, the fan-out problem from section 10.5. Either one owner gets the revenue, or a pet stream holds the visit.

Record time. The ts column is business time: when the activity happened. The specification has no load-time column. A team that needs audits adds one with an underscore prefix, which the specification lets implementations add, such as _loaded_at.

Current state. "Maria's current phones" is three temporal lookups, one per phone type, or a list in the features of an updated_phones activity. State-shaped questions are possible and less natural than event-shaped ones.

14.7Common mistakes

Updating activities. A refund that edits the original order row breaks every past answer. Add a new activity instead.

Mixing entities in one stream. Employee punches in the customer stream make every customer query filter them out, and every count wrong when someone forgets. One entity per stream.

Too many activity names. See the tip in section 14.5.

Burying the measure in the features. Revenue belongs in revenue_impact, in one currency, so every revenue question has one column to add up.

Forgetting identity stitching. Rows with only an anonymous ID are lost to customer-level questions until someone links and backfills them. Make stitching part of every load.

14.8Strengths and limits

The activity schema is the simplest pattern in this book to extend and the best at questions about sequences. A new source adds activities, not tables. A new detail goes into the features. History is natural, because every change is an event. Rules are queries over immutable activities, so old and new definitions run side by side. Simple totals, such as revenue by store and month, read one table. And deletion of a customer's data is one statement on one key.

Its limits come from its focus. It models one entity per stream, so payroll, inventory, and relationships between entities need other streams or other patterns. Identity must be resolved into one global customer column, so key conflicts still need matching work. Many-to-many data and current-state questions are awkward. Without an added column, it keeps no record time, so the audit test needs extra design.

Choose the activity schema for customer analytics, journeys, funnels, and features for models that predict behavior. Pair it with another pattern for finance, payroll, and inventory.

Summary

  • The activity schema models what an entity did, as rows of one narrow, time-ordered table per entity.
  • Every activity uses the same eight columns. Details go into feature_json, and money into revenue_impact.
  • Activities never change. A change in the world is a new activity.
  • The anonymous customer ID links identities before and after a customer is known.
  • Queries start from a cohort activity and append other activities through relationships such as last before and first in between, without adding rows.
  • Journeys and funnels are chains of appends on one table.
  • Other entities, many-to-many data, record time, and current state need extra streams, extra columns, or other patterns.
