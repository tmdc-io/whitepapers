The basic star schema from chapter 7 answers simple questions well and struggles with change. Its strip showed four Fails: attribute history, a relationship that becomes many-to-many, several values per customer, and the audit. Those failures are not the end of the dimensional story. Over three decades, dimensional modelers built a set of standard techniques for exactly these cases. This chapter teaches them, and then scores the star again with all of them in place.

The chapter stands on its own, but it uses the vocabulary of chapter 7. In short: a fact table holds one row per event at a declared grain, with numeric measures. A dimension holds the descriptive context, one row per member, with an integer surrogate key that facts point to. The grain is what one fact row means. Lantern's sales star has one row per order line, with dimensions for date, customer, product, store, promotion, and payment type.

8.1Slowly changing dimensions

Dimension values change. Maria moves. A product changes brand. A store moves to a new district. A slowly changing dimension, or SCD, is a dimension with a defined rule for each such change. The rules are numbered by type. Maria's two moves in 2025 test each one.

Maria lived at 14 Elm St in Oakland until 10 March 2025, then at 220 Bay Rd in San Jose until 2 August 2025, then at 9 Pine Ave in Sacramento. She placed order O-5001 on 14 February, O-5102 on 20 May, and O-5203 on 5 September. The question for every type is the same: which city does each order belong to?

Type 0 keeps the original value. The value never changes after the first load. It suits attributes that are fixed by definition, such as the date a customer joined the loyalty program.

Type 1 overwrites. The row always shows the current value, and all history is lost. It suits corrections of mistakes, such as a misspelled name, and values for which nobody needs history.

Type 2 adds a row. Each change creates a new dimension row, with its own surrogate key and a validity period. Facts point to the row that was valid when the event happened. This is the most widely used type, and the one that gives the star full business-time history.

Type 3 adds a column. The row keeps the current value and the previous value in two columns. It suits a planned, one-time change, such as a sales territory redesign, where reports need "old territory" and "new territory" side by side. It keeps only one step of history.

Type 4 adds a separate history table. The main dimension holds current values only, and a history table holds every past version. Queries that need history join the history table.

Type 6 combines types 1, 2, and 3. It keeps type 2 rows, and every row also carries a current-value column that is overwritten on every change. One row then answers both "what was it then" and "what is it now".

Type 5 pairs a type 1 view of a mini-dimension (section 8.2) with the base dimension, so a fact can be read with the profile that it had when it happened, or with the profile that the customer has now. Type 7 gives the fact table two foreign keys to the same dimension: a surrogate key for the version valid at the time, and a durable key, a key that stays the same for one customer across all versions, to join to the current row. Both types are rarer, and they solve the same problem as type 6 in a different shape.

Only types 2, 4, and 6 put every order in the right city. Most teams choose type 2 by default and add type 6 columns for the attributes that users also want to see as of today. Listing 8.1 shows a type 2 load in two statements: close the open row, then insert the new version.

Listing 8.1 Type 2 load for customer address

-- Step 1: close the current row of each customer whose address changed.
UPDATE dim_customer
SET    valid_to   = (SELECT s.moved_on FROM stg_customer s
                     WHERE s.customer_id = dim_customer.customer_id),
       is_current = FALSE
WHERE  is_current = TRUE
AND    EXISTS (SELECT 1 FROM stg_customer s
               WHERE s.customer_id = dim_customer.customer_id
               AND   s.address    <> dim_customer.address);1

-- Step 2: insert a new version for changed and new customers.
INSERT INTO dim_customer
       (customer_key, durable_key, customer_id, address, valid_from, valid_to, is_current)
SELECT NEXT VALUE FOR seq_customer_key,2
       COALESCE((SELECT MAX(d.durable_key) FROM dim_customer d
                 WHERE d.customer_id = s.customer_id),
                NEXT VALUE FOR seq_customer_durable),3
       s.customer_id, s.address, s.moved_on, DATE '9999-12-31', TRUE
FROM   stg_customer s
WHERE  NOT EXISTS (SELECT 1 FROM dim_customer d
                   WHERE d.customer_id = s.customer_id
                   AND   d.is_current  = TRUE
                   AND   d.address     = s.address);
  1. 1Only rows with a real change are closed. A reload of the same extract changes nothing.
  2. 2Each version gets a new surrogate key, so old facts keep pointing at the old version.
  3. 3The durable key stays the same for one customer across versions. It is what type 7 joins on, and what section 8.9 uses for deletion.

8.2Mini-dimensions

Type 2 works well for values that change a few times a year. It works badly for values that change often. Lantern recalculates every customer's loyalty tier and spending band each month. With type 2 on the customer dimension, 600,000 customers gain up to 600,000 new rows a month, each copying the name, address, and everything else.

A mini-dimension moves the fast-changing attributes into a small dimension of their own. Its rows are the combinations of values, not the customers. Lantern's dim_customer_profile holds every combination of loyalty tier (4 values), spending band (6 values), and pet count band (4 values): 96 rows in total. The fact table gets a second foreign key, customer_profile_key, set at load time to the profile that the customer had on the day of the sale.

Table 8.1 A few rows of the customer profile mini-dimension

1NoneUnder 100 USD1 pet

When Maria moves from Silver to Gold in October, the customer dimension does not change at all. New sales simply carry profile key 58 instead of 37. Old sales still carry 37. The history lives in the facts, and the mini-dimension stays tiny.

TipBand continuous values before they go into a mini-dimension. A weight of 31.4 kg has thousands of possible values. A weight band of "30 to 40 kg" has a handful, and it is what reports group by anyway.

8.3Bridge tables

A fact row has one foreign key per dimension. That works while each event has one member of each dimension. From September 2025, a Lantern pet can have two owners. A grooming visit for Biscuit belongs to Maria and to Sam. The grooming fact has one customer key, and there is no right value to put in it.

A bridge table sits between the fact and the dimension. The fact points to a group, and the bridge lists the members of each group. Biscuit's owners form group 905: Maria and Sam. The grooming fact carries owner_group_key = 905.

The weighting factor solves the next problem. If a report joins the fact through the bridge to customers and adds up revenue, each visit for Biscuit appears twice, once per owner. Total revenue doubles. Multiplying each measure by the weight shares it between the owners, so the totals stay correct. The weights in each group add up to 1.

Listing 8.2 Grooming revenue per customer, through the bridge

SELECT c.customer_name,
       SUM(g.amount_paid * b.weight) AS allocated_revenue,1
       SUM(g.amount_paid)            AS impact_revenue2
FROM   fact_grooming_appointment g
JOIN   bridge_pet_owner b ON b.owner_group_key = g.owner_group_key
JOIN   dim_customer     c ON c.customer_key    = b.customer_key
GROUP BY c.customer_name;
  1. 1The weighted sum shares each visit between its owners. Across all customers, it adds up to the true total.
  2. 2The unweighted sum answers a different question: "how much grooming revenue involved this customer?" It is useful per customer, and wrong as a grand total.

A bridge also handles Lantern's multi-active data: several phone numbers per customer, or several pets per household. The cost is real. Every query through a bridge must choose between weighted and unweighted measures, and the load must maintain the groups. Use bridges where the business truly has many-to-many data, and nowhere else.

8.4Hierarchy bridges

Chapter 7 flattened hierarchies into columns: department, category, and subcategory on each product row. That works when every branch has the same depth. Lantern's category tree is ragged. "Dog" has four levels below it, "Fish" has two, and merchandising adds levels every spring.

A hierarchy bridge stores every ancestor-descendant pair in the tree, with the distance between them. A row for "Dog" and "Dry dog food" says that one is two levels above the other. To roll up sales to any node, join the fact's product category to the bridge as the descendant, and filter on the ancestor.

Listing 8.3 All sales under the Dog node, at any depth

SELECT SUM(f.net_amount) AS dog_sales
FROM   fact_sales_line f
JOIN   dim_product p          ON p.product_key   = f.product_key
JOIN   bridge_category_tree t ON t.descendant_id = p.category_id1
JOIN   dim_category a         ON a.category_id   = t.ancestor_id
WHERE  a.category_name = 'Dog';                   -- any level below Dog, and Dog itself2
  1. 1Each product's category matches one bridge row per ancestor, including a row that pairs the category with itself at distance 0.
  2. 2Filtering on one ancestor picks each product once, so the sum is correct. Grouping by several ancestors at once double counts, because a product belongs to all of them.

8.5Role-playing dimensions

The grooming fact has four dates: booked, checked in, groomed, and paid. Each one is a foreign key to the same dim_date. A dimension that plays several roles in one fact is a role-playing dimension. Most teams create one view per role, with renamed columns, so that a query reads clearly and a report tool does not confuse the roles.

Listing 8.4 Role-playing views of the date dimension

CREATE VIEW dim_booked_date AS
  SELECT date_key AS booked_date_key, calendar_date AS booked_date,
         fiscal_month AS booked_fiscal_month
  FROM   dim_date;

CREATE VIEW dim_paid_date AS
  SELECT date_key AS paid_date_key, calendar_date AS paid_date,
         fiscal_month AS paid_fiscal_month
  FROM   dim_date;
-- One table, two meanings. A query can now group by booked month
-- and filter by paid month without aliasing dim_date twice.

8.6Junk, degenerate, and outrigger dimensions

A junk dimension holds small flags. A web order has flags: gift wrap, autoship, coupon used, first order. Each is a yes or no. Four foreign keys for four flags clutter the fact, and four columns on the fact mix descriptions into measurements. A junk dimension holds every combination of the flags, 16 rows here, and the fact carries one key to it.

A degenerate dimension has no table. The order number and the lot number describe a sale, but they have no other attributes. They stay on the fact row as plain columns, as chapter 7 showed.

An outrigger is a dimension of a dimension. Lantern's stores sit in wage zones, and each wage zone has a minimum wage history. The zone is not part of the sale. It describes the store. An outrigger is a small table that a dimension points to, such as dim_store pointing to dim_wage_zone. Used sparingly, outriggers avoid repeating large attribute sets. Used everywhere, they turn the star into a snowflake, as chapter 9 shows.

8.7Audit dimensions and bitemporal type 2

Stress test 7 asks what the company had on record on a past date. A type 2 dimension keeps business time: when Dev's pay rate was valid. It does not keep record time: when the warehouse learned the rate, or what it believed before a correction. Two techniques add record time to a star.

An audit dimension describes the load. Each fact row gets a key to dim_audit, which records the load batch, the source system, the load time, and any data quality flags. "Which sales came from the Happy Tails system, loaded after 1 June?" becomes a filter. It tells you where each row came from. It does not tell you what a dimension held on a past date.

Bitemporal type 2 adds a second pair of dates. Each dimension row carries business dates, valid_from and valid_to, and record dates, recorded_from and recorded_to. A correction never overwrites a row. It closes the old row in record time and inserts the corrected row, as in section 4.4.

Listing 8.5 The wage claim: Dev's rate on each pay date, as recorded on that date

SELECT pr.pay_date,
       e.hourly_rate     AS rate_on_record,
       e.source_system   AS recorded_by
FROM   payroll_run pr                                  -- one row per pay date
JOIN   dim_employee_bt e
  ON   e.employee_id   = 'E-1047'
 AND   e.valid_from    <= pr.period_end   AND pr.period_end < e.valid_to1
 AND   e.recorded_from <= pr.pay_date     AND pr.pay_date   < e.recorded_to2
ORDER BY pr.pay_date;
  1. 1Business time: the rate valid at the end of the pay period.
  2. 2Record time: as the warehouse knew it on the pay date, before any later correction. Without these two columns, the query can only show today's corrected view.

Bitemporal dimensions are powerful and costly. Every dimension query must choose a record date, or filter to current records, and every load must close rows in two clocks. Most teams use them only for dimensions that face audits, such as employee pay and customer consent, and keep plain type 2 elsewhere. Fact corrections follow the same idea: a correction is a reversing row and a new row, each with its own recorded date, so last month's totals can be reproduced.

8.8Aggregate tables

Lantern's sales fact gains about 38 million rows a year. Most finance reports read monthly totals by store and department. An aggregate table stores those totals in advance: one row per store, department, and fiscal month, a few hundred thousand rows a year.

An aggregate is a smaller star with the same conformed dimensions, or shrunken versions of them, such as a dim_month that holds the month-level columns of dim_date. It must be rebuilt or updated whenever the base fact changes, including late data and corrections, or its totals drift from the base. Treat aggregates as a performance tool, built from the base fact and never loaded from sources directly.

8.9Masking and deleting personal data

On 9 February 2026, Dev Patel asks Lantern to delete his customer data. In a type 2 customer dimension, Dev exists as several rows, one per version, and his name and email are copied into each. The fact table points at all of them.

The common dimensional answer has three parts. First, split personal attributes into their own small dimension or table, keyed by the durable key from section 8.1. Name, email, phone, and street address live there, once per person, not once per version. Second, to delete, replace those values with a fixed placeholder, such as "Deleted customer", or remove the row and point the durable key at a shared "Deleted" member. Facts keep their keys, so sales totals do not change. Third, keep employees in a separate dimension, so that Dev's pay records stay untouched.

Listing 8.6 Mask one customer's personal data

UPDATE dim_customer_pii
SET    customer_name = 'Deleted customer',
       email         = NULL,
       phone         = NULL,
       street        = NULL,
       deleted_on    = DATE '2026-02-16'
WHERE  durable_key   = 7731;                            -- Dev's customer durable key1
  1. 1One statement, one row, because personal data lives once per person. Without the split, the same change must find every type 2 version and every aggregate or extract that copied them.
WarningPersonal data also hides in places that the dimension design does not control: aggregate tables, extracts sent to other teams, and backups. A deletion process must list every place that copies customer attributes.

8.11Strengths and limits

With these techniques, the star keeps full business-time history, handles many-to-many relationships, absorbs fast-changing attributes, and can answer audit questions where it has to. It does all of this while the main tables keep their simple shape: one fact, a ring of dimensions, one-hop joins. That combination is why the star remains the most common serving pattern for analysts.

The limits are the price of keeping that shape. Each technique is a separate piece of design and load code, and the toolkit is large. Identity is still decided while data loads, so a new source and a wrong match still mean changes to dimensions and reloads of facts. Bitemporal history is possible but expensive, so most stars keep record time only in a few places. Relationships still live in the fact grain, so a change in cardinality still touches the fact table.

Choose the full dimensional toolkit when analysts are the main users and the business needs history and many-to-many data in the same easy shape. Add each technique only where a real question needs it.

Summary

  • Slowly changing dimensions have numbered types. Type 2 adds a row per change and is the default. Types 1, 3, 4, and 6 suit specific needs, and types 5 and 7 are rarer variants.
  • Mini-dimensions hold fast-changing attributes as a small set of combinations, so the main dimension stays stable.
  • Bridge tables connect a fact to many members of a dimension. Weighting factors keep totals correct.
  • Hierarchy bridges store every ancestor-descendant pair, so ragged trees can roll up at any level.
  • Role-playing, junk, degenerate, and outrigger dimensions handle repeated dates, small flags, bare identifiers, and dimensions of dimensions.
  • Audit dimensions record where rows came from. Bitemporal type 2 records what the warehouse believed on a past date.
  • Aggregate tables speed up common reports and must stay in step with the base fact.
  • Personal data split by durable key makes deletion a single, targeted change.
  • With these techniques, the star's four Fails become one Good and three Costly results.
