Every spring, Lantern's merchandising team reorganizes the product catalog. In 2025, cat litter moves out of the Cat department into a new Home and Hygiene department, together with odor sprays and cleaning supplies. In the star from chapter 7, the department name is copied onto every product row. About 1,800 rows change, and with type 2 history, 1,800 new versions appear in the product dimension overnight.

The snowflake schema is the dimensional answer for cases like this. It keeps the star's fact tables, and normalizes the dimensions, so that each department exists once. This chapter shows how it works, what it costs, and why its strip looks almost the same as the star's.

9.1The idea

A snowflake schema is a star schema in which some dimensions are split into normalized tables. The fact table does not change. It still has one row per event, with surrogate keys and measures. The change is in the dimensions. Instead of one wide dim_product with brand, category, and department columns, there is dim_product, which points to dim_category, which points to dim_department. Drawn out, the branches look like a snowflake.

In the vocabulary of chapter 3, a star's dimension is denormalized: the department depends on the category, not on the product, so it is a transitive dependency stored on the product row. A snowflake moves each dimension toward third normal form. Each level of a hierarchy becomes its own table, with its own key, and stores its own attributes once.

9.2The Lantern snowflake

Figure 9.1 shows Lantern's sales schema as a snowflake. The fact table in the middle is the same as in chapter 7. The product and store dimensions are now chains.

Not every dimension needs to be snowflaked. Date and customer stay as wide, flat tables, because their hierarchies are shallow and stable. Product and store are chained, because merchandising reorganizes products every year, and operations redraws districts and wage zones. A model where only some dimensions are snowflaked is common, and it is the sensible default.

Listing 9.1 The product chain

CREATE TABLE dim_department (
  department_key  INTEGER     PRIMARY KEY,
  department_name VARCHAR(60) NOT NULL                -- 'Home and Hygiene'
);
CREATE TABLE dim_category (
  category_key    INTEGER     PRIMARY KEY,
  category_name   VARCHAR(60) NOT NULL,               -- 'Cat litter'
  department_key  INTEGER     NOT NULL REFERENCES dim_department1
);
CREATE TABLE dim_product (
  product_key     INTEGER     PRIMARY KEY,
  sku             VARCHAR(20) NOT NULL,
  product_name    VARCHAR(120),
  brand           VARCHAR(60),
  category_key    INTEGER     NOT NULL REFERENCES dim_category2
);
  1. 1Moving cat litter to Home and Hygiene changes this one column on one category row.
  2. 2Products point to their category, not to their department. They do not change when the department changes.

The snowflake's advantage is real, and it is narrow. It shows up when a level of a hierarchy changes, and grows with the number of members below that level. For a store dimension with 97 rows, the difference hardly matters. For a product dimension with 25,000 rows and a yearly reorganization, it matters every spring.

9.3Loading, and history across the chain

Chained dimensions load from the top down: departments first, then categories, then products, then facts. Each level looks up the surrogate key of the level above, just as a fact looks up its dimension keys in a star. The load order is longer, and a failure at the top stops everything below it.

History needs one more decision. Suppose both dim_category and dim_product are type 2. When cat litter moves to a new department, the category gets a new version. Do the products now point to the new category version, or the old one?

There are two answers, and both are used. If products point to the category's surrogate key, every product in the category needs a new version too, to point at the new category version. The cascade brings back the 1,800 new rows that the snowflake was meant to avoid. If products point to the category's durable key, the key that stays the same across versions, products do not change. A query then picks the category version valid on the sale date, with a date-range join. That keeps the snowflake's advantage, and makes every historical query longer.

WarningDecide the history rule for each link in a chain before the first load. A chain where some links use surrogate keys and others use durable keys gives answers that depend on which level a report starts from.

9.4Querying through join chains

Every label at the end of a chain costs one join per level. Listing 9.2 answers a department question in the snowflake.

Listing 9.2 Net sales by department and fiscal month

SELECT dp.department_name, d.fiscal_month,
       SUM(f.net_amount) AS net_sales
FROM   fact_sales_line f
JOIN   dim_product    p  ON p.product_key     = f.product_key
JOIN   dim_category   c  ON c.category_key    = p.category_key1
JOIN   dim_department dp ON dp.department_key = c.department_key
JOIN   dim_date       d  ON d.date_key        = f.date_key
WHERE  d.fiscal_year = 2025
GROUP BY dp.department_name, d.fiscal_month;
  1. 1Two extra joins compared with a star, where department_name is a column on dim_product. Each one is cheap, but an analyst must know the chain.

Many teams hide the chains behind views. A view v_product joins the three product tables and presents one flat row per product, like a star dimension. Analysts query the view, and the storage stays normalized. If query speed matters, the view can be stored as a table and refreshed after each load. At that point, the team has a star for querying and a snowflake for loading, which is a reasonable place to end up.

9.5Snowflakes, outriggers, and stars

The three shapes form a range. A star repeats every hierarchy level on the dimension row. A star with an outrigger (section 8.6) splits off one secondary table where it saves a lot, such as the wage zone of a store. A snowflake normalizes whole hierarchies.

Table 9.1 Choosing a dimension shape

SituationShapeWhy
Shallow, stable hierarchyStarFew repeated values, and they rarely change
One large attribute group shared by many rowsStar with outriggerStores the group once without chaining everything
Deep hierarchy that is reorganized oftenSnowflakeOne row changes instead of thousands
Ragged hierarchy of varying depthStar with a hierarchy bridgeFixed chains cannot hold varying depth (section 8.4)
Users query with a tool that needs flat tablesStar, or snowflake behind viewsUsers see flat rows either way

9.6Common mistakes

Snowflaking by habit. Normalizing every dimension because normalization feels correct adds joins everywhere and saves almost nothing. Snowflake only where a hierarchy is large and changes.

Snowflaking the date dimension. A date dimension with separate month, quarter, and year tables saves a few kilobytes and adds joins to almost every query. Keep dates flat.

Mixing history rules along a chain. See the warning in section 9.3. Choose surrogate or durable keys per link, on purpose.

Exposing the chains to every user. Analysts who must learn every chain write slower queries and make more mistakes. Put flat views on top.

9.7Strengths and limits

The snowflake's strength is the one in the exercise: a change to a hierarchy level touches one row. It also stores each shared value once, which means fewer copies to correct, and fewer copies of personal data to delete. When the dimension tables are very large and their hierarchies are reorganized often, those savings are real.

On the twelve stress tests, the snowflake behaves almost exactly like the star, because it shares the star's facts, its load order, and its techniques from chapter 8. It matches customers on the way in, so new sources and wrong matches cost the same. It is scored with the same bridges and bitemporal dimensions, and those cost a little more on a chain. And it is slower to query, because every label sits at the end of a chain. No stress test measures hierarchy reorganization, so the snowflake's one clear advantage does not appear in the strip. Read the strip with that in mind.

Choose a snowflake for the few dimensions with large, frequently reorganized hierarchies, and keep the rest of the model as a star. Put flat views on top for users.

Summary

  • A snowflake schema keeps the star's facts and normalizes some dimensions into chains, one table per hierarchy level.
  • Its main benefit is that a change to a hierarchy level changes one row instead of every row below it.
  • Chains load from the top down, and each link needs a history rule: surrogate keys cascade versions, durable keys need date-range joins.
  • Every label at the end of a chain costs one join per level. Flat views hide the chains from users.
  • Use a star for shallow, stable hierarchies, an outrigger for one large shared group, a snowflake for large hierarchies that change, and a hierarchy bridge for ragged trees.
  • On the twelve stress tests, the snowflake scores like the star, slightly worse on fast queries. Its real advantage, cheap reorganizations, is outside the tests.
