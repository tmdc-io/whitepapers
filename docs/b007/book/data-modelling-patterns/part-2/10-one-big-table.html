Lantern's store managers use a dashboard that shows sales by hour, product, and promotion. It has to answer in under a second, and it is built by a team that does not want to learn join paths. The team asks for one table with everything on it: one row per sale line, with the product name, the category, the store, the customer's tier, the promotion code, and about a hundred other columns.

That request describes the pattern called one big table, or OBT. It is the simplest pattern in this book to query, and the one with the least modeling in it. This chapter shows when that simplicity is the right choice, and the specific traps that come with it.

10.1The idea

One big table takes denormalization to its end. Instead of a fact table with dimensions around it, there is a single wide table. Every attribute that a user can filter or group by is copied onto every row. A Lantern sales OBT has one row per order line and about 120 columns.

For a long time, this was considered a mistake. Row-oriented databases store each row together, so a wide table makes every query read every column, and repeated text values waste space. Two changes made the pattern practical in the 2010s. Column-oriented storage keeps each column separately, so a query that reads 5 of 120 columns reads only those 5. And columns with many repeated values compress very well, so "Dog food" repeated 10 million times costs little. Wide tables became cheap to store and fast to scan, and their simplicity won many teams over.

The pattern is rarely the whole warehouse in a mature team. It is usually the last layer: built from a star, a normalized core, or a vault, for one group of users. But some small teams build it straight from sources and use nothing else. This chapter covers both, and its scorecard treats one big table as it stands, built from sources, because that is when its limits show.

10.2What one row means

A wide table still has a grain, and it matters even more than in a star, because there is no other table to hold anything at a different grain. Lantern's sales_wide has one row per order line. Every column must make sense for one order line.

Attributes from a coarser grain are safe to copy. Each order line has one order date, one store, and one customer. The trouble comes from attributes at a finer or crossing grain. An order has a shipping fee, and an order line does not. A customer has several pets. Putting either one on an order-line row breaks the grain, and section 10.5 shows what happens.

TipBuild one wide table per grain, not one wide table for the whole company. Lantern has sales_wide at order-line grain, orders_wide at order grain for shipping and payment, and grooming_wide at appointment grain.

10.3Building a wide table

A wide table is always derived. It is the result of a query that joins events to all their context. Listing 10.1 builds sales_wide from Lantern's star. The same query works from a normalized core or a vault, with different joins.

Listing 10.1 Build sales_wide from the star

INSERT INTO sales_wide
SELECT f.order_id || '-' || CAST(f.order_line_no AS VARCHAR(4)) AS order_line_id,
       d.calendar_date   AS order_date,
       d.fiscal_month,
       c.customer_name,  c.city AS customer_city,  c.loyalty_tier,1
       p.product_name,   p.brand, p.category, p.department,
       s.store_name,     s.city AS store_city,     s.region,
       pr.promo_code,
       f.lot_number,
       f.quantity, f.net_amount, f.cost_amount
FROM   fact_sales_line f
JOIN   dim_date      d  ON d.date_key      = f.date_key
JOIN   dim_customer  c  ON c.customer_key  = f.customer_key2
JOIN   dim_product   p  ON p.product_key   = f.product_key
JOIN   dim_store     s  ON s.store_key     = f.store_key
JOIN   dim_promotion pr ON pr.promotion_key = f.promotion_key
WHERE  d.calendar_date >= DATE '2025-05-01'
AND    d.calendar_date <  DATE '2025-06-01';                -- one month partition3
  1. 1Every attribute is copied as a plain column. The customer's city here is the one on the dimension row that the fact points to.
  2. 2Inner joins are safe because the star has Unknown rows for every missing key. Built straight from sources, these must be outer joins, or rows disappear.
  3. 3The build runs per month, so a change to one month rebuilds only that month.

There are three ways to keep a wide table up to date. A full rebuild drops and recreates the table each night. It is simple and always consistent, and it grows slower as history grows. A partition rebuild recreates only the date partitions that changed, as in Listing 10.1. It is the common choice. An incremental merge updates only the rows whose inputs changed. It is the fastest, and the hardest to get right, because a change to one dimension row can touch millions of wide rows.

WarningA change to a dimension attribute is a change to every wide row that copied it. When merchandising renames a category, a partition rebuild must rebuild every partition that contains products of that category, which is usually all of them.

10.4History in a wide table

Each value on a wide row is frozen at build time. Whether it shows history depends on what the build query read.

If the build joins to a type 2 star, as in Listing 10.1, each row copies the version that was valid on the order date. Maria's February order shows Oakland, and her May order shows San Jose. The wide table has business-time history for free, because the star did the work.

If the build reads current values, such as today's CRM table, every row shows today's value. All of Maria's orders show Sacramento. Many teams add both: customer_city_at_order and customer_city_now, which is type 6 from section 8.1, flattened into columns.

Record time is harder. A rebuild replaces rows, so the table never shows what it held before. If that matters, teams keep snapshot tables: a full copy of the wide table, or of its changed partitions, stamped with the build date. Snapshots answer "what did the dashboard show on 1 March", at the cost of storing the table many times over.

10.5The fan-out trap

The most dangerous mistake in a wide table is a row that means two things. In September 2025, Biscuit gets a second owner. The team that maintains grooming_wide wants owner names on each visit. The obvious build joins visits to owners, and each of Biscuit's visits becomes two rows, one per owner. Every revenue total that includes Biscuit now counts his visits twice. This is fan-out: a join that multiplies rows, silently.

There are two safe ways to add many-valued data to a wide table.

Allocation columns keep one row per owner, but add a share column, such as owner_share = 0.5, and use amount_paid * owner_share in every sum. This is the bridge weight from section 8.3, copied onto the row. It works only if every user knows to multiply.

Array columns keep one row per visit and store the owners as a list in a single column, such as owners = ['Maria Lopez', 'Sam Ortiz']. Sums stay correct, because the row count does not change. Questions about one owner need a function that looks inside the list. ANSI SQL has array types since SQL:1999, and most analytical engines support them, with different syntax.

The same trap applies to Maria's three phone numbers, a product's several suppliers, and any other many-valued attribute. Put only values with exactly one value per row at its grain into a wide table. Everything else needs an array, an allocation, or its own wide table at its own grain.

10.6Wide tables for dashboards and machine learning

Two kinds of user benefit most from wide tables.

Dashboards issue many small queries with filters on a few columns, and they need answers in under a second. A wide table, partitioned by date, lets each query scan a few columns of a few partitions, with no joins to plan. Lantern's store dashboard reads sales_wide for the current and previous week only.

Machine learning works on wide tables by nature. A model that predicts which customers will lapse needs one row per customer with many features: days since last order, average basket, number of pets, loyalty tier, share of autoship. That table is a wide table at customer grain, usually called a feature table. It must be built with care for time: each feature must use only data that was known at the prediction date, or the model learns from the future. The as-of queries in section 4.5 are the tool for that.

10.7Common mistakes

One table for everything. A single wide table at order-line grain cannot hold order-level shipping fees or customer-level pet counts without breaking its sums. Build one wide table per grain.

Joining in many-valued data. See section 10.5. Check the row count before and after every join in the build. If it grows, the grain is broken.

Using the wide table as the only record. A wide table that is built from sources and has no layer underneath cannot be rebuilt after a mistake, and cannot show history it did not copy. Keep the raw sources, or a model underneath, from which the table can be rebuilt.

Copying personal data by default. Every wide row that carries a name or email is one more place to delete it. Copy personal attributes only into the tables that need them.

Inner joins from sources. Without Unknown rows, an inner join drops every sale whose customer or product is missing. Use outer joins and fill in placeholders.

10.8Strengths and limits

One big table is the easiest pattern to use. Any person who can filter a spreadsheet can query it, any dashboard tool can read it, and on column-oriented engines it is fast. It needs little design, it is quick to build, and it gives machine learning the shape it already wants. As the last layer on top of a better model, it costs little, because it can always be rebuilt from the layer below.

As the whole warehouse, its limits are serious. Every attribute is a copy, so every change to a source, a rule, or a match means a rebuild, and every copy of personal data must be found. The grain cannot hold many-valued data without arrays or allocation. And because each rebuild replaces rows, the table keeps no record of what it showed before. Choose one big table for dashboards, self-service analysis, and machine learning features, built from a model underneath that can rebuild it. Use it alone only when the sources are few, history matters little, and the team is small.

Summary

  • One big table copies every attribute onto every row. Column-oriented storage and compression made the pattern practical.
  • A wide table still has a grain. Build one wide table per grain, and copy only values that have one value per row at that grain.
  • Wide tables are derived. Full, partition, and incremental rebuilds keep them up to date, and a dimension change can touch every partition.
  • Business-time history comes from the build's source. Record-time history needs snapshot tables.
  • Joining many-valued data causes fan-out, which multiplies rows and sums. Allocation columns and array columns avoid it.
  • Wide tables suit dashboards and machine learning features, built with as-of logic so that features do not use future data.
  • As the last layer, one big table is cheap and useful. As the whole warehouse, it makes every change a rebuild and keeps no record of past states.
