In section 7.6.1, the finance director asked for product sales and grooming revenue per store. The answer needed care: never join two fact tables directly, total each one separately, then join the totals. An analyst who knows that writes two subqueries. An analyst in a self-service tool, who drags "net sales" and "grooming revenue" onto one report, gets numbers that are several times too large, and no warning.

The unified star schema is a design for exactly that analyst. It puts one table, a bridge, in the middle of all the stars, so that any combination of facts and dimensions can be queried in one simple query without double counting. This chapter builds the bridge for Lantern and shows when it is worth its size.

15.1The idea

Francesco Puppini proposed the unified star schema with Bill Inmon in the 2020 book The Unified Star Schema: An Agile and Resilient Approach to Data Warehouse and Analytics Design. The idea keeps the star's tables, facts and dimensions, and changes how they connect. Instead of each fact joining its own dimensions, every table joins one central table, the bridge. Practitioners often call it the Puppini bridge.

The bridge is built with UNION ALL, not with joins. It stacks one block of rows per table, so it never multiplies rows. And every table hangs off the bridge by a many-to-one join, one hop away. Those two properties together are what remove the traps that multi-fact queries fall into.

NoteThis pattern sits in the serving layer, like the star. It needs the same dimension design as a star, including the techniques in chapter 8. What it changes is the query layer on top.

15.2Three traps

The fan trap. A table with a measure joins to a table on its "many" side, and the measure repeats. Lantern's web orders have a shipping fee on the order header. Joining headers to order lines to show fees by product repeats each fee once per line. A sum of the fee is then too large by the number of lines.

The chasm trap. Two fact tables share a dimension, and a query joins both to it. Each store has many sales rows and many grooming rows. The join pairs every sales row with every grooming row of the same store, and both sums grow. This is the trap from section 7.6.1, and the one that self-service tools fall into most often.

The loop. A table can be reached by two paths, and the paths mean different things. A sale points to the store where it happened. A customer points to their home store. "Sales by store" through the sale and "sales by store" through the customer are two different reports, and a tool that picks a path silently picks a meaning.

A star schema avoids these traps through discipline: drill across, choose paths explicitly, keep measures at their grain. The unified star schema avoids them through structure.

15.3How the bridge works

The bridge has one column that names the table each row comes from, usually called stage, and one key column per table in the model, such as _key_sales, _key_store, and _key_date. Each table contributes one block of rows, one row per row of the table. A block fills in its own key, plus the keys of every table that it reaches through many-to-one relationships. All other key columns stay empty.

Table 15.1 shows a few bridge rows for the Oakland store. A sales row fills in its sale key, and the store, date, product, and customer that the sale points to. A grooming row fills in its own key, and its store, date, and customer. A store row fills in only the store key. The empty cells are the reason the bridge is safe: a sales row has no grooming key, so joining the grooming fact to it adds nothing.

15.4Building the Lantern bridge

The bridge is a query over the existing star tables. Listing 15.1 builds it for two facts and two dimensions. A real bridge has one block for every table in the model.

Listing 15.1 The bridge, built with UNION ALL

CREATE TABLE bridge AS
SELECT 'Sales'      AS stage,
       f.sale_line_key AS _key_sales,  CAST(NULL AS VARCHAR(20)) AS _key_grooming,1
       f.store_key  AS _key_store,  f.date_key AS _key_date,  f.customer_key AS _key_customer
FROM   fact_sales_line f
UNION ALL
SELECT 'Grooming', NULL, g.appointment_id,
       g.store_key, g.paid_date_key, g.customer_key2
FROM   fact_grooming_appointment g
UNION ALL
SELECT 'Store',    NULL, NULL, s.store_key, NULL, NULL
FROM   dim_store s3
UNION ALL
SELECT 'Customer', NULL, NULL, NULL, NULL, c.customer_key
FROM   dim_customer c;
  1. 1Each block fills in its own key and leaves the keys of other facts empty, so facts never meet in one row.
  2. 2A fact block carries the keys of every dimension it points to. For grooming, the paid date plays the role of "the date" in this bridge.
  3. 3Dimension blocks let a report show stores with no sales and no grooming at all, which an inner join from a fact would hide.

The bridge has about as many rows as all the tables together, so for Lantern it is dominated by the sales fact: around 38 million rows a year. It holds only keys, which compress well, and it must be rebuilt, or appended to, after each load.

NoteLoops are resolved in the bridge, too. If a report needs both the store where a sale happened and the customer's home store, the bridge gives them two key columns, such as _key_store and _key_home_store, each joined to its own role-playing view of dim_store, as in section 8.5. Each path then has a name, and a report picks a meaning on purpose.

15.5Querying through the bridge

Every query has the same shape: start from the bridge, left-join the tables you need on their keys, group, and add up. Because each bridge row joins at most one row of each table, sums are always correct, for one fact or for several.

Listing 15.2 Product sales and grooming revenue per store, in one query

SELECT st.store_name,
       SUM(f.net_amount)  AS product_sales,
       SUM(g.amount_paid) AS grooming_revenue
FROM   bridge b
LEFT JOIN fact_sales_line           f  ON f.sale_line_key  = b._key_sales1
LEFT JOIN fact_grooming_appointment g  ON g.appointment_id = b._key_grooming
LEFT JOIN dim_store                 st ON st.store_key     = b._key_store
LEFT JOIN dim_date                  d  ON d.date_key       = b._key_date
WHERE  b.stage IN ('Sales', 'Grooming')2
AND    d.fiscal_year = 2025 AND d.fiscal_quarter = 2
GROUP BY st.store_name;
  1. 1On a sales row, the grooming join finds nothing, and on a grooming row, the sales join finds nothing. No row is ever paired with another fact's row.
  2. 2The stage filter is optional here. It skips dimension-only rows, which carry no measures and no date.

Drilling across and the bridge both give the right totals. The difference is who must know the rule. Drilling across asks the analyst, or the tool, to write two queries and join their results. The bridge builds the rule into the data, so a simple query is also a correct one.

15.6Stars, galaxies, and self-service tools

A unified star schema is a galaxy (section 7.7.1) with a different join layer. The facts and dimensions, their grain, their slowly changing dimensions, and their conformed keys are the same. Everything in chapters 7 and 8 still applies.

The bridge helps most where users build their own reports. A self-service tool that sees a galaxy must either forbid multi-fact reports or risk chasm traps. A tool that sees one bridge, with every table one hop away, can let users combine any fields freely. Its authors argue that this makes the model easier to extend, too: a new fact is a new block in the bridge, and existing queries keep working.

It helps least where users write SQL and know the drill-across rule, and where most questions touch one fact. Then the bridge is a large extra table that buys little.

15.7Common mistakes

Joining a fact to a dimension directly. One shortcut join outside the bridge brings back the chasm trap. Every table joins the bridge only.

Filling in keys that a table does not reach many-to-one. A grooming block that carries product keys, by guessing which products were used, puts fan-out back into the bridge. A block carries only keys that its rows determine exactly.

Inner joins from the bridge. An inner join to one fact removes the rows of every other stage. Use left joins.

Forgetting the rebuild. The bridge is derived. Late facts, corrections, and new dimension rows must reach it, or reports disagree with the facts.

15.8Strengths and limits

The unified star schema makes multi-fact questions safe by structure. Any combination of facts and dimensions is one simple query, with correct totals, and loops become named paths. That is a real gain for self-service tools and for teams whose users combine processes often, such as sales with grooming, or labor hours with revenue.

On the twelve stress tests, it behaves like the star from chapter 8, because it is built from the same tables and the same techniques. It still decides identity on the way in, still fixes relationships in the fact grain, and still needs bitemporal dimensions for audits. It adds a bridge that is as long as all the facts together and must be rebuilt after each load. Its one clear advantage, safe multi-fact queries, is not one of the twelve tests, so the strip below looks almost the same as the star's. Read it with that in mind.

Choose the unified star schema when users build their own reports across several business processes, and when double counting has already cost trust. Otherwise, a galaxy with the drill-across rule does the same work with less.

Summary

  • The unified star schema keeps a star's facts and dimensions, and connects all of them through one central bridge.
  • It targets three traps: the fan trap, the chasm trap, and loops.
  • The bridge has a stage column and one key column per table. Each table adds one block of rows with UNION ALL, filling in its own key and the keys it reaches many-to-one.
  • Every table joins the bridge with a left join, one hop away, so multi-fact sums are correct in one simple query.
  • Loops become separate key columns with role-playing dimensions.
  • The bridge is as long as all the facts together and must be rebuilt after each load.
  • On the twelve stress tests, it scores like the star. Its advantage, safe multi-fact queries for self-service, lies outside the tests.
