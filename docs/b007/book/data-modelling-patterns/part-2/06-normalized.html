Lantern's CFO has a simple complaint. Finance says Lantern has 600,000 customers. Marketing says 640,000. The loyalty team says 580,000. Each team counts from its own system, with its own idea of who a customer is, and every board meeting starts with an argument about whose number is right.

The normalized warehouse was designed for exactly this problem. It builds one integrated record of the whole company, in which every customer, product, and store exists once, under one definition. Every report then counts from the same rows. This chapter builds that record for Lantern, and shows what it costs.

6.1The idea

Bill Inmon defined the data warehouse in Building the Data Warehouse in 1992 as a store with four properties. The definition is still the clearest statement of what this pattern is for.

Subject-oriented. Data is organized by business subject, such as customer, product, and employee, not by the system that produced it. There is no "CRM area" and "web shop area". There is one customer area.

Integrated. Every source is translated into one set of definitions, codes, and keys on the way in. A customer from the CRM and the same customer from the web shop become one row.

Time-variant. The warehouse keeps history. Each value can be related to the time when it was true.

Non-volatile. Loaded data is not edited by users. The warehouse changes only through its loads.

Inmon's model for storing this record is a normalized one, in third normal form (section 3.6). Each fact is stored once, so it can never disagree with itself. Departments do not query the core directly. Each one gets a dependent data mart: a star or summary built from the core, for its own questions. "Dependent" means that the mart has no other source. If finance and marketing both count customers from marts built on the same core, they get the same number.

The corporate information factory

Inmon later described the full architecture around the core as the corporate information factory. It has sources, a staging and integration layer, the normalized enterprise warehouse, an operational data store for current operational reporting (section 6.7), and dependent marts for each department. The shape matches the layers in Figure 1.1, with the normalized model as the integrated core.

6.2The building blocks

A normalized core uses ordinary relational tables, designed with care. Five kinds of table carry most of the model.

Entity tables hold one row per business thing: customer, product, store, employee. Their keys are core surrogate keys, because the core must give one key to a thing that sources identify in different ways.

Event tables hold one row per business event: sales_order, order_line, grooming_visit, timesheet_punch. They point to the entities involved.

Associative tables hold many-to-many relationships, one row per pair: product_promotion, and, after September 2025, pet_owner.

Effective-dated child tables hold values that change over time, one row per version: customer_address, employee_pay_rate, product_price. This is where the warehouse becomes time-variant. Each has valid_from and valid_to, as in section 4.3.

Reference tables hold the company's agreed codes and their meanings: country, payment_type, product_category, wage_jurisdiction. Every source code is translated into a reference code during integration.

NoteOnly values that the business needs history for get an effective-dated child table. A customer's date of birth goes on the customer row. Their address, loyalty tier, and marketing consent each get a child table, because questions depend on the value at a past date.

6.4Integration on the way in

The defining work of a normalized warehouse happens before data reaches the core. Each source extract lands in a staging area. A set of integration steps then cleans it, translates its codes, matches its keys to core keys, and only then writes it into the core.

The central tool for keys is the key cross-reference table. It records, for each source key, the core key that it maps to. When the web shop sends an order for maria.lopez@example.com, the load looks up that email in the cross-reference, finds core party 48211, and writes the order for party 48211.

Listing 6.1 Load web orders through the cross-reference

INSERT INTO sales_order (order_id, party_id, store_id, channel, order_date)
SELECT s.order_id,
       x.party_id,                                  -- core key, not the email1
       st.store_id,
       'WEB',
       s.order_date
FROM   stg_web_order s
JOIN   key_xref x
  ON   x.source_system = 'WEBSHOP'
 AND   x.source_key    = UPPER(TRIM(s.email))           -- same cleaning as the match rule2
JOIN   store st ON st.store_code = 'WEB'
WHERE  NOT EXISTS (SELECT 1 FROM sales_order o WHERE o.order_id = s.order_id);3
  1. 1Every core table speaks in core keys. Source keys live only in the cross-reference.
  2. 2The cleaning here must match the cleaning in the match rule exactly. A missing TRIM makes Maria a stranger.
  3. 3An inner join on the cross-reference means that orders from unmatched customers wait in staging. A separate step matches new keys, or creates new parties, before the next load.

Effective-dated tables need one more step. When the CRM sends Maria's new address, the load closes the current row and inserts a new one, like a type 2 dimension. Listing 6.2 shows the pattern in two statements.

Listing 6.2 Load a changed address into an effective-dated table

-- Close the open row when the address changed.
UPDATE customer_address
SET    valid_to = (SELECT s.moved_on FROM stg_crm_customer s
                   JOIN key_xref x ON x.source_system = 'CRM' AND x.source_key = s.customer_id
                   WHERE x.party_id = customer_address.party_id)
WHERE  valid_to = DATE '9999-12-31'
AND    party_id IN (SELECT x.party_id FROM stg_crm_customer s
                  JOIN key_xref x ON x.source_system = 'CRM' AND x.source_key = s.customer_id
                  JOIN customer_address a ON a.party_id = x.party_id
                  WHERE a.valid_to = DATE '9999-12-31' AND a.address <> s.address);1

-- Insert the new version.
INSERT INTO customer_address (party_id, address, valid_from, valid_to)
SELECT x.party_id, s.address, s.moved_on, DATE '9999-12-31'
FROM   stg_crm_customer s
JOIN   key_xref x ON x.source_system = 'CRM' AND x.source_key = s.customer_id
WHERE  NOT EXISTS (SELECT 1 FROM customer_address a
                   WHERE a.party_id = x.party_id AND a.valid_to = DATE '9999-12-31'
                   AND a.address = s.address);2
  1. 1An update in place. After it runs, the table no longer shows that the row was ever open-ended, or when the warehouse learned of the move. This is the record-time loss from section 4.6.
  2. 2Inserts a version only if the open row does not already hold this address, so a repeated load adds nothing.

On 1 June 2025, the Happy Tails customers arrive. The integration step matches each one to a core party by phone and last name, or creates a new party. Run the match, then discover the mistake, then fix it.

The exercise shows the main cost of integrating on the way in. The match is a decision, and the core stores only its result. When the decision is wrong, the fix is not a new row. It is a search for every row that the wrong decision touched, in every subject area, followed by updates. The next pattern chapters show two other approaches: the star makes the same decision in its dimensions, and Data Vault stores the sources' own keys first and decides later.

6.5The party pattern

Dev Patel is a groomer at the Oakland store and a loyalty customer. A model with separate customer and employee tables stores him twice, with two names, two addresses, and no link between them. When Dev changes his address, one copy goes stale. When he asks Lantern to delete his customer data, nothing tells the warehouse that the same person's pay records must stay.

The party pattern solves this. A party is any person or organization that the business deals with. Each party has one row in a party table, with the facts about the person: name, date of birth, contact points. Each way that the party relates to the business is a role, in its own table: customer_role, employee_role, supplier_role. Dev is one party with two roles.

Table 6.2 Dev Patel as one party with two roles

tableparty_idrole details
party51907name Dev Patel, address and phone in effective-dated child tables
employee_role51907employee E-1047, groomer, Oakland store, hired 2021-05-03

The pattern pays off twice in the stress tests. Dev's address changes once, for both roles. And his deletion request in February 2026 has a clear scope: end the customer role and remove or mask the data that only that role needs, while the employee role and its pay records stay. The pattern is common in normalized enterprise models, and its ideas reappear in Data Vault as separate hubs and links.

WarningDo not let the party table become a dumping ground. Values that belong to a role, such as a loyalty tier or a job title, go in the role table or its children. Only facts about the person or organization itself belong on party.

6.6Querying the core, and dependent marts

The core is correct and complete, and it is not pleasant to query. Listing 6.3 answers a common finance question directly from it.

Listing 6.3 Net sales by the customer's city at the time of each order

SELECT c.city_name,
       SUM(l.quantity * l.unit_price - l.discount) AS net_sales
FROM   sales_order o
JOIN   order_line l        ON l.order_id  = o.order_id
JOIN   customer_address a  ON a.party_id  = o.party_id
                          AND a.valid_from <= o.order_date
                          AND o.order_date <  a.valid_to          -- address valid that day1
JOIN   city c              ON c.city_id   = a.city_id
WHERE  o.order_date >= DATE '2025-04-01' AND o.order_date < DATE '2025-07-01'
GROUP BY c.city_name;
  1. 1A range join on the effective dates. It is correct, but every analyst must remember to write it, and get the half-open interval right.

So analysts rarely write queries like this one. Instead, the warehouse team builds dependent marts: stars, summary tables, or flat extracts, refreshed from the core after each load. For example, a finance mart holds a sales star with the customer's city at the time of the order already resolved. Chapter 7 describes the star shape itself. The difference here is the source: a dependent mart is built only from the core, so all marts share the core's definitions and keys.

Listing 6.4 Refresh a customer dimension in a dependent mart

INSERT INTO mart_finance.dim_customer
       (customer_key, party_id, customer_name, city, region, valid_from, valid_to)
SELECT ROW_NUMBER() OVER (ORDER BY p.party_id, a.valid_from),1
       p.party_id, p.name, c.city_name, r.region_name, a.valid_from, a.valid_to
FROM   party p
JOIN   customer_role cr     ON cr.party_id = p.party_id      -- customers only
JOIN   customer_address a   ON a.party_id  = p.party_id
JOIN   city c               ON c.city_id   = a.city_id
JOIN   region r             ON r.region_id = c.region_id;2
  1. 1The mart creates its own surrogate keys. This listing rebuilds the dimension in full after the table is emptied, which is the simplest refresh. Larger marts refresh only changed rows.
  2. 2The mart flattens the chain from party to city to region into one row per address version, so its users never see the joins.

6.7The operational data store

Some questions need integrated data but only the current state, and they need it fast. A store manager wants today's grooming bookings with the customer's loyalty tier and any unpaid balance, across systems, refreshed every few minutes. The core is integrated, but it is loaded nightly and full of history.

An operational data store, or ODS, fills that gap. It is integrated like the core, but it holds only current values, and it is refreshed often. It uses the same cross-reference and reference codes, so its numbers match the warehouse. It is not a replacement for the core, because it keeps no history.

6.8Common mistakes

Modeling the whole company before delivering anything. An enterprise model that tries to define every subject before the first mart ships can take a year to show value. Build the core one subject area at a time, and ship a mart for each.

Copying source rules into the core. A source's constraints are not the company's. The CRM's one owner per pet was a screen design, and the first version of Lantern's core copied it as an owner_id column. Model relationships as the business sees them, and use associative tables where the "one" side might become "many".

Forgetting record time. Effective-dated tables answer "what was true then", not "what did we know then". If audits matter, add load timestamps and keep closed rows unchanged, or use a bitemporal design (section 4.4).

Letting marts read from sources. A mart that pulls one extra column straight from a source system is no longer dependent, and its numbers will drift from the others. Add the column to the core first.

Hiding the cross-reference. Matching decisions are business decisions. Keep the cross-reference visible, with how and when each match was made, so that people can review it and fix it.

6.9Strengths and limits

The normalized warehouse is the pattern for one version of the truth. Every customer, product, and store exists once, under one definition, and every mart counts from the same rows. Normalization makes the core consistent by construction, because a fact stored once cannot disagree with itself. Many-to-many data, such as phones and pets, fits naturally in child tables. And because personal data lives in one place, deletion has a clear target.

Its costs come from deciding everything on the way in. Every new source waits for the integration work, and every matching mistake is stored as a fact. Many values keep only their current state unless someone added an effective-dated table in advance. Update-in-place loads lose record time, so the core cannot show what it believed on a past date. And the core is hard to query, so the pattern needs marts, which add their own copies and their own loads.

Choose the normalized warehouse when consistency across the company matters most, when sources are few and stable, and when there is a team to own the enterprise model. It is also a strong base for an operational data store.

Summary

  • The normalized warehouse is subject-oriented, integrated, time-variant, and non-volatile, in Inmon's definition.
  • Its core is in third normal form, so each fact is stored once. Departments query dependent marts built only from the core.
  • Entity, event, associative, effective-dated, and reference tables carry most of the model.
  • Integration happens on the way in. A key cross-reference maps every source key to one core key.
  • The party pattern stores each person once, with customer and employee as roles.
  • An operational data store gives integrated current data, refreshed often, without history.
  • The pattern gives consistency and clear ownership of data, at the cost of slow integration, hard-to-undo matches, and lost record time.
