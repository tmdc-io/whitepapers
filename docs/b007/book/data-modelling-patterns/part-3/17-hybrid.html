Hybrid architectures

The grid in chapter 16 shows that no pattern is good at everything. The core patterns, Data Vault, anchor modeling, and the normalized warehouse, absorb change and keep records well, and are hard to query. The serving patterns, the star, one big table, the activity schema, and the unified star schema, are easy to query and less tolerant of change. Most real warehouses therefore use one pattern underneath and others on top, each where its strip is strong.

17.1Why combine

The layers from section 1.4 exist because the work in each layer is different. The core must take in every source, keep every version, and survive every change for years. The serving layer must answer questions quickly in the shape that people think in, and it can be rebuilt whenever that shape changes. A pattern optimized for one job is usually poor at the other.

Combining patterns lets each layer use the pattern that suits its job. The price is more than one set of tables, and loads that move data from one layer to the next. Section 17.5 counts that price.

17.2Records and decisions

The most useful line in any layered warehouse separates records from decisions. Figure 17.1 draws it.

Below the line, data is a record: append-only where possible, with sources and arrival times. Above the line, data is a set of decisions: which keys are one customer, what an active customer is, how overtime is computed, and what shape a report needs. Decisions change. If the record below never changes, every layer above can be rebuilt with the new decision, and old reports can be reproduced with the old one.

The patterns differ in where they put the line. A raw Data Vault sits clearly below it, and its business vault sits above. A normalized core straddles it: it records, but it also matches keys and overwrites corrections on the way in. A star built straight from sources sits above it entirely, which is why it struggles with tests that need the record, such as the audit.

TipA persistent staging area is the cheapest way to get a record below the line. Keep every source extract, append-only, with its load time. Even a warehouse made only of stars can then rebuild any star from the original data.

17.3Five common combinations

Persistent staging with stars. The lightest hybrid. A landing layer keeps every extract, and stars are built from it. It suits a small team with few sources. It keeps the most important vault property, a permanent record, without hubs and links. If sources multiply later, a vault can be built from the persistent stage, because the history is already there.

Normalized core with dependent marts. Inmon's own architecture, from chapter 6. It suits companies that want one consistent integrated record, with stable sources and an enterprise modeling team.

Data Vault with stars and wide tables. A raw vault and a business vault in the core, information marts as stars for analysts, and wide tables for dashboards and machine learning. It suits many changing sources and audit pressure, and it needs automation. Chapter 12 describes it.

Anchor model with generated views and stars. An anchor core for a schema that changes constantly, its latest and point-in-time views for technical users, and stars on top for analysts. It suits fast-evolving domains with a team that owns the generator.

A star warehouse with an activity stream beside it. Stars for finance and operations, and a customer activity stream for marketing and product analytics, both fed from the same staging. It suits companies whose customer questions are about sequences and journeys. A unified bridge can be added on top of the stars where self-service users combine processes.

17.5The costs of combining

More tables and more loads. Every layer is another set of tables and another set of loads, in a fixed order. A failure in the core delays every layer above it.

Copies of data. Serving layers copy values from the core. Each copy must be refreshed, and each copy of personal data must be deleted on request.

Two vocabularies. Core tables and serving tables use different names and shapes. The team must keep a clear map from one to the other, or analysts and engineers stop understanding each other.

Latency. Data reaches users only after it passes through every layer. Questions that need fresh data, such as today's grooming bookings, need a faster path, such as the operational data store from section 6.7.

None of these costs is a reason to avoid layers. Each is a reason to add a layer only when a stress test that matters to the business needs it.

Summary

  • Core patterns absorb change and keep records. Serving patterns answer questions. Most warehouses combine them.
  • The most important line separates records, which are kept, from decisions, which can be rebuilt.
  • A persistent staging area is the cheapest record, and it makes any later layer rebuildable.
  • Common combinations are persistent staging with stars, a normalized core with marts, a vault with stars and wide tables, an anchor core with views and stars, and stars with an activity stream.
  • Every layer adds tables, loads, copies, vocabulary, and latency. Add a layer only for a test that matters.
