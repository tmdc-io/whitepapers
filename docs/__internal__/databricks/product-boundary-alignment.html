Databricks and the Product Boundary

How DataOS coexists with the Databricks estate

DataOS productizes data assets for audited consumption by humans, BI, and agents. Databricks has built a genuinely complete asset platform. This doc maps how far it has spread, and where audited consumption still has no home.

1 · How far the Databricks ecosystem has spread

the reality of what Databricks offers off the shelf
Lakehouse foundation

Delta Lake on cloud object storage as the open-format spine, with Iceberg interop (UniForm, managed Iceberg, Iceberg REST catalog) so the same tables serve engines beyond Databricks. Photon runs as the vectorized execution engine underneath most workloads.

Open formats are the strategic posture: the storage layer is deliberately not a lock-in point; the catalog and compute above it are.

Ingestion & pipelines

Lakeflow Connect ships managed connectors for SaaS apps and databases (Salesforce, Workday, ServiceNow, SQL Server via CDC, plus file sources like Google Drive and SharePoint), fully managed on serverless, governed by UC, with auto-retry and cursor recovery.

Declarative pipelines (formerly DLT) cover streaming and batch: AUTO CDC handles SCD1/2 and out-of-order events without watermark code, and an incremental engine keeps materialized views current while reprocessing only changed data. The framework is upstreamed into Apache Spark 4.1 itself.

Between managed connectors (copy the data in) and federation (query it where it lives; see Governance), most non-Databricks estates are reachable one way or the other. Asset bundles give dev/staging/prod code lifecycle with CI/CD.

Governance

ABAC policies went GA in May 2026 alongside governed tags and agentic data classification. Policies attach once at catalog or schema level, match assets via tags, inherit downward, and cover tables, materialized views, and streaming tables, including tables that don't exist yet.

Classification runs as an agent that scans catalogs and auto-tags PII, financial data, and credentials, feeding tags straight into enforcement. Fail-closed by design. Tags now enforce, not just label.

UC's reach extends beyond Databricks-resident data: Lakehouse Federation mounts external systems (Snowflake, BigQuery, SQL Server, PostgreSQL, Oracle, Teradata, Redshift, Salesforce Data 360) as foreign catalogs with governed, read-only access, query pushdown, and table-level controls, so external estates appear inside the same governance pane without moving data.

Quality & prediction

Data Quality Monitoring runs anomaly detection across every table in a schema with zero configuration: per-table learned models predict next-commit freshness and expected row-count ranges, health indicators surface in Catalog Explorer, and alerts fire on deviation (both 2026).

Pipeline-time expectations live in DLT; DQX supplies rule libraries. The platform doesn't just store your data; it forms expectations about it.

Semantics

Metric views went GA April 2026: YAML measures and dimensions with star/snowflake joins, window measures, parameters, and composable measures, plus agent metadata (synonyms, display names) tuned for Genie accuracy. Served to BI over DirectQuery with automatic query rewrites.

The spec is being open-sourced into Apache Spark. Databricks is betting its semantic format becomes the industry's.

Discovery

Discover, Domains, and Subdomains (public preview 2026): an internal marketplace of tables, dashboards, notebooks, metric views, Genie agents, and apps organized by business area rather than technical location, with AI-powered recommendations from usage and lineage signals.

Certification and deprecation flags apply to nearly every asset type: catalogs, models, dashboards, Genie spaces, notebooks.

AI stack

Agent Bricks is a full agent platform, now GA: Knowledge Assistants, Supervisor Agents with on-behalf-of auth validating every fetch against the user's UC permissions, custom agents, MCP-native tool access with a built-in governed tool catalog, persistent agent memory on Lakebase, and frontier-model routing (including Claude Code and Cursor) through one API.

Genie One is GA and acts through MCP, not just answers.

Genie Ontology (preview) is the depth play: a two-feed context graph (curated UC semantics plus knowledge auto-extracted from your queries, dashboards, pipelines, and 50+ connected apps including Slack, Jira, Google Drive, SharePoint, and Salesforce), ranked by OntoRank. Genie reads your Jira tickets and shared drives, not just your tables.

Lakebase

A managed Postgres tier inside the platform: the OLTP leg the lakehouse never had. Serves operational apps, holds agent memory for Agent Bricks, receives reverse-ETL'd serving data synced from Delta tables, and exposes schemas directly as REST endpoints via the Data API.

Transactional and analytical estates under one vendor, one governance model.

Compute

Eight primitives (all-purpose clusters, job clusters, SQL warehouses, serverless, pipeline compute, model serving, vector search, Lakebase), converging on serverless including GPU.

REST access to the warehouse via the Statement Execution API. No semantic or GraphQL API.

Read the table as one system and the conclusion is hard to avoid. Done right, this covers the full breadth of human and agentic consumption.

Data gets in from almost anywhere. SaaS connectors, CDC from operational databases, files from shared drives, streams. Or it stays where it lives and gets mounted through federation. Either way, it lands in open formats any engine can read.

Then the platform takes over. One catalog governs everything, with policies that enforce themselves on tables that don't exist yet. Quality models watch the data without being configured. Semantics carry business meaning into BI and into agents through Genie.

And consumption runs the full range. Analysts in SQL. Dashboards. Applications over REST, operational apps on Postgres. Agents with governed identity, tools, memory, and a context graph that reads the company's Jira and shared drives.

Here's the honest bottom line: a small dedicated platform team can stand up a complete data platform substrate on this, ingestion to agent, without ever leaving one vendor's documentation.

That's the starting position for everything that follows. The substrate exists. The real question is what it's organized around (assets and queries) and what that organizing principle can't express.

2 · The gaps, from a productization angle

What DataOS brings is one idea: the data product is a managed object with a lifecycle.

A product in DataOS is a single artifact. Contract, semantics, quality rules, owner, version, consumers: declared together, not scattered across a catalog, a pipeline repo, and a wiki.

The lifecycle runs the whole arc. Declare the promise. Classify every change against it. Breaking changes ship as new versions while the old one keeps serving. Consumers are registered, notified, and migrated on their own schedule. Retirement happens when observed consumption hits zero, not when someone remembers.

And consumption is audited by construction: every read, human or dashboard or agent, flows through a versioned contract, so "what was promised, to whom, and who approved the change" always has a one-line answer.

Databricks manages assets superbly. Nothing below manages the promise. Each gap that follows is one place where that difference shows up in production.

2.1  Quality is statistical, not contractual

Mechanism

DQ monitoring learns what a table usually looks like and flags deviation. Useful, and structurally incapable of the judgment that matters: it cannot distinguish an intended change from a broken one, because intent is not observable in data. Intent exists only as a declared promise plus a diff against it. Call that missing judgment change classification: given a proposed change, decide whether it violates what consumers were promised (breaking, new major version) or not (compatible, ships). Classification requires three inputs no monitor has: a contract to diff against, the column-level lineage of the change itself, and a verdict that gates release.

Real-world break

An engineer redefines total_amount from gross to net. Row counts normal, freshness normal, nulls normal: every predictive monitor scores the table healthy while finance under-reports revenue. The expensive breaks are precisely the ones statistics can't see.

Cost

Decisions made on wrong numbers, senior-weeks of archaeology, and the slow one: each silent incident teaches the business to re-verify the data team's numbers, un-earning self-service.

Why it holds

Learned models see distributions; permissions-to-change see promises. Closing this requires contracts as platform objects, which is the object-model problem in 2.4, not a monitoring feature.

DataOS

Declared invariants and contract checks run as promotion gates per product; change classification is computed at plan time, before review.

Demo hook

Scene: orders product live, DQ monitoring on, finance dashboard on top.

Show: two changes. A column rename ships as a minor: monitors green, dashboard fine. Then the discount redefinition: monitors still green, but the plan blocks it as breaking.

Land: "Your monitors saw both and said nothing. Only the contract knew the difference."

2.2  Changes have no consumer-facing lifecycle

Mechanism

Bundles version code; git versions transformations; ALTER is instant and in-place on views, metric views, and tags. The entire change apparatus serves the person making the change. Nothing performs change classification (2.1) on behalf of the people depending on it: no contract diff, no v2 serving beside v3, no notice period.

Real-world break

The change above ships through green CI: code review checks Spark, tests check the transformation, validate checks YAML, expectations check nulls. Every gate examines the factory; none examines the promise. Three weeks later, "who approved this?" has no answer, because approval-of-a-promise was never an object in the system.

Cost

Incident cost plus audit cost: for regulated consumers, a number without an approval trail is a finding, not a feature.

Why it holds

Consumer-facing lifecycle means serving two versions of the same logical asset simultaneously and refusing valid SQL DDL that breaks a promise. Both contradict how the catalog and engine treat assets today; this is a platform posture, not a missing endpoint.

DataOS

The product is the promise: versioned contracts, breaking changes forced to new majors, previous versions served through their own environments until observed consumption reaches zero.

Show: v2 keeps serving. Finance stays pinned. Then ask both systems: who approved this? Git blame and a Slack hunt on one side. A one-line release record on the other.

Land: "A 3 a.m. debugging session becomes a calendar invite."

2.3  Consumers are invisible

Mechanism

Lineage records reads, not reliances. It cannot distinguish a production dependency from an exploratory query, shows external readers as opaque service principals, and captures nothing about which properties of a column a reader assumed. There is no registry, no blast-radius computation, no notification path.

Real-world break

Of three real consumers, the producer knows one. The mobile API reading over JDBC through a service principal is invisible; nobody checks lineage before a change anyway, because lineage is where you go after something breaks.

Cost

Every change carries unknown blast radius, so teams either move slow (change review theater) or break things (and pay 2.1's bill).

Why it holds

A real consumer registry requires consumption to flow through a product boundary that registration can gate. UC's model is open grants on securables; any principal with SELECT reads however it likes. Registration without a boundary is a wiki.

DataOS

Consumers are registered objects tied to observed consumption; blast radius is computed, notification is a lifecycle step, and access flows through the product.

2.4  No product object

Mechanism

The catalog's unit is the securable: table, view, function. Nothing binds N tables plus semantics plus quality rules into one versioned unit with an owner, an SLA, and consumers. Audited consumption has no unit to audit.

What Databricks calls a "data product"

The label exists in three places; none is a lifecycle object:

The UC product page: "own and publish high-quality data products." Marketing noun. The features underneath are domains, Discover, and certification.

Databricks Marketplace: the closest thing to a real product object: a listing bundles tables, volumes, models, and notebooks, delivered as a read-only catalog via Delta Sharing to entitled consumers. But it's an external commerce construct: no versioned contract, no change classification, no consumer notification, and no internal equivalent.

Domains + Discover: internally, a "product" is a governed tag plus a certification boolean. Grouping and trust signals, no lifecycle.

Notice the pattern: the external case got a product primitive because commerce forced it. A listing can't be transacted without defined contents and entitlements. Internal consumption never had a forcing function, so the primitive was never built.

Real-world break

"Customer 360" exists as tribal knowledge spread over four tables, two metric views, and a wiki page. Which version a consumer is on, what it guarantees, and who owns it are questions with no queryable answer. And when the buyer says "Marketplace has data products," the accurate response is: for data you sell to other companies, yes; for data your teams promise each other, no.

Cost

Discovery-and-trust stays a social process (weeks of finding, asking, verifying per consumer), and every governance answer must be assembled from fragments at audit time.

Why it holds

A composite lifecycle object contradicts the securable-per-asset foundation everything else (grants, lineage, ABAC, Discover) is built on. Retrofitting it is a rewrite of the catalog's object model. And the forcing-function history says it plainly: Databricks builds product primitives where transactions demand them. Internal promises don't transact, so they don't get primitives.

DataOS

Audited consumption is the internal forcing function, and DataOS ships the primitive it forces: the product manifest: contract, semantics, ports, owner, consumers in one artifact, one lifecycle. Discover becomes the storefront our products surface in.

Demo hook

Scene: ask both systems: show me customer_360.

Show: four tables, two metric views, a wiki tab. No answer for version, guarantee, owner, consumers. The manifest answers all four on one screen.

Land: "Every audit question becomes a lookup."

The four gaps above are about the promise: declaring it, changing it, and knowing who relies on it. The two below are about consumption: what agents can trust, and what serving costs.

2.5  Semantics are ranked, not warranted

Mechanism

Genie Ontology extracts knowledge from queries, dashboards, and 50+ apps and ranks competing definitions by authority (OntoRank). Ranking picks the likeliest meaning of "revenue"; nothing versions it, guarantees it, or notifies anyone when it drifts. Ranking a definition is not verifying the number computed from it.

Real-world break

An agent inherits 2.1's silent semantic shift at machine speed: it doesn't file a confused Slack message like an analyst, it produces confident wrong answers at volume, under a certified-looking source. OBO auth answers "may this agent see this row"; nothing answers "what may this agent rely on."

Cost

Security review becomes the AI bottleneck (no artifact states what an agent may rely on), and the industry outcome Gartner predicts: 40% of enterprises demoting or decommissioning agents by 2027 over governance gaps found in production.

Why it holds

A learned graph is probabilistic by design; warranting context requires the contract objects of 2.4 plus the lifecycle of 2.2. Also: Ontology ingests from everywhere but serves the Genie family; an open, warranted context API for any agent is a different product with a different buyer.

DataOS

Contract-grounded context served to any agent: each dataset carries a machine-readable statement of meaning, guarantee, and freshness: the artifact the security reviewer signs.

Demo hook

Scene: same revenue question, two agents, before and after the silent shift.

Show: the raw-side agent keeps answering. Confidently wrong. The contract-side agent serves correct v2 or flags the change.

Land: "The agent never got suspicious. The contract did."

2.6  Everything meters through their compute

Mechanism

Governed answers require the DBSQL engine: metric views are DirectQuery-only (import mode breaks semantics), Statement Execution runs per-call on a warehouse under one principal, Lakebase serving requires materializing data into it. There is no semantic API (measures by name over REST/GraphQL with tenant context) and no layer deciding which reads shouldn't hit compute at all. And there's a second meter: text-to-SQL agents burn tokens ingesting schemas and retrying failed queries. Metered API spend nobody budgets, scaling with usage.

Real-world break

Who queries changes everything: humans in dozens per day, dashboard tiles in thousands, agents in millions. Near-identical reads, each billing the meter again. The consumption curve inflects exactly when the customer succeeds at AI.

Cost

The DBSQL line becomes the AI tax; embedded and agent workloads also inherit seconds-scale latency and a shared-service-principal security model that reopens what OBO solved.

Why it holds

Serving governed answers without the meter is revenue-negative. A vendor does not ship a feature whose success shrinks its own consumption line. This gap is economic, which makes it the most durable of the six.

DataOS

In-flight dedup collapses concurrent identical queries into one execution; result reuse serves repeated reads without touching the engine; work-avoided metrics make the saving provable per workload, not asserted. Semantic serving over APIs with tenant-aware security, compute pushed down only when work is genuinely new.

Freshness is stated, not hidden: cached answers serve at each product's declared freshness tolerance; fresh or long-tail queries pass through live, with dedup still applied. And agents send small JSON metric queries instead of generating SQL: no schema ingestion, near-zero retries, the token meter flattens with the compute meter.

Demo hook

Scene: a dashboard with a dozen tiles plus a chatty agent, run against both paths.

Show: the DBU meter climbing on one side. The work-avoided counter on the other. Same numbers everywhere. Then the token counts: schema-and-retry loops versus small JSON queries.

Land: "The cheapest query is the one that never runs."

3 · Where DataOS is relevant

the map and the posture

The one-liner

DataOS is the system of record for intent. Contracts declare what's promised, change classification judges every change against the promise, and audited consumption follows, for humans, BI, and agents alike.

Coexistence posture

Their features are our substrate, not our competition.

We import metric views; a year of customer modeling becomes an on-ramp, not a moat. Their tables are our inputs. Their engines run our compute: we push work down, we don't replace it.

We respect their ABAC as the enforcement plane. On top of it, we offer simpler, semantic-shaped REST and GraphQL APIs, governed separately or inclusively, whichever the customer's security model calls for. The filter lives in the layer, not the prompt.

And we offer business-user-friendly discovery of data products, with APIs to build custom experiences on top.

Where a customer already runs DataOS on another engine, Databricks is an extension of a working blueprint, not a new bet.
