Databricks and the Product Boundary

How DataOS coexists with the Databricks estate

DataOS productizes data assets for audited consumption by humans, BI, and agents. Databricks has built a genuinely complete asset platform. This doc maps how far it has spread, and where audited consumption still has no home.

1 · How far the Databricks ecosystem has spread

the reality of what Databricks offers off the shelf
Lakehouse foundation

Delta Lake on cloud object storage as the open-format spine, with Iceberg interop (UniForm, managed Iceberg, Iceberg REST catalog) so the same tables serve engines beyond Databricks. Photon runs as the vectorized execution engine underneath most workloads.

Open formats are the strategic posture: the storage layer is deliberately not a lock-in point; the catalog and compute above it are.

Ingestion & pipelines

Lakeflow Connect ships managed connectors for SaaS apps and databases (Salesforce, Workday, ServiceNow, SQL Server via CDC, plus file sources like Google Drive and SharePoint), fully managed on serverless, governed by UC, with auto-retry and cursor recovery.

Declarative pipelines (formerly DLT) cover streaming and batch: AUTO CDC handles SCD1/2 and out-of-order events without watermark code, and an incremental engine keeps materialized views current while reprocessing only changed data. The framework is upstreamed into Apache Spark 4.1 itself.

Between managed connectors (copy the data in) and federation (query it where it lives; see Governance), most non-Databricks estates are reachable one way or the other. Asset bundles give dev/staging/prod code lifecycle with CI/CD.

Governance

ABAC policies went GA in May 2026 alongside governed tags and agentic data classification. Policies attach once at catalog or schema level, match assets via tags, inherit downward, and cover tables, materialized views, and streaming tables, including tables that don't exist yet.

Classification runs as an agent that scans catalogs and auto-tags PII, financial data, and credentials, feeding tags straight into enforcement. Fail-closed by design. Tags now enforce, not just label.

UC's reach extends beyond Databricks-resident data: Lakehouse Federation mounts external systems (Snowflake, BigQuery, SQL Server, PostgreSQL, Oracle, Teradata, Redshift, Salesforce Data 360) as foreign catalogs with governed, read-only access, query pushdown, and table-level controls, so external estates appear inside the same governance pane without moving data.

Quality & prediction

Data Quality Monitoring runs anomaly detection across every table in a schema with zero configuration: per-table learned models predict next-commit freshness and expected row-count ranges, health indicators surface in Catalog Explorer, and alerts fire on deviation (both 2026).

Pipeline-time expectations live in DLT; DQX supplies rule libraries. The platform doesn't just store your data; it forms expectations about it.

Semantics

Metric views went GA April 2026: YAML measures and dimensions with star/snowflake joins, window measures, parameters, and composable measures, plus agent metadata (synonyms, display names) tuned for Genie accuracy. Served to BI over DirectQuery with automatic query rewrites.

The spec is being open-sourced into Apache Spark. Databricks is betting its semantic format becomes the industry's.

Discovery

Discover, Domains, and Subdomains (public preview 2026): an internal marketplace of tables, dashboards, notebooks, metric views, Genie agents, and apps organized by business area rather than technical location, with AI-powered recommendations from usage and lineage signals.

Certification and deprecation flags apply to nearly every asset type: catalogs, models, dashboards, Genie spaces, notebooks.

AI stack

Agent Bricks is a full agent platform, now GA: Knowledge Assistants, Supervisor Agents with on-behalf-of auth validating every fetch against the user's UC permissions, custom agents, MCP-native tool access with a built-in governed tool catalog, persistent agent memory on Lakebase, and frontier-model routing (including Claude Code and Cursor) through one API.

Genie One is GA and acts through MCP, not just answers.

Genie Ontology (preview) is the depth play: a two-feed context graph (curated UC semantics plus knowledge auto-extracted from your queries, dashboards, pipelines, and 50+ connected apps including Slack, Jira, Google Drive, SharePoint, and Salesforce), ranked by OntoRank. Genie reads your Jira tickets and shared drives, not just your tables.

Lakebase

A managed Postgres tier inside the platform: the OLTP leg the lakehouse never had. Serves operational apps, holds agent memory for Agent Bricks, receives reverse-ETL'd serving data synced from Delta tables, and exposes schemas directly as REST endpoints via the Data API.

Transactional and analytical estates under one vendor, one governance model.

Compute

Eight primitives (all-purpose clusters, job clusters, SQL warehouses, serverless, pipeline compute, model serving, vector search, Lakebase), converging on serverless including GPU.

REST access to the warehouse via the Statement Execution API. No semantic or GraphQL API.

Read the table as one system and the conclusion is hard to avoid. Done right, this covers the full breadth of human and agentic consumption.

Data gets in from almost anywhere. SaaS connectors, CDC from operational databases, files from shared drives, streams. Or it stays where it lives and gets mounted through federation. Either way, it lands in open formats any engine can read.

Then the platform takes over. One catalog governs everything, with policies that enforce themselves on tables that don't exist yet. Quality models watch the data without being configured. Semantics carry business meaning into BI and into agents through Genie.

And consumption runs the full range. Analysts in SQL. Dashboards. Applications over REST, operational apps on Postgres. Agents with governed identity, tools, memory, and a context graph that reads the company's Jira and shared drives.

Here's the honest bottom line: a small dedicated platform team can stand up a complete data platform substrate on this, ingestion to agent, without ever leaving one vendor's documentation.

That's the starting position for everything that follows. The substrate exists. The real question is what it's organized around (assets and queries) and what that organizing principle can't express.

2 · The gaps, from a productization angle

What DataOS brings is one idea: the data product is a managed object with a lifecycle.

A product in DataOS is a single artifact. Contract, semantics, quality rules, owner, version, consumers: declared together, not scattered across a catalog, a pipeline repo, and a wiki.

The lifecycle runs the whole arc. Declare the contract. Classify every change against it. Breaking changes are stopped at plan time and ship only with explicit consent and a version bump. Registered consumers hear about the change before it lands, in the channels they already work in: email, Slack, Teams, webhooks. Retirement is a deliberate, notified act, not a quiet deletion.

And consumption is audited by construction: every read, human or dashboard or agent, flows through a versioned contract, so "what was declared, to whom, and who approved the change" always has a one-line answer.

Databricks manages assets superbly. Nothing below manages the contract. Each gap that follows is one place where that difference shows up in production.

2.1  Quality is statistical, not contractual

Mechanism

DQ monitoring learns what a table usually looks like and flags deviation. Useful, and structurally incapable of the judgment that matters: it cannot distinguish an intended change from a broken one, because intent is not observable in data. Intent exists only as a declaration plus a diff against it. Call that missing judgment change classification: given a proposed change, decide whether it violates what the contract declared to consumers (breaking, new major version) or not (compatible, ships). Classification requires three inputs no monitor has: a contract to diff against, the column-level lineage of the change itself, and a verdict that gates release.

Real-world break

A performance PR pre-aggregates a scanned-item cargo table to pallet grain: one GROUP BY, MAX() on the text columns so the schema holds. Totals reconcile to the kilo and every monitor stays green, while the dangerous-goods declaration downstream now attributes a full pallet's weight to a hazmat code that belongs to one 90 kg item. The expensive breaks are precisely the ones statistics can't see. (Part 4 runs this exact scenario end to end.)

Cost

Decisions made on wrong numbers, senior-weeks of archaeology, and the slow one: each silent incident teaches the business to re-verify the data team's numbers, un-earning self-service.

Why it holds

Learned models see distributions; permissions-to-change see contracts. Closing this requires contracts as platform objects, which is the object-model problem in 2.4, not a monitoring feature.

DataOS

Declared invariants and contract checks run as promotion gates per product; change classification is computed at plan time, before review.

2.2  Changes have no consumer-facing lifecycle

Mechanism

Bundles version code; git versions transformations; ALTER is instant and in-place on views, metric views, and tags. The entire change apparatus serves the person making the change. Nothing performs change classification (2.1) on behalf of the people depending on it: no contract diff, no consent gate, no notice period.

Real-world break

The change above ships through green CI: code review checks Spark, tests check the transformation, validate checks YAML, expectations check nulls. Every gate examines the factory; none examines the contract. Three weeks later, "who approved this?" has no answer, because approval-of-a-contract was never an object in the system.

Cost

Incident cost plus audit cost: for regulated consumers, a number without an approval trail is a finding, not a feature.

Why it holds

Consumer-facing lifecycle means two things a catalog doesn't do: refusing a valid change because a contract forbids it, and notifying people who never touched the code. Both contradict how the catalog treats assets today: an ALTER either has permissions or it doesn't, and the set of people who care is recorded nowhere. This is a platform posture, not a missing endpoint.

DataOS

The product is the contract: versioned, breaking changes blocked at plan time and shipped only with explicit consent, consumers notified through their channels before the change lands. The version history is the audit trail: what changed, who consented, who was told.

2.3  Consumers are invisible

Mechanism

Lineage records reads, not reliances. It cannot distinguish a production dependency from an exploratory query, shows external readers as opaque service principals, and captures nothing about which properties of a column a reader assumed. There is no registry, no blast-radius computation, no notification path.

Real-world break

Of three real consumers, the producer knows one. The mobile API reading over JDBC through a service principal is invisible; nobody checks lineage before a change anyway, because lineage is where you go after something breaks.

Cost

Every change carries unknown blast radius, so teams either move slow (change review theater) or break things (and pay 2.1's bill).

Why it holds

A real consumer registry requires consumption to flow through a product boundary that registration can gate. UC's model is open grants on securables; any principal with SELECT reads however it likes. Registration without a boundary is a wiki.

DataOS

Consumers are registered objects tied to observed consumption; blast radius is computed, notification is a lifecycle step, and access flows through the product.

2.4  No product object

Mechanism

The catalog's unit is the securable: table, view, function. Nothing binds N tables plus semantics plus quality rules into one versioned unit with an owner, an SLA, and consumers. Audited consumption has no unit to audit.

What Databricks calls a "data product"

The label exists in three places; none is a lifecycle object:

The UC product page: "own and publish high-quality data products." Marketing noun. The features underneath are domains, Discover, and certification.

Databricks Marketplace: the closest thing to a real product object: a listing bundles tables, volumes, models, and notebooks, delivered as a read-only catalog via Delta Sharing to entitled consumers. But it's an external commerce construct: no versioned contract, no change classification, no consumer notification, and no internal equivalent.

Domains + Discover: internally, a "product" is a governed tag plus a certification boolean. Grouping and trust signals, no lifecycle.

Notice the pattern: the external case got a product primitive because commerce forced it. A listing can't be transacted without defined contents and entitlements. Internal consumption never had a forcing function, so the primitive was never built.

Real-world break

"Customer 360" exists as tribal knowledge spread over four tables, two metric views, and a wiki page. Which version a consumer is on, what it guarantees, and who owns it are questions with no queryable answer. And when the buyer says "Marketplace has data products," the accurate response is: for data you sell to other companies, yes; for data your teams commit to each other, no.

Cost

Discovery-and-trust stays a social process (weeks of finding, asking, verifying per consumer), and every governance answer must be assembled from fragments at audit time.

Why it holds

A composite lifecycle object contradicts the securable-per-asset foundation everything else (grants, lineage, ABAC, Discover) is built on. Retrofitting it is a rewrite of the catalog's object model. And the forcing-function history says it plainly: Databricks builds product primitives where transactions demand them. Internal contracts don't transact, so they never got a primitive. Notice the asymmetry: their semantic format is becoming a standard (metric views into Spark), but their product metadata (Domains, certification, Ontology) has no standard shape at all. We emit the standards for exactly the layer they don't have.

DataOS

Audited consumption is the internal forcing function, and DataOS ships the primitive it forces: the product manifest: contract, semantics, ports, owner, consumers in one artifact, one lifecycle. Discover becomes the storefront our products surface in.

The four gaps above are about the contract: declaring it, changing it, and knowing who relies on it. The two below are about consumption: what agents can trust, and what serving costs. The last is about operating: keeping the contract over time.

2.5  Semantics are ranked, not warranted

Mechanism

Genie Ontology extracts knowledge from queries, dashboards, and 50+ apps and ranks competing definitions by authority (OntoRank). Ranking picks the likeliest meaning of "revenue"; nothing versions it, guarantees it, or notifies anyone when it drifts. Ranking a definition is not verifying the number computed from it.

Real-world break

An agent inherits 2.1's silent semantic shift at machine speed: it doesn't file a confused Slack message like an analyst, it produces confident wrong answers at volume, under a certified-looking source. OBO auth answers "may this agent see this row"; nothing answers "what may this agent rely on."

Cost

Security review becomes the AI bottleneck (no artifact states what an agent may rely on), and the industry outcome Gartner predicts: 40% of enterprises demoting or decommissioning agents by 2027 over governance gaps found in production.

Why it holds

A learned graph is probabilistic by design; warranting context requires the contract objects of 2.4 plus the lifecycle of 2.2. Also: Ontology ingests from everywhere but serves the Genie family; an open, warranted context API for any agent is a different product with a different buyer.

DataOS

Contract-grounded context served to any agent: each dataset carries a machine-readable statement of meaning, guarantee, and freshness: the artifact the security reviewer signs. And it's standard-shaped: DataOS emits ODCS for datasets, ODPS for products, and OKF for agent context, so any agent or tool can parse it without our SDK.

2.6  Everything meters through their compute

Mechanism

Governed answers require the DBSQL engine: metric views are DirectQuery-only (import mode breaks semantics), Statement Execution runs per-call on a warehouse under one principal, Lakebase serving requires materializing data into it. There is no semantic API (measures by name over REST/GraphQL with tenant context) and no layer deciding which reads shouldn't hit compute at all. And there's a second meter: text-to-SQL agents burn tokens ingesting schemas and retrying failed queries. Metered API spend nobody budgets, scaling with usage.

Real-world break

Who queries changes everything: humans in dozens per day, dashboard tiles in thousands, agents in millions. Near-identical reads, each billing the meter again. The consumption curve inflects exactly when the customer succeeds at AI.

Cost

The DBSQL line becomes the AI tax; embedded and agent workloads also inherit seconds-scale latency and a shared-service-principal security model that reopens what OBO solved.

Why it holds

Serving governed answers without the meter is revenue-negative. A vendor does not ship a feature whose success shrinks its own consumption line. This gap is economic, which makes it the most durable of the six.

DataOS

In-flight dedup collapses concurrent identical queries into one execution; result reuse serves repeated reads without touching the engine; work-avoided metrics make the saving provable per workload, not asserted. Semantic serving over APIs with tenant-aware security, compute pushed down only when work is genuinely new.

Freshness is stated, not hidden: cached answers serve at each product's declared freshness tolerance; fresh or long-tail queries pass through live, with dedup still applied. And agents send small JSON metric queries instead of generating SQL: no schema ingestion, near-zero retries, the token meter flattens with the compute meter.

2.7  Operating a product is invisible

Mechanism

A table is queried, not called: there's no runtime to compute "is this trending toward a breach" against. Unity Catalog surfaces consumption and query_history logs per-query latency and errors. These are signals, not an operating loop. Nothing rolls them up against a target the product committed to, and nothing acts when the trend turns bad.

Real-world break

A product drifts toward a freshness or latency SLA breach for days. Query counts look healthy. No SLO catches the drift, no incident opens, no one is paged. The team hears about it from a complaint, after the SLA is already broken.

Cost

Every SLA is enforced by the consumer noticing. That inverts the relationship: the customer becomes the monitoring system, each breach is discovered downstream where it's most expensive, and the team's credibility pays for the gap between "broken" and "noticed."

Why it holds

The pieces exist: table-level drift profiling, SQL alerts on thresholds, a webhook to page someone. But they're per-table, assemble-it-yourself parts with no product entity to hang them on. The SLA lives in a wiki, the alert lives in Databricks SQL, the routing lives in PagerDuty, and nothing binds them to the thing the consumer actually bought. An SLO is telemetry rolled up against an internal target, watched continuously, wired to an incident process. That requires a runtime entity operating as one contract, not three tools someone stitched together and maintains by hand. And it's downstream of 2.4: you can't operate an entity the catalog can't express.

DataOS

The product manifest carries the SLA; the runtime derives SLOs from live telemetry, set tighter than the SLA on purpose. Breach an SLO and an incident opens and routes to the owning team automatically. The SLA holds because the SLO caught it first, not because someone noticed after the fact. Operating a data product is what turns publishing into product management.

Coexistence posture

Their features are our substrate, not our competition.

We import metric views; a year of customer modeling becomes an on-ramp, not a moat. Their tables are our inputs. Their engines run our compute: we push work down, we don't replace it.

We respect their ABAC as the enforcement plane. On top of it, we offer simpler, semantic-shaped REST and GraphQL APIs, governed separately or inclusively, whichever the customer's security model calls for. The filter lives in the layer, not the prompt.

And we offer business-user-friendly discovery of data products, with APIs to build custom experiences on top.

The contracts themselves are standard-shaped: ODCS and ODPS under the Linux Foundation, plus OKF for agent context. The contract is portable, even from us.

Where a customer already runs DataOS on another engine, Databricks is an extension of a working blueprint, not a new bet.

4 · Demo: one shipment through the boundary (WIP)

Work In Progress

One fixture, one antagonist, four movements, all seven gaps. Runtime around twenty minutes. The project is freight_ops: a freight operator loads containers, every item scanned at load becomes a row in logistics.cargo_lines, and one downstream output is legally consequential: the dangerous-goods declaration filed with port authorities, where declared hazmat weight must match item-level reality. Mis-declare and the container is held, or ships under a false filing. That is why this product carries a contract at all.

The contract is not a separate document. It lives in the model header: the grain, the assertions, the cadence, the column classifications, all in the same file as the SQL they govern. A change to the query is, by construction, a change to the file that declares what the query must honor. That is what makes a diff classifiable.

models/logistics/cargo_lines.sql:

-- One row per item scanned at container load.
-- Feeds the dangerous-goods declaration filed with port authorities.
MODEL (
  name logistics.cargo_lines,
  kind FULL,
  columns (
    shipment_id INT,
    container_id VARCHAR,
    pallet_id VARCHAR,
    sku VARCHAR,
    hazmat_un VARCHAR,
    weight_kg DECIMAL,
    order_line_id INT
  ),
  grains [shipment_id, container_id, pallet_id, sku],
  cron '*/15 * * * *',
  assertions (
    cargo_order_line_consistency,
    hazmat_un_weight_validation,
  ),
  column_classifications (
    hazmat_un = restricted
  )
);

SELECT
  shipment_id,
  container_id,
  pallet_id,
  sku,           -- Stock-keeping unit, one per scan
  hazmat_un,     -- UN dangerous-goods code; applies to its item only
  weight_kg,     -- Scanned item weight in kilograms
  order_line_id
FROM logistics.scan_events
WHERE scan_type = 'load'

The semantic model is a sibling file, same name, same project, same plan. The 1:1 the audit checks and the measures agents query are declared next to the transformation they describe. Note the caveat on hazmat_weight_by_un: the author wrote down, in the metadata itself, exactly the assumption the demo is about to attack.

models/logistics/cargo_lines.yml:

kind: semantic
name: cargo_lines
depends_on: logistics.cargo_lines
description: Cargo manifest lines (semantic layer)

ai_context:
  instructions: >
    One row per scanned item. Use for manifest weights, hazmat
    declarations, and billing joins. Query via SQL, REST, or GraphQL.
  synonyms: [manifest lines, scan lines]

dimensions:
  - name: hazmat_un
    behavior:
      type: categorical
    terms:
      - compliance.un_code
  - name: sku
    behavior:
      type: identifier
  - container_id
  - pallet_id

measures:
  - name: hazmat_weight_by_un
    type: sum
    expression: "{cargo_lines.weight_kg}"
    filters:
      - "{cargo_lines.hazmat_un} IS NOT NULL"
    description: Declared dangerous-goods weight
    behavior:
      type: simple
    ai_context:
      caveats:
        - Valid only at scanned-item grain; a UN code
          belongs to its item, not its pallet.
  - name: manifest_gross_weight
    type: sum
    expression: "{cargo_lines.weight_kg}"
    behavior:
      type: simple

Data quality is a third sibling, and it includes the same statistical machinery Databricks has: anomaly detection on row counts. Keep that in mind; the demo will show it staying quiet in both worlds.

models/logistics/cargo_lines-dq.yml:

type: dq
name: cargo_lines_dq
depends_on: logistics.cargo_lines

rules:
  - row_count > 0
  - duplicate_count(sku) = 0
  - anomaly detection for row_count
  - change for row_count >= -50%

The metric surface resolves to a semantic measure. And the standalone audit is plain SQL that returns failing rows: a check anyone could write anywhere. The difference will be what happens when it fails.

models/metrics/hazmat_weight.yml and audits/compliance/cargo_order_line_consistency.sql:

kind: metric
name: hazmat_weight
measure: cargo_lines.hazmat_weight_by_un
ts: cargo_lines.scan_ts
granularity: day
description: Declared DG weight by UN code

ai_context:
  caveats:
    - Per-item sum; never re-aggregate across a grain change.

dimensions:
  - name: hazmat_un
    ref: cargo_lines.hazmat_un

tags: [compliance, hazmat]
terms: [glossary.dangerous_goods_weight]
-- Every cargo line must map to exactly one order line.
ASSERTION (
  name cargo_order_line_consistency,
  dimension consistency,
  standalone true,
);

SELECT c.order_line_id, COUNT(*) AS cargo_rows
FROM logistics.cargo_lines c
JOIN orders.order_lines o
  ON o.id = c.order_line_id
GROUP BY c.order_line_id
HAVING COUNT(*) <> 1;

Three registered consumers complete the fixture: dg-declaration-service (API, webhook notify), customs-manifest (export, email), billing (dashboard, Slack). Access to the product is gated on agreement.md; intended use lives in usage.yml.

Movement 1 · A normal Tuesday

Start with the product answering questions. "Show me cargo_manifest: version, guarantee, owner, consumers" is one lookup against the product, not a hunt across four tables, two metric views, and a wiki (2.4). The customs dashboard refreshes its tiles all morning and a compliance agent polls hazmat_weight per shipment; the work-avoided counter climbs while the warehouse sleeps, and the agent's queries are small JSON against declared measures, not schema-ingesting SQL (2.6).

SAY"Everything you just saw answered, in one lookup, from one object. Hold that. We are about to change something."

Movement 2 · The change arrives

An engineer opens a performance PR: pre-aggregate cargo_lines to pallet grain. One GROUP BY, MAX() on the text columns so the schema holds. The goal is legitimate, the totals reconcile to the kilo, and every statistical monitor, theirs and ours, stays green: the DQ file's own anomaly rules see nothing wrong with reconciling totals (2.1).

The plan sees what monitors can't. The diff is judged against grains [shipment_id, container_id, pallet_id, sku]: Breaking. The blast radius names every affected asset and all three registered consumers, including the API service that catalog lineage can only show as a service-principal blob (2.3). Nothing ships without explicit consent, and when an owner consents, the version bumps and the notification lands in dg-declaration-service's channel before the change does (2.2). Ask the room: who approved this? Git blame on one side. One plan record on the other.

SAY"Your monitors saw this diff run and said nothing. The contract knew. And notice who got told, before the change landed, not after."

Movement 3 · The agent test

Same question to two agents: how much UN1950 is on shipment 4417? The raw-side agent, post-shift, answers 3,180 kg, confidently, into a compliance workflow, under a certified-looking source. The contract-side agent answers 90 kg, because the silent shift never shipped, and the measure it queried carries the caveat the author wrote on day one (2.5).

SAY"The agent never got suspicious. The contract did."

Movement 4 · Weeks later

Port scanners degrade and scans arrive slower. Query counts look healthy; nothing is failing, everything is drifting. The freshness term in the contract derives an SLO watched from live telemetry, and when the SLO breaches, an incident opens and routes to freight-ops before the declaration misses a filing window (2.7).

SAY"Your customer found the last one. The runtime found this one."

Close. One shipment, one contract, seven gaps crossed. In the other world every gate was green. Here, seven things spoke up.

5 · Objections
