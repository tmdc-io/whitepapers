Governed Write-Back: A Reference Architecture

A standard write path for agents over analytical data: a declared Action Contract beside the semantic model, an append-only Intent Ledger, two delivery modes, and an author-owned Executor as the only component that touches the outside world. This document answers Real-World Data Problems for Write-Back (the problems paper); references of the form P1..P9 link to the nine problems catalogued there.

SECTION 00

Abstract#

Semantic models give agents a governed way to read enterprise state: certified entities, measures, and dimensions, with ownership, versioning, and policy attached. Nothing equivalent exists for changing that state. Every write an agent performs today happens outside the governed layer, through hand-written tools and direct API calls that carry their own implicit and unreviewed permission model.

This document describes a standard architecture that closes the gap. An Action Contract is declared beside the semantic model: a versioned specification of what mutations are allowed, on which entities, under which conditions. An Accept Service validates incoming write requests against the contract and records them in an append-only Intent Ledger. Intents are delivered in one of two modes, queued or immediate, and the only component that ever touches an external system is an author-owned Executor Module: plain Python, deliberately outside any scheduled pipeline. A Reconciliation Check closes the loop by confirming that applied intents eventually become observable in the analytical data.

The entire architecture rests on one correctness posture, stated in the banner above and enforced everywhere below: accept-time validation is advisory; apply-time validation is authoritative.

SECTION 01

Design stance#

The problems paper reduces to a single image: the analytical layer is a photograph of the business, and a photograph is always of the past. Sync lag, late-arriving entities, shared snapshots, and effective dating (P1, P4, P5, P6) are four ways the photograph misleads anyone who writes based on it. No architecture eliminates the photograph; the choice is between pretending the gap does not exist and designing around it explicitly.

This architecture designs around it with one reframe: the queue converts a correctness problem into a rejection-rate problem. If a write is recorded as an intent and the authoritative system validates again when the intent is applied, stale validation at accept time can produce only two outcomes: a false accept that gets caught at apply, or a false reject that annoys the caller. Neither corrupts state. That is a much better failure menu than the alternative, where a stale check gates a live mutation directly.

Three postures follow, and every section below is an application of one of them:

  1. The platform never mutates a source system. The Executor Module does, and a named author owns it. The platform's job is contract, policy, and record.
  2. The semantic layer is never the source of truth for operational state. It describes state held elsewhere, on a lag. It can host the contract for allowed mutations and the record of requested ones; it cannot adjudicate what is true right now.
  3. Honest vocabulary. Join-graph checks "resolve," they never "enforce" (P7). Verdicts come in three, not two: accepted, rejected, unverifiable (P4). Validation is either advisory or authoritative, and every check declares which it is.

When this layer is not worth it

A reference architecture should say where it does not apply. For a single write against a single system with a good API and its own validation, placing this layer in the middle adds a hop, a staleness surface, and a second validation regime that can disagree with the source's. The value concentrates in three situations:

  • Discovery. The caller (typically an agent) cannot know forty different APIs, but it can know one contract. The Action Contract is the catalogue of what may be done.
  • One policy and audit plane. Writes spanning several systems, or writes that must answer "who did this, under whose authority, and was it approved," need a single place where those questions have answers.
  • The ledger has independent worth. Replayable intents, deferred application, human approval gates, and a complete record of what was asked and decided are valuable even when the write itself is simple.

If a proposed action claims none of the three, it should be a direct API call, and the contract review should say so.

SECTION 02

Architecture overview#

Two runtimes, one ledger, one authoring surface.

One intent, end to end:

The sentence that organizes everything: there is one authoring surface, the Executor's apply function, and two invocation paths; the declared mode decides who calls it and when. Queued intents are picked up by the Dispatch Worker on a schedule. Immediate intents are invoked inline by the Accept Service while the caller waits. Same code, same contract, same ledger row either way.

The two-runtime split is not an implementation detail; it exists because of P8. Scheduled analytical pipelines re-run by design (restatement, backfill), and anything with side effects inside them re-fires those side effects. The write path therefore lives entirely outside the pipeline scheduler, and Section 8 makes the rule explicit.

SECTION 03

The Action Contract#

The Action Contract is the write-side sibling of the semantic model: a versioned, reviewable declaration, bound to a semantic entity, listing what may be done to it. It lives in the same repository discipline as the read model: a file, a pull request, an owner.

What an Action Contract declares:

  • The bound entity, connecting the contract to the semantic model's types, dimensions, and joins.
  • A key mapping: the explicit path from the warehouse's internal (surrogate) key, through the current dimension row, to the natural or API key the source system accepts. This answers P3 directly. Intents are recorded against the natural key, resolved at accept time from the current row, never against a surrogate. Where the analytical layer has merged several source identities into one entity, the mapping must name the surviving one; if it cannot, the action is not yet authorable.
  • Actions, each with an input schema, a write class, a risk tier, a delivery mode, validation predicates in three tiers, an executor binding, and a reconciliation reference.

Two worked examples, deliberately different in character:

kind: ActionContract
name: product_pricing
entity: semantic.products
key_mapping:
  from: product_sk                       # warehouse surrogate
  via:  dim_products.source_product_id    # column carrying the natural key
  to:   oms.product_id                    # what the source API accepts

actions:
  - name: update_list_price
    write_class: W2          # slow attribute update
    risk_tier: reversible
    mode: queued
    freshness_tolerance: 24h
    input:
      product_id: {type: string, required: true}
      new_price:  {type: decimal, gt: 0, required: true}
      currency:   {type: string, enum: [USD, EUR, GBP]}
      effective_from: {type: date, required: true}
    validation:
      referential:            # derived from the join graph; "resolves"
        - product_id resolves in dim_products
        - currency resolves via products -> price_books
      attribute:              # declared predicates, evaluated at accept
        - dim_products.status != 'discontinued'
        - input.new_price <= dim_products.msrp * 1.5
      stateful: []            # none; that is what makes this W2, not W3
    executor:
      module: executors/oms_pricing.py
      callable: apply
    reconciliation:
      check: checks/price_intents_landed
      sla: 48h

  - name: cancel_order
    write_class: W4          # state transition
    risk_tier: irreversible
    mode: queued
    expected_version:
      field: dim_orders.row_version      # advisory read at accept
    approval:
      required: true
      approvers: [role:ops_lead]
    input:
      order_id: {type: string, required: true}
      reason:   {type: string, enum: [customer_request, fraud, oos]}
    validation:
      referential:
        - order_id resolves in dim_orders
      attribute:
        - dim_orders.status in ('placed','allocated')   # advisory snapshot claim
      stateful:
        - source_check: order status in ('placed','allocated')
          when: apply                                   # authoritative, at apply
    executor:
      module: executors/oms_orders.py
      callable: apply
    reconciliation:
      check: checks/cancelled_orders_landed
      sla: 24h
An Action Contract with one W2 and one W4 action

Three constructs in these examples carry most of the weight:

Actions target operations, never measures. There is no action called adjust_net_revenue, because net revenue is a computation, not a thing (P2). The authoring litmus test: if an intent can only be phrased against a derived number, it is not yet a writable intent; it is a goal that decomposes into one or more real source operations.

The when: apply construct. The same predicate appears twice with different authority: evaluated against the analytical snapshot at accept (advisory, cheap, catches most nonsense early) and against the source at apply (authoritative). Divergence between the two evaluations is recorded on the intent itself, which means the system measures its own staleness per action over time instead of guessing at it (P1, P6).

The reconciliation reference. Every action names the check that will later confirm its effects became observable. An action without one draws a registration warning (Section 4), because a write path that never verifies its own landing is a rumor mill.

SECTION 04

Write classes and the decision table#

Not all writes are the same risk, and the biggest single design error in write paths is treating them uniformly. Every action declares exactly one write class, and the class, not author preference, determines the legal routing and the mandatory controls. Authors can tighten (queue something that could run immediately); they can never loosen.

#Write classDefinitionExamplesStaleness sensitivityDefault routeMandatory controls
W1Append / create-newCreates a record that did not exist; conflicts impossible by constructionCreate HR case; log supplier note; submit a PO request; create draft productNoneQueueIdempotency key
W2Slow attribute updateMutates an attribute whose real-world change rate far exceeds sync lagProduct description; cost-center reassignment; supplier contact; long-tail priceLowQueue, with declared freshness toleranceIdempotency key; tolerance at least the measured sync lag of the backing dimensions
W3Contended mutationMutates state that other actors change concurrently within one sync windowInventory adjustment; price during an active promotion; budget draw-downHighImmediate (the target API is the validator; the accept-time check is openly advisory), otherwise refuseExpected version, checked at apply time against the source, never the warehouse
W4State transitionMoves an entity along its lifecycle; legality depends on current state by definitionCancel order; approve PO; initiate termination; close shipmentDefinitionalQueue + version check + approval tierExpected version; human approval for irreversible or financial tiers
W5Cross-system compositeOne business intent, side effects in two or more systemsOnboard employee (HR + directory + payroll); launch product (PIM + pricing + channel)N/ARefuse. Decompose into W1..W4 intents; orchestration lives above this layerNone: the class is not accepted

Routing is a function of three declared facts, nothing else:

Two deliberate consequences of this shape. First, W2 misclassification is caught at registration, not at runtime: if the declared tolerance is tighter than the measured sync lag of the dimensions the validation reads, the action is really a contended mutation wearing a slow-update costume, and the contract is rejected before it can mislead anyone. Second, immediate mode exists only where a real validator exists downstream. It is a pass-through with an honest advisory check, never the platform pretending to enforce against stale state.

The decision table is enforced when a contract is registered or loaded, as a set of mechanical checks. Errors block registration; warnings surface for review.

SECTION 05

Validation: three tiers, three verdicts#

Validation at the Accept Service runs in three tiers, and naming the tiers prevents the failure mode where someone reads "validated" as "legal."

TierWhat it checksWhere truth comes fromAuthorityAnswers
Referential Do the intent's references hang together: does this product exist, does this currency apply to this region, does this order belong to this customer Derived automatically from the semantic model's join graph advisory Verdicts are phrased as "resolves," never "enforced." Declared joins are claims by an author; warehouses do not enforce referential integrity, and real tables carry orphans P7
Attribute Declared predicates on the payload and on current dimension attributes: status is not discontinued, price is within bounds The analytical snapshot at accept time advisory A claim about the snapshot, honest about its age P1
Stateful Anything depending on contended current state: live status, inventory levels, in-flight promotions The snapshot at accept, and the source system at apply, via the when: apply construct advisory at accept, authoritative at apply; the split is the correctness posture P1, P5, P6

Verdicts come in three, because two is dishonest:

The third verdict exists because of P4. A supplier onboarded this morning is fully real and completely invisible to the warehouse until the next sync. "Rejected" would be a confident lie, and agents encode confident lies as ground truth: they abandon legal tasks, report false failures, or retry in loops. The Accept Service compares the referenced entity against the dimension's sync watermark (the timestamp of its last successful load); if the entity could plausibly postdate it, the verdict is unverifiable, and policy decides whether such intents may queue for authoritative re-validation at apply time.

For effective-dated sources (P6), one further rule: validation predicates are evaluated as of the intent's effective date, not as of now, and state transitions on such entities always re-read the source at apply, because in those systems the past itself is editable. The queue is the natural home for effective-dated intents: an intent recorded with its effective date can simply wait, and be applied when the world reaches it.

SECTION 06

The Intent Ledger#

The ledger is the architecture's center of gravity: an append-only record where every write request lands, whatever its fate. Conceptually, one row per intent, carrying:

  • identity: intent id, idempotency key, the acting principal and (where applicable) the approving human
  • the request: action name, payload, effective date, expected version
  • the adjudication: verdicts per validation tier, with the advisory and authoritative evaluations recorded separately
  • the outcome: status, external reference returned by the source system, timestamps for every transition

The ledger is three things at once. It is the queue: the Dispatch Worker drains accepted intents from it, applying intents that touch the same entity strictly in order (part of the answer to P5). It is the audit trail: the complete, append-only history of what was asked, decided, approved, applied, and observed. And, exposed through the semantic layer as a readable entity (for example pending_intents), it is part of the read model, which is the move that answers P9: an agent's verification read returns warehouse state and ledger state together, so "PLACED, with an applied cancellation awaiting sync" replaces the phantom failure.

Its status machine, in full:

Two states deserve the emphasis, because naive designs omit exactly these two and real integrations produce them daily. unverifiable is the honest answer to a snapshot that cannot know (Section 5). unknown is the honest answer to a call that went out and never came back: the request may or may not have taken effect, and the only safe resolution is observation, not blind retry. Reconciliation is what converts unknown into applied or failed based on evidence.

Implementation is deliberately unspecified here: any durable store with transactional row updates and ordered draining serves. What is not negotiable is the shape: append-only, one status machine, per-entity ordering, idempotency keys on every intent.

SECTION 07

Delivery modes: queued and immediate#

Queued is the default, and most of the architecture's virtues live here. The Dispatch Worker drains accepted intents on a schedule, in per-entity order, with retry, backoff, and quarantine handled by the platform. The queue is what makes the correctness posture real: authority is deferred to apply time, where the source can answer. It is also what makes three whole problem families tractable:

  • Contention (P5): intents carrying an expected_version are checked at apply against the source; if the world moved past the version the caller believed in, the intent fails loudly instead of winning silently. Where the business allows it, the stronger move is designing the action itself as an append or an event ("record an adjustment of minus 30") rather than a level-set ("set on-hand to 70"), because commutative writes cannot lose updates at all.
  • Effective dating (P6): an intent recorded with a future effective date waits in the queue and applies when the world reaches it. Deferred application stops being a workaround and becomes a feature.
  • Approval (risk tiers): a queued intent can sit in awaiting_approval indefinitely without holding any caller hostage. Human gates and synchronous calls do not mix; human gates and queues do.

Immediate exists only where a real validator exists downstream (write class W3 with a target that validates). It is a pass-through: the Accept Service runs its advisory checks, records the intent, invokes the Executor inline, and returns the source's answer to the waiting caller. What immediate mode does not give you is worth a plain sentence: it provides no stronger correctness than the target API itself provides. It also concentrates every hard operational problem in one place: synchronous latency budgets, mid-call failure with unknown outcome (the unknown state exists largely because of this mode), and the awkward theatre of the platform's advisory check disagreeing with the source's authoritative one while the caller watches. In any rollout, immediate mode comes last, smallest, and most reluctantly.

SECTION 08

The author handover: the Executor Module#

Everything so far is platform machinery. The Executor Module is where an author, the person who owns the action, takes over. It is deliberately small: one Python function with a strict contract.

# executors/oms_orders.py
from writepath import Intent, ExecutorContext, Outcome

def apply(intent: Intent, ctx: ExecutorContext) -> Outcome:
    """
    Contract:
      - MUST be idempotent on intent.idempotency_key: pass it to the
        target if the API supports it; otherwise check-before-write.
      - MUST NOT read the warehouse to decide legality; the source is
        the validator here. ctx.source gives an authenticated client.
      - MUST return one of:
          Outcome.applied(external_ref=...),
          Outcome.rejected(code=..., detail=...),   # the source said no
          Outcome.failed(retryable=True|False, ...) # transport / system error
          Outcome.unknown(...)                      # sent, no response
      - MUST NOT raise for business rejections; raise only for bugs.
    """
    order = ctx.source.oms.get_order(intent.payload["order_id"])
    if order.status not in ("placed", "allocated"):
        return Outcome.rejected(code="ILLEGAL_STATE",
                                detail=f"order is {order.status}")

    resp = ctx.source.oms.cancel_order(
        order_id=intent.payload["order_id"],
        reason=intent.payload["reason"],
        idempotency_key=intent.idempotency_key,
    )
    return Outcome.applied(external_ref=resp.cancellation_id)
The one function an author writes

The four outcomes are the whole vocabulary between author and platform. applied carries the source's reference. rejected is a business no from the source and is final. failed is a transport or system error, and the author says whether retrying makes sense. unknown is the honest answer when a call went out and nothing came back; the platform parks it for reconciliation instead of retrying blind. Business rejections return; only bugs raise.

The rule that keeps this safe

The Executor Module is plain Python, loaded and invoked by the write runtime. It is never an interval-scheduled pipeline model.

The reasoning is P8 in one paragraph. Analytical pipelines re-run by design: restatement and backfill re-execute past intervals, and that is the read side's superpower. Any side effect embedded in a pipeline re-fires when the pipeline re-runs, and the duplicates land in the outside world (a re-booked truck, a re-sent offer letter, a re-issued coupon) where nobody is checking. The Executor therefore fires only for ledger rows in accepted status, and every external call is keyed on the intent's idempotency key. A restatement re-runs pipelines, finds no new accepted intents, and is a no-op against the world by construction, not by discipline.

What the platform guarantees around apply, so authors never rebuild it: per-entity ordering, retry with backoff for retryable failures, quarantine after exhausted attempts, parking of unknown outcomes for reconciliation, authenticated source connections and secrets through ctx, and structured logging of every invocation against the intent row.

What the platform explicitly does not do: compensation. There are no automatic rollbacks and no multi-step sagas. Cross-system compensating transactions are a graveyard of good intentions; the moment "undo" is automatic, its failure modes multiply faster than its successes. If an author needs a reverse, they declare a separate action that is the business-level reverse (an order un-hold, a credit memo), and it travels through the same ledger with the same controls. The buyer fear behind irreversibility is answered by the proposal and approval gates in front of the write, not by promises of magic behind it.

SECTION 09

Reconciliation: closing the loop#

Applying a write is a claim; reconciliation is the evidence. Each action names a Reconciliation Check: a scheduled comparison between the ledger and the synced analytical tables, asking one question: for every intent marked applied longer ago than the SLA, is its expected effect now observable?

Reconciliation does three jobs with one mechanism. It closes the audit loop: applied becomes reconciled on evidence, or diverged on an SLA breach, and divergences are routed to a human with the full intent history attached. It resolves the unknown state: the call that never answered is settled by observation rather than by guesswork or blind retry. And it feeds the system's self-knowledge: divergence rates and advisory-versus-authoritative disagreement rates per action are exactly the data that tunes each action's freshness tolerance (P1) and exposes which contracts were classified optimistically.

The check itself is authored beside the contract, versioned in the same repository, reviewed in the same pull request. A write path whose landing is never verified is a rumor mill; this is the component that keeps it a system of record.

SECTION 11

Adoption sequence#

The order is chosen so that each phase proves something the next one depends on.

  1. Ledger, Accept Service, W1 only. Append and create-new actions: referential and attribute validation, queue, dispatch, one executor. No versions, no approvals, no contention risk by construction. This proves the loop end to end.
  2. W2 with freshness tolerance, plus Reconciliation Checks. The first real staleness handling, and the point where the system starts measuring sync lag and divergence instead of assuming them.
  3. W4 with expected version and approval gates. The capability people actually want to see: an irreversible action proposed by an agent, gated by a human, applied by the queue, confirmed by reconciliation.
  4. W3 immediate, as a pass-through where the target validates. Last, smallest, and most reluctantly, for the reasons in Section 7.

W5 stays out at every phase. Composite cross-system intents decompose into W1..W4, and their orchestration is a different layer with different tools. A write path that stays narrow stays trustworthy.

REFERENCE

Glossary#

Action Contract
The versioned, reviewable declaration of allowed mutations, bound to a semantic entity: actions, input schemas, write classes, validation predicates, executor binding, reconciliation reference.
Accept Service
The platform component that receives a write intent, runs advisory validation, records the intent, and (in immediate mode) invokes the Executor inline.
Intent Ledger
The append-only record of every write intent: payload, actor, verdicts, status, and outcome. Simultaneously the queue, the audit trail, and (exposed as a readable entity) part of the read model.
Executor Module
The author-owned Python function that performs the real-world call against the source system. Fires only for accepted ledger rows; never part of a scheduled pipeline.
Dispatch Worker
The scheduled platform component that drains accepted intents from the ledger in per-entity order and invokes the Executor.
Reconciliation Check
The scheduled, author-owned comparison of applied intents against synced analytical state; resolves unknown, confirms reconciled, flags diverged.
Write class (W1..W5)
The taxonomy that determines routing and controls: append/create, slow attribute update, contended mutation, state transition, cross-system composite (refused).
Risk tier
Informational, reversible, irreversible, financial. Higher tiers force approval gates.
Freshness tolerance
A per-action declaration of how stale the validating snapshot may be for validation to remain meaningful; checked against measured sync lag at registration.
Expected version
The version of the entity the caller believed it was acting on, checked at apply time against the source.
Idempotency key
A unique key per intent making retries and re-deliveries produce one effect.
Sync watermark
The timestamp of a dimension's last successful load; the basis of the unverifiable verdict.
Registration Rules (WR-xxx)
Mechanical checks run when a contract is registered; the decision table in executable form.
Advisory / authoritative
The two authority levels of validation: claims about the analytical snapshot, and the source system's answer at apply time.
