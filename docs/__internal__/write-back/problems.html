Real-World Data Problems for Write-Back

The concrete ways operational/analytical drift breaks agent writes, illustrated with HR (Workday), supply chain (ERP), and ecommerce (OMS) data. Philosophical objections are out of scope. Every problem here is one a mid-size Workday + SAP + Shopify estate produces in an ordinary week.

PROBLEM 01 The photograph

Sync lag: validating against yesterday#

When a person makes a change in Workday or SAP, that change does not appear in the analytics warehouse instantly. It arrives with the next scheduled sync: a batch extract, a nightly load, sometimes a near-real-time feed, but always a delay. For dashboards this barely matters; nobody cares whether headcount was refreshed at 2am or 4am. The read side was built on the assumption that a few hours of delay is acceptable, and for reading, it is.

A write changes the stakes entirely. If an agent checks "is this employee active?" against the warehouse before acting, it is checking a photograph, and the photograph might be six hours old. A human making the same check would notice contradictions, ask a colleague, hesitate. An agent takes the answer literally and proceeds. The staleness that was harmless on a dashboard becomes the basis for an action against a live system.

The useful way to think about the risk is as a product of three factors: how often the entity actually changes, how long the sync delay is, and how many other actors are touching the same entity. A cost center that changes twice a year, read through a warehouse ten minutes behind, carries effectively zero staleness risk. Inventory during a flash sale, read through the same warehouse, is fiction within seconds. Same warehouse, same lag, opposite risk. This is why the design cannot treat "the warehouse is stale" as a single yes/no fact.

Real scenarios

  • HR · Workday

    A staffing agent assigns workers to project codes using the warehouse's worker dimension, fed by a Workday RaaS extract that runs every night at 2am. An employee is terminated at 9am. Until the next extract, every downstream system that trusts the warehouse believes the person is active. The agent's assignment bounces off Workday's own validation at best; at worst, if the target system validates less strictly than Workday, a terminated employee ends up allocated to a client project, and the error surfaces weeks later in a billing review.

  • Supply chain · ERP

    A goods-receipt agent checks that a purchase order is in APPROVED status before recording a receipt against it. Procurement closed the PO two hours ago after a pricing dispute. The warehouse still shows APPROVED. The receipt intent is validated, submitted, and rejected by the ERP, and the receiving dock now has physical goods with no system record, which is exactly the situation goods-receipt processes exist to prevent.

  • Ecommerce · OMS

    During a promotion, an inventory agent reads on_hand = 240 for a SKU from the warehouse and approves a channel allocation. The number was true at the 6am sync. By 10am the SKU has sold 300 units. The allocation was validated against a quantity that stopped being real four hours earlier.

What the design must absorb

Validation performed at accept time (when the intent is received) can only ever be advisory. The authoritative check happens at apply time, against the source system itself. The gap between the two is not a flaw to be minimized to zero; it is a property to be declared per action, which is what the design cut's freshness_tolerance field and write-class system exist for.

PROBLEM 02 The transformation tax

Transformation inversion: there is no field to write back to#

The numbers agents read from the semantic layer were manufactured. net_revenue_usd is not a column that exists anywhere in the order management system; it is the output of a pipeline that filtered out test orders, subtracted discounts and returns, converted currencies at the order-date rate, and merged duplicates. That manufacturing is precisely what makes the read side valuable: the agent gets a clean, comparable, business-ready number instead of raw operational noise.

The trouble starts the moment someone asks the agent to change that number. "Adjust net revenue for order 555123" sounds like a write, but net revenue is not a thing that can be written. It is a computation over five source fields, one of which is a filter, one of which is an exchange rate that was correct on a specific date. Reversing the pipeline is not a technical inconvenience; for most transformations it is mathematically impossible, because information was deliberately discarded on the way in. Which component was wrong: the gross amount, the discount, the return, or the rate? The measure cannot say, because the measure was built by forgetting that distinction.

This is the problem an entire product category (reverse ETL: Census, Hightouch) was built around, and their decade of scar tissue reduces to one lesson: the hard part of writing back is not moving the data, it is knowing which source field and which key the write actually belongs to.

Real scenarios

  • HR · Workday

    An executive asks a compensation agent to "increase total comp for this team by 5%." total_compensation in the warehouse is base pay plus bonus target plus an equity valuation plus a benefits load factor, normalized to USD. There is no total-comp field in Workday to write. A real raise is a compensation-change business process against base pay, effective-dated, routed through approval. An agent that doesn't know this either fails, or worse, finds some writable field and modifies the wrong component.

  • Supply chain · ERP

    A costing agent is asked to "correct the landed cost" on a receipt line. Landed cost was assembled from unit price, allocated freight, duty, and handling, each from a different source document. The correction belongs to exactly one of those components (the freight allocation was wrong), and writing anywhere else corrupts a number that finance reconciles monthly.

  • Ecommerce · OMS

    A margin agent reads contribution_margin and is asked to bring an underperforming SKU above threshold. The only levers that exist in any writable system are the list price and the promotion flag; the margin itself is arithmetic. An action defined against the margin is undefined; actions defined against price and promotion are real.

What the design must absorb

Actions are never defined against measures. They are defined against source-system operations (update_base_pay, apply_discount, adjust_freight_allocation), and the state model's job is to carry the explicit mapping from the semantic entity down to the source fields and keys those operations touch. A useful litmus test for authors: if an intent can only be phrased against a derived number, it is not yet a writable intent; it is a goal that decomposes into one or more real operations.

PROBLEM 03 The transformation tax

Identity: the key the agent has is not the key the source wants#

Warehouses assign their own identifiers. When a worker's record is loaded, the warehouse mints a surrogate key (employee_sk = 88412), an integer that exists nowhere in Workday and means nothing to any operational system. Surrogates exist for good read-side reasons: they make joins fast, they insulate the warehouse from upstream key changes, and they make it possible to keep history, because when the worker transfers departments, the warehouse doesn't overwrite the old row; it closes it and opens a new one with a new surrogate. This versioning pattern is called SCD2 (slowly changing dimensions, type 2), and it means one person is many rows.

Now hand that surrogate to an agent. The agent queried last quarter's org structure, picked up employee_sk 88412, and now wants to act on that person. Three things are wrong at once. The surrogate identifies a historical version of the person, possibly one whose department, manager, and cost center are all obsolete. The source system has never heard of the number. And even once the surrogate is resolved to a real identifier, Workday itself has two: the human-readable Employee ID for some APIs, the WID (a GUID) for others, and the right one depends on which integration surface the write uses.

For reads, none of this matters; the surrogate does its job invisibly. For writes, identity resolution is a mandatory, explicit step, and skipping it produces writes that land on the wrong version, the wrong system, or the wrong person.

Real scenarios

  • HR · Workday

    A workforce agent builds a reallocation plan from a warehouse query joining last year's project assignments. Every worker reference in the plan is a surrogate pointing at the SCD2 row that was current then. For workers who have since transferred, the plan's context (manager, org, location) describes people who no longer exist in that configuration, and any write built on it inherits the obsolescence.

  • Ecommerce · OMS

    The warehouse's customer dimension merged three source identities into one entity: a Shopify customer GID, a guest-checkout email, and a legacy account from a migrated platform. A retention agent decides to issue a credit "to the customer." The OMS needs exactly one of the three source identities, and picking the wrong one credits an account the customer can no longer log into. The merge that made the read-side customer-360 possible is what makes the write ambiguous.

  • Supply chain · ERP

    Vendor-master cleanup merged "ACME Corp" and "Acme Corporation" into a single warehouse supplier entity. The ERP still carries both vendor numbers, one active, one blocked. A payment-terms agent updating "the supplier" must know which vendor number survived, and the warehouse entity, having deliberately blurred that distinction, cannot tell it.

What the design must absorb

Every state model declares an explicit key_mapping: the path from the warehouse surrogate, through the current dimension row, to the natural or API key the source system actually accepts. Intents are recorded against the natural key, resolved at accept time from the current SCD row, never against a surrogate. Where the warehouse has merged multiple source identities, the mapping must name the surviving one, and if it can't, the action is not yet authorable.

PROBLEM 04 The photograph

Late-arriving entities: the false reject#

This is Problem 1's mirror image. There, the warehouse said yes about something that had become false. Here, the warehouse says no about something that has become true. A supplier onboarded in the ERP at 10am is fully real, fully valid, ready to transact, and completely invisible to the warehouse until the afternoon sync. An agent that validates "does this supplier exist?" against the warehouse gets a confident, wrong no.

With human users, this failure is an annoyance. A person who gets "supplier not found" thirty minutes after onboarding it shrugs, knows the system is slow, tries again after lunch. Agents do not shrug. An agent receives "rejected" and encodes it as ground truth: the write was illegal. Depending on how it is built, it either abandons a perfectly legal task, reports a false failure upward, or retries in a tight loop against a validation that won't change for hours. All three behaviors are worse than the underlying problem.

This is the case that forces a third verdict into the validation vocabulary. "Accepted" and "rejected" assume the validator's knowledge is complete. Against a synced snapshot, it never is, and the honest answer for an entity the warehouse hasn't met yet is "I can't verify this," which is a different claim from "this is illegal."

Real scenarios

  • Supply chain · ERP

    Procurement onboards a supplier at 10am specifically because an urgent PO needs to go out today. The procurement agent, asked to create that PO at 10:30, is told the supplier doesn't exist. The one situation where the write is most time-sensitive (a brand-new entity being used immediately) is exactly the situation the snapshot handles worst.

  • HR · Workday

    A hire is entered in Workday in the morning; an onboarding agent tries to create the IT-provisioning case an hour later and is rejected because the worker isn't in the dimension yet. The agent reports the onboarding as blocked. The new hire's first-day laptop ticket, the very thing the agent existed to automate, is now waiting on a nightly batch.

  • Ecommerce · OMS

    Merchandising creates a SKU at noon for a product launching at 6pm. The pricing agent, applying launch pricing at 2pm, is told the SKU is invalid. By the time the warehouse learns the SKU exists, the launch window has passed.

What the design must absorb

The accept service compares the referenced entity against the dimension's sync watermark, the timestamp of the last successful load. If the entity could plausibly have been created after that watermark, the verdict is unverifiable, a first-class status distinct from rejection. Policy then decides whether unverifiable intents may queue, to be re-validated at apply time when the source can answer authoritatively. The three-way taxonomy accepted / rejected / unverifiable is not decoration; it is what makes the system usable by callers that take every answer literally.

PROBLEM 05 The photograph

Lost update: two agents, one snapshot#

Concurrency problems are as old as databases, and databases solved them decades ago with locks and transactions. Those solutions work because the database doing the validating is the database doing the writing: it can hold a lock between the check and the change.

A warehouse-validated write has no such luxury. The check happens against the warehouse; the change happens in the ERP; nothing connects them. Worse, the warehouse snapshot is shared: every agent reading between two syncs sees the identical photograph. Two agents can both check the same inventory level, both find it sufficient, both act, and both be individually correct against a snapshot that neither of their actions updated. The source system receives two writes in sequence, applies both, and the second silently destroys the assumption the first was built on.

Nothing in this failure looks like an error. No validation failed, no exception was thrown, no log line is suspicious. The damage is discovered later, as a negative inventory balance or a price that doesn't match any decision anyone remembers making, and by then the causal chain is two syncs deep and effectively unreconstructable. Agents make this categorically worse than humans did, because agents act in bursts, in parallel, within the same sync window, on the same entities. The probability of collision stops being negligible.

Real scenarios

  • Supply chain · ERP

    A replenishment agent and an allocation agent both read on_hand = 100 for a SKU from the 6am snapshot. Replenishment applies a safety-stock adjustment of −30 assuming 100 available; allocation commits 90 units to a store assuming the same. The ERP accepts both. On-hand is now −20, the store order will short-ship, and both agents' logs show flawless execution.

  • HR · Workday

    A requisition-hygiene agent closes stale requisitions while a hiring-manager assistant agent extends one of the same requisitions with an updated close date. Both validated against the morning extract, both wrote, and the requisition's final state depends purely on which write arrived second. A candidate pipeline is either orphaned or resurrected at random.

  • Ecommerce · OMS

    A pricing agent applies a planned price change to a SKU while a promotion agent, within the same sync window, computes a 20%-off promotional price from the base price it read this morning. The promotion math is now applied to a base price that no longer exists, and the customer-facing price is a number nobody chose.

What the design must absorb

Contended mutations (write classes W3 and W4 in the design cut, meaning writes to state that other actors change within a sync window) carry an expected_version: the version of the entity the caller believed it was acting on, checked at apply time against the source, never against the warehouse. If the source has moved past that version, the intent fails loudly instead of winning silently. The stronger move, where the business allows it, is to redesign the action itself: record an adjustment event rather than set a level, because append-only and commutative writes cannot lose updates in the first place.

PROBLEM 06 The photograph

Effective dating: "current" is a question, not a column#

Most systems treat time simply: a record has the value it has, and updates replace it. HR systems cannot afford that simplicity, because HR reality is full of changes that take effect at a different time than they were entered. A raise approved in July can be effective from June (retro pay). A reorg entered today can be effective in September. Workday is built around this from the ground up: every transaction carries both an entry date and an effective date, and the two routinely disagree in both directions. The formal name is bi-temporal data, but the plain version is: the system's answer to any question depends on when you ask about, not just when you ask.

A warehouse extract, by necessity, flattens this into a photograph: "the current row." That flattening quietly answers only one of the possible time questions, and an agent that does arithmetic on the flattened value can be perfectly correct and completely wrong at once. The failure below isn't a stale read in the Problem 1 sense; the warehouse was faithfully up to date with everything that had been entered. What it couldn't know is that an entry made next week would rewrite last month.

There is a second, subtler trap in the same family: existence is also effective-dated. A future-dated position or a future-dated supplier contract exists as a row today but is not a valid target for action until its effective date arrives. "It's in the dimension" and "it can be acted on now" are different claims.

Real scenarios

  • HR · Workday

    A compensation agent computes a 3% raise, effective August 1, on a base of $95k read from the warehouse on July 19. On July 20, payroll enters a retroactive increase effective June 1, making the true June-onward base $101k. The agent's arithmetic was flawless; its base was a snapshot that a later entry rewrote. The raise lands at $97.85k instead of $104.03k, the employee notices, and the correction consumes more HR effort than the original raise.

  • HR · Workday

    A staffing agent assigns a worker to a position it found in the dimension. The position is real but future-dated, part of a September reorg entered in July. The assignment is rejected, or worse, accepted into an org structure that doesn't operationally exist for another six weeks, confusing every report between now and then.

  • Supply chain · ERP

    Contract price lists carry effective ranges. A PO agent prices an order against the price row that is in the table today, but the delivery date falls inside the next contract period, where a different price is in effect. The PO is issued at a price that will fail three-way match at invoice time, and accounts payable inherits the dispute.

What the design must absorb

For effective-dated sources, validation predicates must be evaluated as of the intent's effective date, not as of "now," and state transitions on such entities (write class W4) always re-read the source at apply time, because the past itself is editable. This problem is also the strongest single argument for the queue at the heart of the design: an intent recorded with its effective date can simply wait, and be applied when the world reaches it.

PROBLEM 07 The transformation tax

Declared joins are not enforced integrity#

The semantic model's join graph looks like a natural validation asset. "Orders join to customers on customer_id" reads like a rule, and using it to check that a write's references hang together (this SKU exists, this currency is valid for this region, this order belongs to this customer) is genuinely useful and essentially free.

The trap is in what a declared join actually is. In an operational database, a foreign key is enforced: the engine physically refuses a row that violates it. In a warehouse, the join is a description written by an author, a claim about how the data usually relates. Cloud warehouses do not enforce referential integrity even when asked; Snowflake accepts foreign-key DDL and then ignores it by design. And real warehouse tables carry the residue of every upstream mess: guest checkouts with null customers, orders pointing at customers deleted upstream, positions referencing cost centers that closed mid-quarter.

So a validation built on the join graph is real evidence, but it is evidence of a specific, limited kind: "this reference resolves in the snapshot we have." It is not proof that the relationship holds operationally, and vocabulary discipline here matters more than it looks. The first time a document says the join graph "enforces" anything, someone downstream will design as if it does.

Real scenarios

  • Ecommerce · OMS

    A service agent issues a goodwill credit "to the customer on order 555123." The order is a guest checkout; its customer_id is null. The join the validation walked exists in the model and fails on this row, and the credit has no destination. A close cousin, order 555124, points at a customer since deleted upstream; validation resolves the reference against the warehouse's retained row and approves a credit to an account the source system no longer has.

  • HR · Workday

    The model declares positions join to cost centers. The quarterly close retired forty cost centers; open positions still reference them in the extract. A staffing agent's assignment validates cleanly against the model and is rejected by Workday, whose own validation knows the cost center is closed.

  • Supply chain · ERP

    A carrier-master cleanup retired a set of carrier codes. Historical shipments referencing them remain in the warehouse, as they should. A shipment agent, validating a new booking against "carrier codes present in the dimension," happily selects a retired code, because presence in a dimension that retains history says nothing about current validity.

What the design must absorb

Referential validation derived from the join graph belongs in the advisory tier, and its verdict is phrased as "resolves," never "enforced." It is cheap, mechanical, and worth having; it catches typos, hallucinated IDs, and structural nonsense before anything reaches a source system. The authoritative verdict on whether a relationship actually holds is always the source's, at apply time.

PROBLEM 08 Self-inflicted

Restatement re-fires side effects#

Analytical pipelines are built to re-run. When an upstream bug is found, the fix is to restate: re-execute the affected date range and overwrite the bad outputs. Backfills do the same for new logic over old data. This is not an edge case; it is the read side's superpower. Idempotent re-execution over intervals is what makes warehouse data correctable at all, and a healthy data team restates something every month.

Now imagine a write nestled inside one of those pipelines: a scheduled model that, as part of its daily run, calls a carrier API to book pickups. It works perfectly for a month. Then someone restates July. The scheduler faithfully re-executes every July interval, and every embedded API call fires again. The carrier receives a second booking for July 3rd, and a second for the 4th, and so on through the month. Nothing in the pipeline is aware anything is wrong, because from the pipeline's perspective nothing is: re-running is what it's for.

The failure is silent in a specific, expensive way. Warehouse-side, the restated outputs are correct, which is all anyone checks. The duplicates exist only in the outside world, and they surface on their own schedule: an invoice, a confused supplier, a customer who received two coupon emails. By then the restatement that caused them is weeks old and nobody connects the two events.

Real scenarios

  • Supply chain · ERP

    A daily model books carrier pickups for outbound shipments as it processes the day's orders. An August restatement of July re-books a month of pickups. Trucks are dispatched to docks with nothing to collect, and the carrier's invoice for the phantom pickups is the first anyone hears of it.

  • HR · Workday

    A model that generates and sends offer letters as part of a requisition pipeline is backfilled after a template fix. Candidates who accepted weeks ago receive fresh offer letters, some reflecting the corrected (different) terms. Legal gets involved. This exact class of incident is why HR integration teams are conservative about anything automated touching candidate communication.

  • Ecommerce · OMS

    An attribution model that issues win-back coupon codes to lapsed customers is restated after an attribution-logic fix. Every lapsed customer in the window receives a second coupon code, both codes are live, and the promotion budget is spent twice on the same cohort.

What the design must absorb

Side effects never live inside interval-scheduled models. The executor (the author-written function that actually calls the outside world) fires only for rows in the intent ledger, the append-only record of accepted write requests, and every external call is keyed on the intent's idempotency key. A restatement re-runs pipelines, finds no new accepted intents, and is a no-op against the outside world by construction. This single rule is the difference between "the ledger is elegant" and "the ledger is mandatory."

PROBLEM 09 Self-inflicted

Read-your-writes: the agent that couldn't see its own hand#

Any competent agent verifies its work: act, then read back, then confirm. The instinct is exactly right, and against a single system it works. Against a split read/write architecture it backfires, because the write went to the source system and the read-back goes to the warehouse, and the warehouse won't reflect the write until the next sync, hours from now.

So the agent cancels an order, the cancellation succeeds, and the agent's verification read says PLACED. Every fact the agent can see says the cancellation failed. A human would recognize the pattern ("the dashboard just hasn't refreshed"); the agent has no such folklore. It does the diligent thing: retries the cancellation, or reports the failure, or escalates. The retry is the mild outcome; a duplicate intent is at least deduplicable. The escalation is worse: a human now investigates a failure that never happened, and organizational trust in the agent, the scarcest resource in any agent rollout, takes the hit.

The insidious part is that this failure is caused by good agent design. The more rigorously an agent verifies its actions, the more reliably it falls into the gap. Any write path that punishes verification is a write path agents cannot safely use.

Real scenarios

  • Ecommerce · OMS

    A service agent cancels an order inside the fulfillment cutoff window, verifies against the warehouse, sees PLACED, and re-submits. With idempotency in place the retry is absorbed; without it, the OMS receives a second cancellation request against an already-cancelled order and returns an error that the agent now reports as a new failure, compounding the confusion.

  • HR · Workday

    An onboarding agent creates an IT-provisioning case, reads back the worker's case list from the warehouse, finds nothing, and creates the case again. IT receives two tickets for one laptop, and the dedup burden lands on the service desk, which is precisely the manual work the agent was meant to remove.

  • Supply chain · ERP

    A procurement agent submits a PO change, cannot see it reflected, and flags the change as failed in its run summary. The nightly ops review now contains a red item that self-resolves at 2am. After a few weeks of phantom reds, the team stops reading the agent's run summaries at all, which defeats the point of having them.

What the design must absorb

The intent ledger is itself exposed through the semantic layer as a readable entity (pending_intents), so the verification read returns the whole truth: warehouse status PLACED, and an applied cancellation intent C-88 awaiting sync. The agent's verify step reads warehouse state and ledger state together, and idempotency keys on the accept service make the inevitable retry harmless. The ledger stops being only the write path's bookkeeping and becomes part of the read model, which is the move that closes the loop.

The grouping from the introduction is worth restating as the takeaway. Problems 1, 4, 5, and 6 are the photograph disease and are managed, never eliminated: the design's job is to declare, measure, and bound the gap, not to pretend it closes. Problems 2, 3, and 7 are the transformation tax and are paid once per action, at authoring time, in the form of explicit mappings and honest vocabulary. Problems 8 and 9 are eliminated outright by two structural rules: side effects only from the ledger, and the ledger visible in the read path. A design review of any write-path proposal can use exactly that split as its checklist.

The architecture that answers these nine problems, component by component, is described in Governed Write-Back: A Reference Architecture.

REFERENCE

Glossary#

Terms from the companion design-cut document, defined here so this page stands alone.

Accept service / accept time
The platform component that receives a write intent, runs advisory validation, and records it. Accept time is when the intent arrives; apply time is when the executor acts on the source system. Validation verdicts differ in authority between the two.
Intent ledger
An append-only record of every write intent: payload, actor, validation verdicts, status, and outcome. It is simultaneously the queue, the audit trail, and (exposed as pending_intents) part of the read model.
Executor
The author-written function that performs the real-world call against the source system. It fires only for accepted ledger rows, never as part of a scheduled pipeline run.
Write classes (W1–W5)
The design cut's taxonomy: W1 append/create-new, W2 slow attribute update, W3 contended mutation, W4 state transition, W5 cross-system composite. The class determines routing (queue, immediate, refuse) and mandatory controls.
freshness_tolerance
A per-action declaration of how stale the validating snapshot may be for the validation to remain meaningful. Registration fails if the tolerance is tighter than the measured sync lag of the dimensions the validation reads.
expected_version
The version of the entity the caller believed it was acting on, carried on the intent and checked at apply time against the source. A mismatch fails the intent loudly instead of letting the last writer win silently.
Idempotency key
A unique key per intent, passed to (or checked against) the target system so that retries and re-deliveries produce the same single effect. What makes the inevitable duplicate submission harmless.
Sync watermark
The timestamp of a dimension's last successful load. Comparing a referenced entity against it distinguishes "this reference is invalid" from "this reference is newer than my knowledge."
unverifiable
The third validation verdict beside accepted and rejected: the snapshot cannot answer, typically because the entity may postdate the sync watermark. Policy decides whether unverifiable intents may queue for re-validation at apply time.
key_mapping
The declared path from a warehouse surrogate key, through the current dimension row, to the natural or API key the source system accepts. Intents are recorded against the natural key.
SCD2
Slowly changing dimensions, type 2: the warehouse pattern of keeping history by closing the old row and opening a new one on change. One entity becomes many rows, each with its own surrogate key and validity range.
Effective date
The date a change takes business effect, as distinct from the date it was entered. In effective-dated systems like Workday the two routinely differ in both directions (retro pay, future-dated reorgs), so "current" is a question about a date, not a stored value.
