Retail revenue reporting

Reverting a bad metric change on Databricks and DataOS

A retail pipeline published revenue metrics that finance and merchandising used daily. A request to add promo reporting changed the definition of one existing metric, and reports began showing inflated revenue. This is what it took to get the earlier numbers back on each platform.

TL;DR

Databricks
Every table, job and metric is owned separately and versioned separately, so restoring last week's state has to be coordinated across those owners. Teams pause the pipeline and fix forward instead, and reporting stays down until the fix ships.
DataOS
The tables, metric definitions and quality checks are one versioned data product, so last week's state is one revert. Reporting resumes on it within minutes while the promo work is redone in parallel.

The fix takes the same work on both platforms. The time reporting stays unavailable differs.

How it happened

Four steps, in order.

Before the change

The pipeline was already in production

Sales orders flowed through a chain of assets into a small set of published metrics that finance used to close the month and merchandising used for planning. Those definitions had not changed in months. Each asset in the chain had its own owner and its own release schedule.

The request

Merchandising asks for promo reporting

They want revenue before discounts, the campaigns driving the discounting, and the discount cost per promo. That means new fields in the tables and new metrics alongside the existing ones. The existing metrics were meant to stay as they were.

The defect

Net Revenue changed definition

While the promo metrics were added, Net Revenue was changed to read revenue before discounts. The metric kept its name, so no dashboard returned an error and no alert fired. The same report returned a higher number, and every team reading Net Revenue reported inflated revenue.

Before the change

Net Revenue
revenue − discounts
$4.2M

The definition finance signed off on.

After the change

Net Revenue
revenue  (discounts no longer subtracted)
$5.1M

Same name, same report, wrong number.

The decision

Restore the earlier definition, then redo the promo work

Finance reports the inflated figure. The team decides to put Net Revenue back to what it meant the week before, and to redo the promo work separately. What that restoration requires is where the two platforms differ.

What has to be reverted: one table, or everything behind the number?

The metric sits at the end of a chain: raw tables, cleaned tables, aggregates, metric definitions, quality checks, and the jobs that run them. Restoring one part of that chain does not restore the number finance was using.

Two recoveries

The same defect, and what each platform allows you to revert.

Databricks

Different owners, different lifecycles

Each asset in the chain has its own owner and its own lifecycle. Each one changed on its own schedule, so there is no single point in time at which all of them were last correct together. The faulty logic is also still scheduled to run tonight.

Because each asset has a different owner and a different lifecycle, reverting becomes a program management issue rather than a technical step: agreeing a target state with every owner, sequencing the reverts in dependency order, and holding the pause until all of them are done.

  1. Work out which tables and jobs the change touched
  2. Pause the schedules so the bad logic does not run again
  3. Pick a matching version for each asset, in dependency order
  4. Fix, validate, then restart everything

Because that coordination is slow, teams commonly skip the revert and fix forward instead. Reporting stays down until the fix is finished.

DataOS

One owner, one lifecycle, one version

Tables, aggregates, metric definitions and quality checks are versioned together as one data product, owned by one team. The state finance was using last week is a single named version, so the target of the revert is a version number.

One lifecycle means there is nothing to coordinate. There is no agreement to reach with four owners and no dependency order to work out, so reverting stays a technical step.

  1. Revert the data product to its last good version
  2. The earlier metrics are live again within minutes
  3. Redo the promo work in parallel, then release it

Reporting returns before the fix is written. Teams using Net Revenue keep working. Teams waiting on the new promo metrics wait as long as they already were.

Why the revert takes minutes

Reports read a stable name. The versions behind it are kept.

In the data product, each model keeps its built versions and reports read one unchanging name. Reverting points that name back at the version that was already built and validated, so there is no rebuild to wait for and no table to restore by hand.

Time to restore reporting

Both teams write the same fix. They differ in when reporting resumes.

Summary

What you can revert One table or one job at a time The whole data product, as one version

Metric definitions get changed by mistake on any platform. What differs is whether the earlier state can be restored as one version, or has to be reassembled from separately owned assets before reporting can resume.
