Internal · Working note · August 2026

A grain change, played through

The same one-line performance PR, in a Databricks-only environment and with DataOS in the loop. Everything reconciles to the kilo in both worlds. Only one of them ships a false dangerous-goods declaration.

The problem

logistics.cargo_lines holds one row per scanned item. Eight items across two containers; net 12,400 kg, tare 3,600, manifest gross 16,000. One aerosol pallet line carries a hazmat code: UN1950, 90 kg.

A performance PR pre-aggregates the table to pallet grain, because pallets are what gets loaded and billed. One line changes: a GROUP BY, with MAX() on the text columns so the schema stays identical and nothing downstream errors.

62% fewer rows, totals identical to the kilo. The PR says "no change to totals," which is true, so it's approved. And the dangerous-goods declaration for that shipment now reads 3,180 kg of UN1950 instead of 90 kg, because the aerosol's UN code came along for the ride on a row that's now a pallet.

The arithmetic is invariant under this change, so every arithmetic check is structurally blind to it. What changed is what a row means, and meaning isn't a number any reconciliation can touch. The general law: additive measures survive grain changes; counts collapse, ratios shift, attribution corrupts.

Databricks only

Databricks does notice. Data Quality Monitoring learns what each table usually looks like, expected row counts and commit cadence, with no configuration at all. When cargo_lines drops from 8 rows to 3, the completeness model flags it, the health indicator goes red in Catalog Explorer, and an alert reaches the table owner. So far, everything worked.

Then comes the triage. The owner opens the alert, finds the recent PR ("pre-aggregation for performance, no change to totals") and recomputes the totals. True, to the kilo. The anomaly gets marked expected, the model relearns its baseline, and three rows per shipment becomes the new normal. From that night on, the DG declaration ships 3,180 kg of UN1950 under a green health indicator.

The failure isn't in the monitor. It's in what the monitor's signal can be checked against. Nothing in this environment records what a row was promised to mean, so the only reference the owner has is the PR description, which is honest. A statistical alert plus an honest PR is a rubber stamp.

With DataOS

DataOS governs transformation, semantics, and metrics as one unit, and the contract for cargo_lines declares its grain: one row = one scanned item, joining 1:1 to orders.order_lines. Three acts.

Act 1 · the plan catches it

The same change hits vulcan plan before it merges. The diff is captured, classified breaking against the declared grain, every impacted asset listed, registered consumers named, and the product version bumps on apply.

Act 3 · the fix

The performance goal was legitimate; the mistake was where the aggregation lived. The author restores item grain in cargo_lines and moves the pallet pre-agg into rollup.pallet_billing_01, which declares pallet grain in its own contract:

"Oh, I can do this in Databricks?"

Mostly, yes. Every audit above was written by a person, and each has a Databricks equivalent: the 1:1 join is a DQX rule or a DLT expectation, the hazmat cap is an expectation, the reconciliation is a SQL alert. A fail-severity expectation will even halt its own pipeline. The checks travel fine.

What has no equivalent is the verdict. (Breaking) wasn't produced by running a check against data. It was produced by diffing a change against a declared grain. Databricks has nowhere to write that sentence, "one row is one scanned item," as something the platform holds you to, because there is no contract object to hold it. You can assert things about data. You cannot assert things about a change, and the change is where this incident started.

The rest follows from that missing object. The endangered audits appeared in the plan before any data moved; an expectation only exists at runtime. dg_declaration was blocked by a failure in a different model; an expectation halts only its own pipeline, and wiring one pipeline's failure to another's refusal is orchestration you build and then maintain. And these checks live inside the product and version with it, rather than scattered across pipeline code, DQX config, and a wiki page holding the SLA.

The checks are portable. The consequences aren't.

The alert, replayed in this world

The monitor fires exactly as before. Nothing here switches it off, and nothing should. What changes is what the triager finds when they look: a plan record. Breaking, grain change named, version bumped, three consumers notified, the declaration held at its last verified state. The same dismissal that was a guess against a PR description becomes an acknowledgment against a recorded change.
