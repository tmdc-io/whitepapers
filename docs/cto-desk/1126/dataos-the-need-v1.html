The need

Why non-tech companies need DataOS · 18 November 2026

Business teams can now build agents in hours. Getting one safely into production still takes weeks, and most never make it. Non-tech companies need a platform that makes the safe path the fast path.

This page sets out the evidence for that need. It expands section 1 of "DataOS for Engineering Leaders". Sources are inline and in appendix A. Section 8 says which sources are independent and which come from vendors.

The need in five lines
  • Building is no longer the hard part. People in every function build agents and apps with AI.
  • What they build is unsafe by default. It fails in identity and data access.
  • Companies cannot govern it today, so few builds reach production.
  • Non-tech companies feel this most. With few engineers, their safe answer is to block, and the block feeds the next round of sprawl.
  • The need is a platform that makes the safe path the fast path, for agents built in any tool.

Terms used below

AgentAn AI program that does a task for a person.
Vibe codingBuilding software by describing it to an AI tool, often without programming skills.
ProductionThe state where an agent or app runs for real users on real company data.
SprawlMany agents in many tools that nobody can list, trust, maintain or cost.
OWASPA nonprofit that publishes the standard lists of software security risks.

1The bottleneck moved

For years, the hard part of software was building it. A company that wanted a new internal tool needed engineers, a project and months of work. AI changed that. Today, a sales manager or a planner can describe a tool and get a working version in an afternoon.

The hard part is now the path into production. A working agent still needs sign-in, access to company systems with each person's own permissions, a security review, monitoring and an owner. None of that comes from the AI tool that built it. So the queue moved. It used to wait for engineers to build. Now it waits for someone to make the result safe.

This is the need that DataOS answers. The rest of this page shows the evidence.

2The evidence chain

The need rests on four links. Each link has its own evidence.

Building is cheap and widespreadLink 1
  • Of US workers who built a work tool with AI coding tools in the past year, 34% have no formal programming background (Zapier, May 2026).
  • Companies run about 12 agents each today and expect 67% more within two years (MuleSoft, Feb 2026).
  • At State Farm, staff created more than 3,000 AI agent identities in Microsoft Power Platform (Microsoft, Aug 2026).
  • Gartner forecasts that 40% of new enterprise production software will be built with vibe coding by 2028, as cited by Island (Island, Aug 2026).
What gets built is unsafe by defaultLink 2
  • AI-generated code contained an OWASP Top 10 flaw in about 44% of tasks, across more than 100 models. The rate barely changed from 2025 (Veracode, Jul 2026).
  • Real breaches failed in the same two places, identity and data access. The Tea app exposed about 72,000 ID photos from an open storage bucket (Engadget, Jul 2025). A flaw in the Base44 platform let anyone register for private enterprise apps (The Hacker News, Jul 2025).
  • Scans of vibe-coded apps report missing database protection and leaked keys in a large share of apps (SupaExplorer, Jan 2026).
  • Agents add their own risks. The OWASP list for AI applications ranks prompt injection first. It also lists excessive agency, where an agent gets more tools or access than its task needs (HackerOne on OWASP, 2025).
Companies cannot govern it todayLink 3
  • 84% of CIOs say that employees create agents and apps faster than IT can govern them. 81% do not fully see the agents built outside approved systems (Dataiku, 2026).
  • 74% of organizations say that agents get more access than they need. 43% run agents on shared service accounts (CSA and Aembit, Mar 2026).
  • Of 307 technology leaders, 93% worry about AI-built tools in production. Only 8% call their governance strong (Retool, Jun 2026).
  • Two-thirds of 2,000 CIOs and CTOs say that they are accountable for AI systems that they do not fully control (IBM, Jun 2026).
Money is moving to fix itLink 4
  • The average company spent 4.7 times its 2025 level on AI in 2026, against a plan of 1.9 times (Menlo Ventures, Nov 2026).
  • Microsoft now gives every new Copilot Studio agent its own identity, governed through Agent 365 (Microsoft).
  • Investors put more than $1.7B into eight companies in this space in 2026. Section 4 lists them.

5Why non-tech companies feel it most

A tech company can hire security engineers and review each app. A non-tech company cannot. It has many business builders and a small platform team, often fewer than ten engineers. It also holds regulated data: prices, customer records and HR data. So its only safe answer is to block what business teams build. The block starts a loop.

Many builders, few engineersBusiness teams build faster than anyone can review
The blockThe platform team stops business-built apps from reaching company systems
The queueRequests to approve apps wait for weeks, and nobody works through them
Shadow appsTeams build in tools that the block does not reach
Sprawl and an incidentA leak, a broken app or an audit question

The incident leads to a stricter block, and the loop starts again.

The engineering leader is caught inside this loop. The paper calls it being "the department of no". The way out is not a stricter block. It is a path that makes business-built agents safe by default, so the platform team can approve them in days.

6What stands between an agent and production

Brad Nietfeldt lists 21 security hurdles for AI-built apps, grouped in five launch gates (brad.expert, Nov 2026). His list targets public apps, and it leaves out the main risks of agents. The table adds those risks and shows which hurdles a platform removes and which stay with each app. Each hurdle links to the standard reference that defines it.

GateHurdlesWho removes it
Identity
  • Sign-in that can be bypassed
  • Forged login tokens
  • Stolen passwords
  • Account takeover
The platform, through company sign-in and a permission test on every call
Data
  • Open storage
  • Database tables open to too many users
The platform, through each person's own access on company systems
Boundary
  • Leaked secrets and source code
  • Risky third-party scripts
  • Requests that reach internal systems
The platform, through managed secrets, clean hosting and network limits
Operations
  • No logs or monitoring
  • No owner when the builder leaves
The platform, through one audit log, monitoring and a list of agents with owners
Agent risks
  • Prompt injection
  • Too many tools or permissions
  • Agents on shared accounts
Mostly the platform, through limits on tools and access per person. Prompt injection also needs care in each agent
Abuse
  • Fraud on public forms and messages
  • Clickjacking
  • Open redirects
Mostly the app. Less relevant behind company sign-in
Business logic
  • Prices or discounts that the user controls
  • Rules that run twice
The app. No platform removes these

Most of the hurdles sit in the layers that a platform can own. That is the case for a platform. It takes these hurdles off every app at once, and the security review then covers only what each app does.

7What the platform must provide

The evidence above sets the requirements. A platform that answers this need provides:

  1. Company sign-in and a permission test on every call, so no agent runs on a shared account.
  2. Access to company systems with each person's own permissions.
  3. One audit log across systems, with a list of agents, their owners and their users.
  4. Limits on what each agent can reach and do.
  5. One review of the platform, not one review per agent.
  6. All of this for agents built in any tool, not only in one vendor's tool.
  7. Correct business numbers, so agents use the same definitions as the reports.

The value proposition shows what each person gets from these requirements. The paper shows what our own deals say about the buyer.
